# NDMProgramm — план масштабного архитектурного рефакторинга

> **Назначение файла:** это одновременно архитектурный план и рабочий промпт для Codex.  
> Codex должен **проанализировать актуальный VBA-код целиком**, сопоставить его с требованиями ниже и выполнить рефакторинг.  
> Допускается масштабная перестройка классов, переименование и удаление устаревших сущностей, если это улучшает архитектуру и не меняет согласованную расчетную логику.

---

## 0. Главная задача и жесткие ограничения

Нужно провести **масштабный архитектурный рефакторинг** расчетного ядра NDMProgramm, прежде всего вокруг:

- расчета НДС;
- поиска предельных состояний;
- Capacity;
- нормальных и продольных трещин;
- хранения результатов;
- статусов и комментариев;
- записи Results / Summary.

### Что должно остаться неизменным

Если ниже явно не указано обратное:

- **математика и инженерная методика остаются как сейчас**;
- **численные результаты остаются как сейчас**;
- **основная последовательность и смысл расчетов остаются как сейчас**;
- **вывод на лист Results / Summary должен остаться визуально и содержательно таким же**, за исключением согласованного добавления `ResultComment`: в каждом расчетном блоке добавить один столбец с комментарием непосредственно перед общим статусом соответствующего раздела; остальные блоки, колонки, значения и общее поведение сохранить;
- существующие пользовательские настройки и профили по возможности сохраняются совместимыми;
- существующие глобальные regression / integration / UI tests должны проходить после рефакторинга, **кроме тестов, которые явно проверяют старую архитектуру, старые имена классов или иное поведение, которое настоящим ТЗ сознательно меняется**.

### Что разрешено и желательно менять

- границы ответственности классов;
- внутренние API;
- имена классов и методов;
- структуру результатов;
- дублирующую логику;
- расположение status / comment / diagnostic logic;
- внутренний способ переиспользования уже посчитанных НДС;
- устаревшие классы можно **удалять**, а не оставлять ради совместимости, если они больше не нужны;
- большие классы можно разделять на несколько специализированных;
- очевидные архитектурные и технические ошибки, обнаруженные в процессе, можно исправить, если это не меняет согласованную инженерную постановку.

> **Важно:** не ограничивай рефакторинг излишней осторожностью. Если для чистой архитектуры требуется серьезно перестроить внутренний код, сделай это. Но не используй архитектурный рефакторинг как повод незаметно менять расчетную методику.

# 1. Целевая архитектура

Нужно четко разделить четыре слоя:

```text
1. State
   Решение одного конкретного НДС.

2. Search
   Поиск предельного состояния / lambda по заданной траектории и критерию.

3. Engineering calculations
   Capacity, Crack, Stability и другие инженерные проверки,
   использующие готовые State/Search.

4. Result + Presentation
   Хранение готовых результатов, централизованные статусы/комментарии
   и пассивный вывод на лист.
```

Ключевой принцип:

> **Расчетные модули должны запрашивать нужное НДС, а не самостоятельно повторно запускать solver, если эквивалентное состояние уже было рассчитано.**

---

## 1.1. Универсальная сущность конечного НДС

Использовать и развить существующий `CSectionStateResult` как **единый формат конечного НДС**.

Он должен представлять любое конечное состояние, например:

- `StrengthState`;
- `CapacityState`;
- `PreCrackState`;
- `PostCrackState`;
- `CurrentCrackedState`;
- будущие дополнительные named states.

Состояние должно хранить все необходимое, чтобы после расчета другие модули и writers **не возвращались к solver для интерпретации результата**:

- тип состояния;
- фактический material model / spec;
- целевые `N / Mx / My`;
- найденные внутренние усилия;
- `epsilon0 / kappaX / kappaY`;
- невязки;
- ключевые extrema strains / stresses;
- признак convergence;
- physical-range / extension flags;
- iterations / solver-call metadata, если это полезно;
- status metadata;
- diagnostic / stop reason, если применимо.

Имена `BeforeMcrcState / AfterMcrcState` заменить на более общие:

```text
PreCrackState
PostCrackState
```

так как образование трещины уже не обязано быть связано только с чистым `Mcrc`.

---

## 1.2. Один общий механизм получения НДС

Существующий `CStateSolutionRunner` должен стать **общим механизмом решения одного State**.

Расчетные модули не должны самостоятельно разбирать:

- сошелся solver или нет;
- использовано ли extension;
- находится ли состояние в физическом диапазоне;
- какой внутренний status присвоить состоянию.

Это должно формироваться централизованно при создании `CSectionStateResult`.

Над ним нужен красивый механизм **Get-or-Solve / repository / provider**:

```text
Request State
    ↓
Есть полностью эквивалентное состояние?
    ├─ Да → вернуть готовый CSectionStateResult
    └─ Нет → решить через CStateSolutionRunner,
             сохранить,
             вернуть
```

Предпочтительная реализация — отдельный `CStateRepository`.

Если после анализа актуального кода Codex увидит существенно более естественную близкую реализацию, он может выбрать ее, но ответственность за хранение и переиспользование State не следует переносить в `CCombinationResult`: этот класс должен оставаться корнем результатов сочетания, а не превращаться в repository.

Обязательны следующие свойства:

1. **одно и то же конечное НДС не пересчитывается повторно**;
2. reuse работает между разными инженерными проверками;
3. ключ состояния должен учитывать не только `StateType`, но как минимум:
   - расчетные усилия;
   - material spec / material role;
   - режим state solution, если он способен изменить результат;
4. состояние хранится в результате одного LC и доступно всем потребителям;
5. reuse не должен случайно спутать `PostCrackState` и `CurrentCrackedState`, даже если material model одинаков.

### Что именно хранить в `CStateRepository`

`CStateRepository` должен хранить **только конечные, именованные и потенциально переиспользуемые НДС**, имеющие самостоятельный смысл для других частей программы, например:

- `StrengthState`;
- `CapacityState`;
- `PreCrackState`;
- `PostCrackState`;
- `CurrentCrackedState`.

Промежуточные пробные состояния, возникающие внутри `LimitSearch` при подборе `lambda`, **не складывать в общий `CStateRepository`**. Например:

```text
lambda = 0.5
lambda = 0.75
lambda = 0.68
Newton iteration / bracket probe / secant probe
```

Такие точки являются внутренней численной кухней конкретного Search.

При рефакторинге обязательно проверить и сохранить полезную идею текущего кэширования пробных `lambda`-точек: в существующей реализации повторно запрашиваемые точки могут восстанавливаться без нового solve и использоваться для ускорения поиска / warm start. **Не потерять эту оптимизацию при переносе Search-логики.**

При этом не фиксировать заранее конкретный класс или структуру кэша: Codex должен после анализа фактической реализации определить наиболее естественное место для локального кэша в новой Search-архитектуре. Обязательные требования только такие:

- кэш относится к конкретному Search / search-session и не смешивается с `CStateRepository`;
- он не становится глобальным хранилищем конечных State;
- повторно вычисленная эквивалентная пробная точка по возможности не должна запускать лишний solve;
- безопасность сопоставления пробной точки должна сохраняться, чтобы не перепутать разные load-path / нагрузки / настройки, влияющие на результат.

После того как Search нашел итоговую физически значимую точку, например `lambda_ult`, ее конечное НДС оформляется как соответствующий `CSectionStateResult` (например `CapacityState`) и только тогда может быть сохранено в `CStateRepository`.

## 1.3. Универсальный слой поиска предельного состояния

Нынешнюю общую математику:

- `CLoadPathVector`;
- `CLoadPathMath`;
- `CStateGuessBuilder`;

сохранить как общие низкоуровневые элементы, если после анализа Codex не найдет более чистого объединения.

Из текущего `CCapacitySolver` вынести универсальные поисковые алгоритмы, чтобы они **не знали**, ищут они Capacity или CrackFormation.

Рекомендуемая архитектура:

```text
CLimitSearchCoordinator
    ├─ CUltimateStrainSearch
    └─ CLoadMultiplierSearch
```

и универсальный:

```text
CLimitSearchResult
```

Поисковые алгоритмы должны работать в терминах:

```text
Target(lambda) = Offset + lambda * Base
```

и получать внешний **limit criterion** / criterion object / эквивалентный механизм.

Минимально должны существовать независимые критерии для:

- прочности / Capacity;
- образования нормальной трещины.

`CapacityCalculator` и `CrackFormationCalculator` должны пользоваться **одной и той же поисковой инфраструктурой**, а не содержать копии Newton / Jacobian / Bisection / Brent / Secant logic.

> Codex может выбрать конкретный интерфейс критерия и имена классов, если предложит более естественный вариант для VBA, но разделение **search algorithm ↔ physical criterion** обязательно.

### Стандартные исходы общего LimitSearch

`CLimitSearchResult` должен отличать **численную успешность поиска** от его физического исхода. Для этого зафиксировать общие `ResultCode` поиска:

| ResultCode | Смысл |
|---|---|
| `LIMIT_FOUND` | Найдена корректная `lambda`, при которой достигнут целевой критерий. |
| `INITIAL_STATE_BEYOND_LIMIT` | Уже при `lambda = 0` начальная / постоянная часть траектории достигает или превышает целевой критерий. |
| `CRITERION_NOT_REACHED` | Корректно установлено, что на рассматриваемой траектории целевой критерий не достигается. |
| `SEARCH_BOUND_REACHED` | Достигнута техническая граница поиска (`MaxLambda` или аналог), но нельзя утверждать, что критерий физически недостижим вообще. |

Важно:

- `INITIAL_STATE_BEYOND_LIMIT` — **не `NumFail`**. Это физически определенный исход начальной точки траектории.
- `CRITERION_NOT_REACHED` применять только тогда, когда не-достижение критерия действительно установлено физически / методически. Простое достижение `MaxLambda` должно давать `SEARCH_BOUND_REACHED`.
- Эти коды принадлежат общему Search-слою. Конкретный инженерный расчет трактует их на своем уровне.
- Для `CrackFormation` при режиме `Auto` код `INITIAL_STATE_BEYOND_LIMIT` может быть промежуточным сигналом для переключения на другую допустимую траекторию. Если пользователь явно задал фиксированный путь, например `lambda*Mxy`, а трещина уже образована от постоянной `N`, код сохраняется как фактический исход этого Search и трактуется `CCrackFormationCalculator`.
- Для `Capacity` тот же `INITIAL_STATE_BEYOND_LIMIT` означает, что базовая нагрузка уже превышает несущую способность и дальнейший поиск добавочной нагрузки по этой траектории не имеет смысла.

# 2. Централизованная система результатов, статусов и комментариев

Это обязательная часть рефакторинга.

## 2.1. Внутренний статус ≠ внешний статус

В расчетном ядре **не хранить строки** `"OK"`, `"FAIL"`, `"NumFail"` и т. п. как основной тип статуса.

Ввести единый внутренний enum, например:

```text
EResultStatus

rsUnset
rsNotRequested
rsNotApplicable
rsBlockedByDependency

rsSuccess
rsSuccessWithWarning

rsCheckFailed

rsNumericalFailure
rsInvalidInput
rsInvalidConfiguration
rsInternalError
```

Названия можно слегка адаптировать, если это улучшает единообразие проекта, но смысл должен сохраниться.

### Смысл

| Internal status | Смысл |
|---|---|
| `Unset` | результат еще не сформирован; в завершенном расчете нежелателен |
| `NotRequested` | расчет отключен профилем |
| `NotApplicable` | проверка физически/методически неприменима |
| `BlockedByDependency` | этап не запускался из-за результата обязательного предыдущего этапа |
| `Success` | расчет корректно завершен |
| `SuccessWithWarning` | корректный результат с fallback / особой веткой |
| `CheckFailed` | расчет корректен, но инженерная проверка не проходит |
| `NumericalFailure` | настоящая численная несходимость |
| `InvalidInput` | ошибка пользовательских исходных данных |
| `InvalidConfiguration` | ошибка профиля / настроек |
| `InternalError` | непредусмотренная внутренняя ошибка программы |

---

## 2.2. У каждого результата обязательны Status + Code + Comment

Каждая существенная result entity должна иметь единообразные метаданные, предпочтительно через отдельный маленький объект наподобие:

```text
CResultMeta
    InternalStatus
    ResultCode
    ResultComment
```

Можно добавить `DiagnosticDetails`, если это естественно для текущего кода.

### Требования к `ResultCode`

- короткий;
- стабильный;
- машинно-читаемый;
- не зависит от текста комментария;
- используется для точной причины результата.

Примеры:

```text
CRACK_NOT_FORMED
POST_CRACK_NO_CONVERGENCE
NO_TENSION_REBAR
CAPACITY_EXCEEDED
INVALID_PROFILE
BLOCKED_BY_POST_CRACK_STATE
```

### Требования к `ResultComment`

- **развернутый, но не длинный**;
- **на русском языке**;
- понятен инженеру без чтения diagnostic log;
- не используется как источник логики;
- пригоден для будущего вывода на лист.

Пример:

```text
"Расчет ширины не выполнялся, так как НДС непосредственно после образования трещины не сошлось."
```

---

## 2.3. Комментарии должны корректно агрегироваться

Если пользователю позже понадобится выводить комментарии на лист:

- комментарии должны **читабельно склеиваться**;
- не дублироваться;
- идти в логичном порядке;
- включать только сообщения, относящиеся к **конкретному выводимому блоку / типу расчета**.

Например:

- Crack-блок не должен тащить комментарий Stability;
- Capacity-блок не должен выводить комментарии Crack;
- Overall / Batch Summary при необходимости может собрать общий комментарий только из применимых верхнеуровневых результатов.

Не реализовывать склейку ad hoc внутри каждого writer.

Сделать **централизованный presentation/comment helper или другой единый механизм**, который подготавливает релевантный display comment перед записью.

Конкретную форму реализации Codex может выбрать по текущей архитектуре.

---

## 2.4. Один класс отвечает за преобразование статусов наружу

Развить существующий `CBatchStatusPolicy` либо аккуратно переименовать его в более общий класс, например:

```text
CCalculationStatusPolicy
```

Он должен стать **единственным шлюзом**:

```text
InternalStatus
    ↓
ExternalStatus
    ↓
DisplayText
```

Внешнее слабое представление оставить компактным:

```text
OK
FAIL
BaseFail
NumFail
InputErr
CalcErr
N/A
```

Рекомендуемое соответствие по умолчанию:

| Internal | External |
|---|---|
| `Unset` | `CalcErr` |
| `NotRequested` | `N/A` |
| `NotApplicable` | `N/A` |
| `BlockedByDependency` | `N/A` |
| `Success` | `OK` |
| `SuccessWithWarning` | `OK` |
| `CheckFailed` | `FAIL` |
| `NumericalFailure` | `NumFail` |
| `InvalidInput` | `InputErr` |
| `InvalidConfiguration` | `InputErr` |
| `InternalError` | `CalcErr` |

Допускается **контекстное централизованное отображение** по сочетанию типа результата, `InternalStatus` и `ResultCode`. Обязательный частный случай:

```text
CapacityResult
InternalStatus = rsCheckFailed
ResultCode = INITIAL_STATE_BEYOND_LIMIT
        ↓
ExternalStatus = BaseFail
```

`BaseFail` использовать только для Capacity / несущей способности по прочности: он означает, что уже при `lambda = 0` базовая часть нагрузки не несется сечением. Для других расчетов `INITIAL_STATE_BEYOND_LIMIT` трактуется их собственным инженерным слоем и не обязан давать `BaseFail`.

В этом же централизованном месте должны находиться:

- display text;
- приоритет статусов;
- aggregation rules;
- conversion legacy → new status на время миграции, если это понадобится.

**Ни один writer не должен самостоятельно интерпретировать Converged / ExtensionUsed / StopReason / неизвестные строки статусов.**

Если позже понадобится заменить внешний текст `NumFail` на другой, это должно делаться **в одном месте**, без правок расчетчиков и writers.

### Комментарии в коде для статусов и ResultCode

Все централизованно объявленные внутренние статусы и стандартные `ResultCode` должны иметь **понятный русский комментарий прямо в enum / классе / модуле, где они определены**:

- что означает этот статус / код сам по себе;
- чем он отличается от близких состояний;
- когда его допустимо формировать.

На более высоком уровне, где общий статус / код получает конкретный инженерный смысл, также оставить короткий русский комментарий о его трактовке именно в этом слое.

Пример:

```text
Search:
INITIAL_STATE_BEYOND_LIMIT
' Критерий уже достигнут при lambda = 0.

Capacity:
' Для Capacity этот код означает, что базовая нагрузка уже не несется;
' внешний статус отображается как BaseFail.

CrackFormation:
' В Auto может служить сигналом сменить load-path;
' при фиксированном path означает, что трещина уже вызвана постоянной частью.
```

Не заставлять разработчика восстанавливать смысл статусов по цепочке вызовов или по текстам writers.

# 3. Новая архитектура Capacity и Crack

## 3.1. Capacity

Текущий `CCapacitySolver` после миграции универсальных search algorithms либо удалить, либо переименовать и сильно сузить до роли Capacity-specific coordinator.

Целевая логика:

```text
CCapacityCalculator
    ↓
Strength limit criterion
    ↓
CLimitSearchCoordinator
    ↓
CLimitSearchResult
    ↓
CCapacityResult
```

Capacity-specific код отвечает за:

- создание нужной load-path;
- выбор strength material spec;
- интерпретацию найденного limit result;
- инженерский `CheckFailed / Success`;
- свои result fields / comment.

Он **не должен** содержать общие реализации Newton / UltimateStrain / Bisection / Brent / Secant.

---

## 3.2. Crack

Текущий `CCrackWidthCalculator` удалить как монолит и разделить обязанности.

Рекомендуемая структура:

```text
CCrackCalculator                — coordinator
CCrackFormationCalculator       — образование трещины
CCrackSectionDataCalculator     — Abt, As, ds, selected rebars, stresses, geometry
CCrackWidthFormulaCalculator    — ls, phi, psi, a_crc, utilization
```

Codex может слегка скорректировать число классов, если найдет более естественное разделение, но **solver/search/formula/geometry нельзя снова смешать в одном большом классе**.

### Последовательность

Сохранить текущий инженерный смысл:

```text
CrackFormation
    ↓
PreCrackState
    ↓
PostCrackState
    ↓
CurrentCrackedState, если он нужен хотя бы одной включенной проверке
    ├─ LongitudinalCrack
    └─ CrackWidth, если нормальная трещина образована
```

### Важное уточнение по `CurrentCrackedState`

`CurrentCrackedState` не является «состоянием только для ширины нормальной трещины».

По текущей логике оно нужно как минимум для:

- проверки продольных трещин;
- ширины нормальной трещины;
- Results / visualization, если выбран этот state.

Поэтому:

> Если `CurrentCrackedState` нужен хотя бы одному активному потребителю, он рассчитывается.  
> Если полностью эквивалентное НДС уже существует, оно **переиспользуется**, а не считается повторно.

Longitudinal crack calculation должен стать отдельным потребителем готового `CurrentCrackedState`, а не причиной держать лишнюю solver-логику внутри CrackWidth.

---

## 3.3. Формула ширины раскрытия должна быть чистой

После получения:

```text
Abt
As
ds
sigma_s
sigma_s,crc
Es
phi1
phi2
phi3
...
```

`CCrackWidthFormulaCalculator` выполняет только формульную математику.

В нем не должно быть:

- `CSectionSolver`;
- `CStateSolutionRunner`;
- Newton / Secant;
- load path search;
- material provider logic.

Если обязательный предыдущий этап не получен:

```text
CrackWidthResult.Status = BlockedByDependency / NotApplicable
```

а не фиктивный `NumFail`.

`NumFail` принадлежит именно той сущности, solver/search которой действительно не сошелся.

# 4. Result graph и пассивные Writers

## 4.1. CCombinationResult как корень, а не плоский мешок полей

По возможности уйти от большого числа параллельных Public Double/String полей.

Целевая композиция примерно такая:

```text
CCombinationResult
│
├─ States
│   ├─ StrengthState
│   ├─ CapacityState
│   ├─ PreCrackState
│   ├─ PostCrackState
│   └─ CurrentCrackedState
│
├─ CapacityResult
├─ CrackResult
│   ├─ FormationResult
│   ├─ WidthResult
│   └─ LongitudinalResult
├─ StabilityResult
│
└─ Meta
```

Не обязательно одномоментно удалять каждый legacy property, если это создаст бессмысленный объем миграции, но итоговая архитектура должна иметь **один источник правды**, а не две параллельные модели результата.

---

## 4.2. Writers должны стать пассивными

`CBatchResultWriter`, `CCrackSummaryWriter` и другие writers:

### Должны

- получать готовые result entities;
- обращаться к централизованной status policy;
- получать уже подготовленный relevant display comment;
- конвертировать единицы;
- записывать данные;
- оформлять лист.

### Не должны

- решать, является ли отсутствие state ошибкой;
- анализировать `Converged`;
- трактовать `ExtensionUsed`;
- присваивать `OK / FAIL / NumFail`;
- определять, можно ли запускать следующий расчет;
- повторять инженерную логику Capacity / Crack / Stability;
- склеивать комментарии по собственным правилам.

### Вывод на лист

**Должен остаться таким же, как сейчас.**

То есть рефакторинг writers нужен для устранения вредной логики, но **не для редизайна Results**.

В каждом расчетном блоке Results / Summary добавить столбец `ResultComment` непосредственно перед общим статусом соответствующего раздела. Writer должен получать для него уже готовый комментарий, относящийся только к этому блоку: отфильтрованный по типу расчета, без дублей и при необходимости читабельно склеенный централизованным механизмом. Других изменений структуры вывода в рамках этого рефакторинга не требуется.

# 5. План выполнения — 5 крупных этапов


## Организация длинного рефакторинга: Git и восстановление контекста Codex

Этот рефакторинг достаточно большой, поэтому нельзя полагаться только на текущий диалоговый контекст Codex. Git и короткие файлы состояния в репозитории должны использоваться как внешний источник истины, по которому Codex сможет восстановить нить работы после compaction / очистки контекста.

### Baseline старой рабочей архитектуры

Перед началом основных правок Codex должен:

- определить текущий рабочий `HEAD`, соответствующий последней заведомо рабочей версии старой архитектуры;
- сохранить его hash как **baseline** рефакторинга в progress/status-файле;
- не переписывать и не разрушать этот baseline;
- при необходимости сравнивать текущую реализацию с baseline через Git, а не пытаться восстанавливать старое поведение по памяти.

Baseline нужен прежде всего как эталон поведения и источник для сравнения:

- что было до рефакторинга;
- что уже изменено;
- не потеряна ли существующая рабочая логика;
- где именно появилось изменение поведения.

### Progress / status как внешняя память

На время рефакторинга Codex должен вести в репозитории короткий Markdown-файл прогресса. Конкретное имя и расположение файла не фиксировать заранее: выбрать естественное место, согласованное со структурой проекта.

В этом файле достаточно поддерживать:

```text
Baseline:
<commit hash>

Completed:
- ...

Current:
- ...

Important decisions:
- ...

Known temporary issues:
- ...

Next:
- ...
```

Это не дублирование полного архитектурного MD. Файл должен быть коротким журналом фактического состояния работ.

После каждого законченного значимого этапа Codex должен обновлять этот progress/status-файл.

### Восстановление состояния после compaction

Если Codex по ходу длинной задачи больше не уверен:

- какой этап уже выполнен;
- какие классы уже перенесены;
- какие решения были зафиксированы;
- что осталось сделать;
- является ли текущее изменение новым или уже выполненным ранее;

он должен **сначала восстановить состояние проекта**, а уже потом продолжать правки.

Минимальный источник восстановления:

```text
git status
git diff
git log
baseline commit
этот architecture/refactoring MD
progress/status MD
```

При необходимости дополнительно использовать `git show` / сравнение с baseline или промежуточными milestone commits.

Не повторять уже выполненные этапы только потому, что они выпали из текущего диалогового контекста.

### Промежуточные рабочие точки Git

По возможности большие этапы рефакторинга следует завершать отдельными логическими Git milestone-точками, когда:

- этап закончен;
- проект компилируется;
- соответствующие тесты проходят;
- временная миграционная логика находится в согласованном состоянии.

Не делать commit после каждой мелкой правки и не дробить историю искусственно. Конкретную границу milestone выбирать по фактической структуре работ.

Если среда Codex не предполагает автоматическое создание commit-ов либо это нежелательно в текущем workflow, то как минимум progress/status-файл и Git diff должны позволять однозначно восстановить состояние между этапами.

### Правила безопасности работы с Git

- Git использовать как источник истории и сравнения, а не как повод автоматически откатывать пользовательские изменения.
- Не выполнять destructive reset / checkout / rewrite history без явной необходимости и понимания последствий.
- Не откатывать существующие пользовательские изменения, не относящиеся к текущему рефакторингу.
- Перед крупным этапом понимать текущее состояние `git status`.
- После этапа проверять diff и тесты, чтобы случайные изменения не «протекли» в соседние части проекта.

Главная цель этого блока: **рефакторинг должен оставаться продолжимым даже после сильного сокращения контекста Codex**. Источником истины являются текущее состояние Git, согласованный архитектурный MD и короткий фактический progress/status-файл, а не только история диалога.

## Этап 1. Новый фундамент Result / Status / State

Сначала сформировать новый каркас:

- единый `EResultStatus`;
- result metadata (`Status + Code + Comment`);
- центральная status policy;
- расширенный `CSectionStateResult`;
- централизованный механизм хранения/поиска named states;
- Get-or-Solve / reuse состояний.

На этом этапе:

- максимально сохранить текущее поведение;
- временные legacy adapters допустимы;
- writers пока могут продолжать работать через совместимый слой;
- заложить основу, чтобы последующие этапы не плодили новые временные API.

**Критерий завершения:** можно создать, сохранить, найти и повторно использовать state; внутренний status больше не обязан быть строкой; старые внешние тексты статусов по-прежнему выдаются централизованно.

---

## Этап 2. Обобщить StateSolution и LimitSearch

Перевести решение НДС и поиск предела на общую инфраструктуру:

- `CStateSolutionRunner` возвращает/формирует полноценный `CSectionStateResult`;
- вынести `UltimateStrain` и `LoadMultiplier` из Capacity-specific solver;
- общий `CLimitSearchCoordinator`;
- общий `CLimitSearchResult`;
- отдельные physical criteria.

После этого сначала перевести Capacity на новую инфраструктуру и удалить/сузить старый `CCapacitySolver`.

**Критерий завершения:** Capacity дает те же инженерные и численные результаты, но search algorithms больше не принадлежат Capacity.

---

## Этап 3. Полностью перестроить Crack-модуль

Разрезать монолитный `CCrackWidthCalculator`:

- formation;
- state sequence;
- section/tension-zone data;
- pure formula;
- longitudinal crack consumer.

Перевести crack formation на общий LimitSearch.

Использовать:

```text
PreCrackState
PostCrackState
CurrentCrackedState
```

через единый state repository/provider.

Не пересчитывать `CurrentCrackedState`, если он уже был получен другим потребителем.

После успешной миграции старый `CCrackWidthCalculator` удалить.

**Критерий завершения:** все текущие Crack результаты совпадают, но solver/search/formula responsibilities физически разделены.

---

## Этап 4. Перестроить Result aggregation и Writers

Перевести `CCombinationResult` и верхнеуровневый batch orchestration на новые result entities.

Централизовать:

- aggregation внутренних статусов;
- внешний display status;
- result comments;
- relevant comment composition.

Удалить из writers расчетную и статусную логику.

Сохранить существующий Results / Summary output.

**Критерий завершения:** writers только представляют готовые результаты; изменение display text статуса требует правки одного централизованного места.

---

## Этап 5. Очистка, тесты и окончательная проверка архитектуры

После миграции:

- удалить мертвые legacy classes / methods / duplicated fields;
- переименовать классы, если их старое имя больше не соответствует ответственности;
- убрать временные adapters, которые больше не нужны;
- пройти по всему проекту и проверить, что нигде не осталось:
  - локального строкового парсинга статусов;
  - повторного solver для уже существующего equivalent state;
  - Capacity/Crack-specific копий общей search mathematics;
  - инженерной логики в writers;
  - комментариев, используемых как машинные условия.

### Тесты

Обязательно:

1. Запустить **весь существующий глобальный набор тестов**.
2. Исправлять production-код, если тест обнаруживает реальную регрессию.
3. Менять тест только если он явно проверяет старую архитектуру / старое имя / сознательно измененную внутреннюю структуру.
4. Добавить новые regression tests для:
   - status mapping;
   - aggregation;
   - ResultCode / ResultComment;
   - `BlockedByDependency`;
   - state reuse / отсутствие повторного solve;
   - отсутствие лишних повторных solve для эквивалентных пробных `lambda`-точек внутри Search, если текущая логика поиска предполагает их повторное использование;
   - reuse `CurrentCrackedState` между longitudinal crack и crack width;
   - Capacity и CrackFormation через общий LimitSearch;
   - `LIMIT_FOUND / INITIAL_STATE_BEYOND_LIMIT / CRITERION_NOT_REACHED / SEARCH_BOUND_REACHED`;
   - Capacity `INITIAL_STATE_BEYOND_LIMIT` → внешний `BaseFail`;
   - `sigma_s,crc <= 0` → `psi_s = 1.0`, без ложного `NumFail`;
   - неизменность основных расчетных результатов.
5. После завершения еще раз пройти весь этот MD-файл **пункт за пунктом** и проверить соответствие реализации.

# 6. Важные правила для Codex во время рефакторинга

### Не делать архитектуру ради количества классов

Нужна чистая ответственность, а не максимальное число сущностей.

Если после анализа актуального кода и понимания реализации становится ясно, что предлагаемый новый класс будет очень маленьким, простым и не имеет самостоятельной значимой ответственности, **не создавать отдельный класс только ради схемы**. Его ответственность следует аккуратно включить в ближайший логически подходящий класс или модуль.

Если два маленьких класса естественно объединяются без смешения обязанностей, допускается объединить. Разделение на `State / Search / Engineering calculations / Result + Presentation` является разделением ответственности и не требует обязательного отдельного класса для каждого элемента схемы.

Если текущий большой класс фактически содержит несколько независимых механизмов, его лучше разделить.

---

### Не сохранять ненужные legacy-классы

Если после миграции класс больше не имеет собственной ответственности:

- удалить его;
- либо переименовать и сузить до новой ответственности.

Не оставлять thin-wrapper только ради старого имени, если в нем нет реальной необходимости.

---

### Не менять математику скрытно

Если при рефакторинге обнаружена очевидная ошибка:

- исправить ее;
- четко зафиксировать в итоговом отчете;
- добавить regression test;
- отдельно отметить, почему это bug fix, а не изменение методики.

Если вопрос спорный или методический — **не менять без отдельного решения пользователя**.

---

### Зафиксированные решения по ранее открытым edge case

Ранее обсуждавшиеся специальные случаи больше не считать открытыми вопросами.

#### 1. Начальная точка load-path уже достигает предела

Использовать общий Search-код:

```text
INITIAL_STATE_BEYOND_LIMIT
```

Дальнейшая трактовка выполняется инженерным слоем:

- `Capacity` → `rsCheckFailed` и внешний `BaseFail`;
- `CrackFormation + Auto` → допускается переключение на другую траекторию;
- `CrackFormation + фиксированный path` → сохранить код как физический исход выбранной траектории и сформировать понятный русский `ResultComment`.

Это не `NumFail`.

#### 2. `sigma_s,crc` получилось неположительным

Не считать это численной ошибкой само по себе.

Для автоматического коэффициента:

```text
psi_s = 1 - 0.8 * sigma_s,crc / sigma_s
```

расчетный `psi_s` не должен превышать `1.0`; если `sigma_s,crc <= 0`, принимать `psi_s = 1.0` и продолжать расчет при корректно найденных обязательных State.

Сохранить общую защиту:

```text
0 <= psi_s <= 1
```

В текущем коде соответствующая защита уже существует; при рефакторинге ее необходимо **сохранить**, а не превратить этот физический случай в `NumFail`.
