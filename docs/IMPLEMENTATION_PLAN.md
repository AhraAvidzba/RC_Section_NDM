# Implementation Plan

Дата: 2026-07-19.

Этот план уточняет дальнейшие этапы после аудита текущей реализации. Он не
заменяет `docs/ImplementationPlan.md`, а фиксирует новую дорожную карту
рефакторинга и расширения архитектуры с учетом фактического состояния кода.

## Общие правила выполнения этапов

Для каждого этапа:

1. выполнить локальный аудит затрагиваемых модулей;
2. не менять математическую модель без отдельного обоснования;
3. вносить минимальные законченные изменения;
4. запускать релевантные тесты;
5. фиксировать, что изменилось относительно исходного поведения;
6. не переходить дальше при провале регрессии.

Если Excel COM зависает, не тратить время на повторные попытки. Пользователю
сразу предлагается команда:

```powershell
Get-Process EXCEL -ErrorAction SilentlyContinue | Stop-Process -Force
```

Статус: выполнен в рамках текущей задачи.

## Этап 1. Регрессионная база

Цель: зафиксировать текущее поведение перед рефакторингом.

Статус: выполнен 2026-07-19.

Принятое архитектурное решение: в целевой архитектуре остается только единый
совместный расчет `N + Mx + My`. Отдельные пользовательские запуски и
отдельные результаты по `Mx` и `My` больше не развиваются. Одноосный изгиб
проверяется только как частный случай общей постановки при `My = 0` или
`Mx = 0`.

На этапе 1 `SolveMx`, `SolveMy`, `rngResultMx` и `rngResultMy` не удалялись.
Их текущие точки использования зафиксированы в `docs/TEST_CASES.md` для
удаления на следующем этапе.

Минимальные действия:

- создать единый регрессионный запуск всех существующих `Run-*.ps1`;
- добавить отчетный файл с результатами текущей стабильной версии;
- добавить тесты:
  - круг с текущим проверочным набором;
  - чистое сжатие;
  - Mx с малым ненулевым My;
  - My с малым ненулевым Mx;
  - двухосный изгиб;
  - симметрия круглого сечения;
  - повторный запуск без изменения исходных данных;
  - повторный запуск после изменения геометрии;
  - перенос начала координат для физически эквивалентной задачи;
  - сравнение данных в оперативном результате и выгрузке на лист, если лист результата уже создан.

Ограничение: если точного эталона нет, использовать текущие результаты как
временную регрессионную базу с пометкой `TEMPORARY_BASELINE`.

Ожидаемый результат:

- `docs/TEST_CASES.md` или дополнение к существующему плану валидации;
- таблица тестов с входными данными, фактическими результатами, временем и статусом.

Фактический результат:

- добавлен общий запуск `tools/build_workbook/Run-AllTests.ps1`;
- добавлен регрессионный запуск `tools/build_workbook/Run-RegressionBaselineTests.ps1`;
- добавлен модуль `tests/modTestRegressionBaseline.bas`;
- сохранены отчеты `docs/regression/Stage01_AllTests_Report.txt` и
  `docs/regression/Stage01_RegressionBaseline_Raw.txt`;
- обновлен `docs/TEST_CASES.md`.

## Этап 2. Упорядочивание настроек

Цель: убрать неоднозначное управление расчетом.

Статус: выполнен в два шага после принятия регрессионной базы.

Выполненное решение:

- удалены отдельные пользовательские и расчетные ветви `Mx` и `My`;
- единый публичный метод capacity: `CCapacitySolver.SolveByLoadMultiplier`;
- единый диапазон результата: `rngResultSection`;
- удалены настройки `Capacity.CalculateMx`, `Capacity.CalculateMy`,
  `Capacity.CalculateMxy`;
- одноосные случаи сохранены как частные случаи общей постановки
  `N + Mx + My`;
- настройки `System` сведены в единый каталог и разделены на именованные диапазоны
  `SolverSettings`, `CapacitySettings`, `ConcreteDiagram`, `SteelDiagram`,
  `GeometrySettings`, `OutputSettings`, `AutoCADSettings`;
- `Geometry.Type`, `Circle.Diameter`, `Circle.CenterX`, `Circle.CenterY` читаются из `System`;
  лист `Расчет` только отображает эти значения формулами;
- жесткие перекрытия capacity-настроек в `CBatchSectionCalculator` убраны;
- создан `docs/SETTINGS_REFERENCE.md`.

Не выполнено на этом этапе и остается на будущие задачи:

- второй метод несущей способности;
- изменение поведения `NumericalFailure`;
- кэширование расчетных объектов;
- графики, AutoCAD-импорт и новые алгоритмы поиска `lambda`.

Выполненные проверки:

- все рабочие ключи `rngSystemSettings` читаются через `CSystemSettingsReader`;
- дубли рабочих ключей отсутствуют;
- удаленные ключи не присутствуют в книге и не используются как настройки;
- `Capacity.MaxLambda` из `System` доходит до batch-расчета и не перекрывается кодом;
- новые смысловые диапазоны настроек существуют в книге;
- выпадающие списки добавлены только для реально поддерживаемых вариантов.

Особое требование:

- формулы на листах допустимы и предпочтительны для прозрачных пользовательских расчетов;
- расчетное ядро не должно использовать листы как рабочую память.

Результат:

- обновлен `docs/SETTINGS_REFERENCE.md`;
- обновлен `docs/TEST_CASES.md`;
- полный `Run-AllTests.ps1` проходит без ошибок.

## Этап 3. Унификация постановки N-Mx-My

Цель: сохранить одну расчетную постановку совместного действия `N + Mx + My`.

Минимальные действия:

- подтвердить, что публичные обертки `SolveMx`, `SolveMy`, `SolveMxy` отсутствуют;
- не восстанавливать отдельные подсистемы для Mx и My;
- документировать систему координат, знаки и приложение моментов;
- добавить тест координатной инвариантности;
- добавить тест переноса момента при смене начала координат, если пользовательский ввод позволяет перенос начала.

Ожидаемый результат:

- обновление `docs/CoordinateSystem.md`;
- тесты равновесия после переноса координат.

## Этап 4. Решатель равновесия

Цель: сделать выбор метода решателя явным и честным.

Фактически сейчас есть:

- full Newton;
- tangent matrix;
- damping;
- line search;
- load stepping.

На этапе 4:

- не добавлять фиктивные методы в список;
- ввести настройку метода только с реально поддерживаемыми значениями;
- централизовать настройки `CSectionSolver`;
- расширить объект результата решателя статусами:
  - `Success`;
  - `StatusCode`;
  - `StatusMessage`;
  - `IterationCount`;
  - `ResidualN/Mx/My`;
  - `ResidualNorm`;
  - `Epsilon0/KappaX/KappaY`;
  - диагностические признаки.

Ожидаемый результат:

- тест метода Newton;
- тест line search on/off;
- тест численной несходимости без трактовки как физического разрушения.

## Этап 5. Два метода несущей способности

Цель: добавить явный выбор метода capacity без поломки текущего bisection-поиска.

Методы:

```text
SolveByLoadMultiplier
SolveByUltimateStrain
```

### 5.1 SolveByLoadMultiplier

Сохранить текущий закон:

```text
N = const
Mx = lambda * MxBase
My = lambda * MyBase
```

До изменения закона масштабирования нужно отдельное решение и тест.

Сначала привести текущий bisection к единому интерфейсу, затем при
необходимости добавлять Brent или safeguarded secant.

### 5.2 SolveByUltimateStrain

Добавлять только после регрессионной базы и упорядочения настроек.

Уравнения:

1. равновесие по `N`;
2. сохранение направления вектора моментов;
3. достижение заданной предельной деформации.

Критическое бетонное волокно и критический стержень выбирать заново на каждой
итерации, но не решать отдельную задачу для каждого волокна.

Ожидаемый результат:

- сравнительные тесты двух методов;
- отчет по совпадению/расхождению `lambda`;
- число вызовов внутреннего решателя и время.

## Этап 6. Единый объект результата и технический лист

Цель: создать снимок наиболее неблагоприятного сочетания.

Создать класс:

```text
CAnalysisResult
```

или эквивалентную VBA-структуру.

Содержимое:

- `ResultDataVersion`;
- критическое сочетание;
- исходные `N`, `Mx`, `My`;
- внутренние `Nint`, `Mxint`, `Myint`;
- `epsilon0`, `kappaX`, `kappaY`;
- `lambda` или utilization;
- метод расчета;
- статус;
- бетонные волокна;
- арматурные стержни;
- деформации, напряжения, силы;
- признаки растяжения/сжатия;
- нейтральная линия;
- координатные и главные оси.

Создать технический лист, например:

```text
ResultData
```

Таблицы:

- `Summary`;
- `ConcreteFibers`;
- `ReinforcementBars`.

Запись выполнять пакетно через двумерные массивы.

## Этап 7. Кэширование геометрии

Цель: не перестраивать сетку при неизменной геометрии.

Создать:

- `GeometrySignature`;
- `MeshSignature`;
- объект кэша в управляющем слое.

Сброс кэша при изменении:

- типа геометрии;
- размеров;
- центра;
- шага сетки;
- `Mesh.BoundarySubdivisions`;
- арматуры;
- источника геометрии;
- импортированной AutoCAD-сетки.

Материалы и нагрузки не должны сбрасывать сетку.

Тесты:

- первый расчет;
- повторный расчет без изменения геометрии;
- изменение нагрузки;
- изменение шага сетки.

## Этап 8. График геометрии и результата

Цель: визуализация по `ResultData`, без повторного расчета.

Требования:

- отдельный лист визуализации;
- XY-график, не отдельная фигура на каждое волокно;
- одинаковый масштаб X/Y;
- бетонные волокна;
- арматура;
- пользовательские оси;
- главные оси;
- нейтральная линия;
- сжатая/растянутая зоны;
- режим окраски по знаку деформации как первый стабильный режим.

## Этап 9. Импорт готовой сетки AutoCAD

Цель: добавить источник геометрии `AutoCADRegions`.

Ограничения:

- только Late Binding;
- не добавлять Reference на AutoCAD;
- книга должна работать без AutoCAD;
- импортировать готовые `Region`, не строить сетку в Excel.

Внутренний формат импортированных областей должен совпадать с форматом
`TFiber`:

- `ID` или `Handle`;
- `X`;
- `Y`;
- `Area`;
- `MaterialID`.

Сначала импортировать бетонные области. Арматуру импортировать только после
отдельного аудита минимального формата.
