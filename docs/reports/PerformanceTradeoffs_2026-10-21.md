# Эксперименты со скоростью формирования и расчёта сечения — 21.10.2026

Рабочие исходники, книга и ALL CODE не изменены. Все варианты реализованы только
в изолированных диагностических копиях. Это исследование компромиссов, а не внедрение
нового режима и не полная расчётная приёмка.

## Методика

- База: `4ccfe9c7336d4c49e665dee42a4e5d24c200c1ff`, ветка `codex/linked-rebar-row-offsets`.
- Рабочая книга SHA256: `7B4C769D3813CE0057FFA93026281CD8ED7D3DC23F60159A2655882AB37D2772`.
- ALL CODE SHA256: `F88F3868FF9C3FF0D14DB981D6F90CC1467D4CB0E426A462497EF86FC158950E`.
- Windows, локальный Excel COM, Intel Core i7-8700. Собственные экземпляры Excel,
  пользовательские Excel/AutoCAD не закрывались. Абсолютное время зависит от нагрузки компьютера.
- Круг D300 мм: 884 бетонных элемента и 8 стержней d20, as40. Круг D1000 мм:
  8496 бетонных элементов и те же 8 стержней. Шаг сетки 10 мм, граничное дробление 2.
- Основные серии: PR2, N=-100000 Н, Mx=-4000000 Н·мм, My=-3000000 Н·мм,
  точка нагрузки по действующим настройкам. PR2 запрашивает расчёт трещин;
  отдельное прямое НДС прочности, несущая способность и устойчивость в этом профиле
  выключены. Их совместная работа проверена ниже отдельным batch из шести сочетаний.
  Знак N соответствует внутренней системе.
- QPC охватывает чтение настройки сообщений, всю FormSectionForWorkbook либо
  RunSectionCalculationForWorkbook, подготовку/восстановление Excel, запись, txt-отчёт и схему.
  Подготовка фикстуры, запуск Excel, компиляция, подтверждение окон человеком и проверки
  равенства находятся вне таймера. Это полный макрос, а не только solver.
- Для каждого режима сначала отдельный прогрев; затем медиана трёх повторов на 884
  элементах, двух на 8496 и в batch. Первые запуски сохранены в CSV как repetition=0,
  но не смешаны с прогретыми. Первый вход guard в новом Excel занимал около 2,4 с.
- × больше 1 означает ускорение. Коэффициенты рассчитаны относительно Full **той же серии**.
  FullEnd в поздних сериях контролирует дрейф времени. Разницу в несколько процентов
  не следует считать устойчивым выигрышем.

## Запрошенный вариант компактного JSON

В JSON переводились rngNDMSectionGeometry, rngNDMSectionContours,
rngNDMSectionAnnotations и rngNDMMaterialDiagrams. **Сводки прочности/НДС, трещин,
устойчивости и подробные НДС элементов оставались обычными таблицами.** Небольшая
таблица свойств сечения также оставалась обычной, поскольку содержит данные состояний
и ссылки единиц. Таким образом, выигрыш не получен скрытым удалением результатов.

JSON записывает заголовки один раз, постоянные столбцы — одним значением, остальные —
массивами. Весь текст разбит на фрагменты по 4000 символов и записан одним Value2.
Декодирование входит в время расчёта и схемы, готовая модель между ними не подставляется.

## Проверки и ограничения

В вариантах вывода, кроме NoReport и десятичного JSON, проверенные расчётные поля совпали.
Сравнивались скалярные свойства объектов результатов и конечные НДС всех элементов;
внутренние промежуточные массивы алгоритмов трещин этим сравнением не покрыты.
Допуск чисел: 1e-14 + 1e-10 × max(|a|,|b|); строки/статусы сравнивались точно.
При отключении txt-отчёта различается LastResidualNorm: в одном конечном НДС вместо
примерно 5,02e-7 (D300) либо 1,06e-4 (D1000) возвращается 0. По фактическому коду
CSectionSolver.AppendDiagnostics обновление этого поля стоит после проверки
mDiagnosticsEnabled. Само равновесие и сходимость проверяют другие значения;
в данных примерах остальных расхождений не было. Это недостаток диагностики,
зафиксированный отдельно; в рамках исследования производительности он не исправлялся.

Формирование и расчёт замерялись отдельно. В начале каждого цикла модель формировалась
заново. Прототип Memory использует только непосредственно полученную модель этой
фикстуры, без опасного повторного использования после изменения входов. Для рабочего
режима потребуется надёжная проверка актуальности; эти экспериментальные переключатели
нельзя переносить в рабочую книгу как готовую реализацию.

Варианты JSON сохраняют данные, но требуют нового читателя и утрачивают удобство
прямого просмотра/редактирования геометрических строк и использования их формулами.
Загрузка из AutoCAD, одновременная работа с тяжёлыми чужими книгами, сохранение файла
пользователем, все формы сечений и визуальное попиксельное сравнение здесь не измерялись.
Длительные полные ON/OFF прогоны не запускались. Неудачные прототипы и их журналы
сохранены как неудачные, общий PASS всем вариантам не присвоен.

## Рекомендация

Первый практический кандидат — схема по запросу и уменьшение повторного оформления
Results с сохранением численных данных. Именно сочетание этих действий дало примерно
1,8–3,6 раза для расчёта в двух основных примерах. Прототип с пропуском оформления
показывает верхнюю оценку такого выигрыша; сохранение прежнего внешнего вида через
готовый шаблон потребует отдельной реализации и проверки.

Больший выигрыш даёт отказ от записи всех подробностей после каждого расчёта, вплоть
до модели в памяти. Его цена явно показана в таблицах. Можно отдельно спроектировать
режим, где подробные данные и схема строятся по запросу; сохранность модели после
закрытия книги при этом должна быть отдельным обязательным решением.

Полный перенос вспомогательных таблиц в JSON по данным этих экспериментов для ускорения
не рекомендуется: даже точный компактный вариант замедлил чтение и полный цикл.
Укрупнение сетки и отключение проверок нельзя автоматически приравнивать к безопасной
оптимизации вывода.
