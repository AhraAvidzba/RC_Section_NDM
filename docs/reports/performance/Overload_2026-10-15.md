# Задержка при большой перегрузке — 15.10.2026

Задержка воспроизведена и устранена в общих классах поиска несущей способности.
Проверено круглое сечение Ø300 мм, 8Ø20, расстояние до оси арматуры 40 мм,
без дополнительных рядов, N = 500 тс, M = 100 тс·м. Нагрузка приложена
в центре бетонной сетки. Продолжение диаграмм включено, коэффициент наклона
плато 0,001. Допуски, материалы и бюджеты решателей не ослаблялись.

## Что занимало время

На сетке 10×10 мм (716 бетонных элементов) полный штатный расчёт занимал
19,30 с для Mx и 20,16 с для My. На сетке 50×50 мм (32 элемента) первоначальные
диагностические запуски дали 5,07 и 4,91 с. Увеличение числа элементов
увеличивает стоимость каждой оценки усилий, но причиной лишней работы
оказался порядок проверки начальной точки пути.

В режиме Auto сначала масштабируется момент при постоянной N = 500 тс,
затем N при постоянном M = 100 тс·м и лишь затем всё сочетание.
У первых двух путей уже при λ = 0 постоянная часть нагрузки превышает
физический предел деформаций. Однако UltimateStrain сначала выполнял
неудачные старты и только при резервном LoadMultiplier получал этот отказ.
В итоге до полезного последнего пути расходовались четыре дополнительных
старта. Всего — 192/190 итераций UltimateStrain; полезному пути достаточно 4.

Продолжение диаграмм позволяет найти прямое равновесие за физическими
пределами. Сам поиск физической предельной плоскости оценивает физические
диаграммы: включённое продолжение не устраняло эти лишние попытки автоматически.
По журналу Mx поиск несущей занимал примерно 17,2 с, прямое НДС — около
0,01 с; остальное время приходилось на подготовку, диагностику, Results и схему.

## Исправление и ограничения

CCapacityLimitSearchProblem перед UltimateStrain проверяет ненулевую
постоянную часть нагрузки существующим CCapacitySolver. Только найденное
равновесие с превышением деформаций даёт прежний rcInitialStateBeyondLimit.
Для этой проверки выполняется одна обычная попытка без серии удвоения ступеней.
Если равновесие не найдено численно, сохраняется прежний поиск UltimateStrain:
NumFail не становится доказательством физического отказа.

CLimitSearchCoordinator и CUltimateStrainSearch не повторяют уже подтверждённый
физический отказ другим численным методом. Порядок Auto и переход к следующему
пути сохранены. Нормальный путь, найденный при λ < 1, по-прежнему завершает
поиск. При нулевой постоянной нагрузке дополнительный НДС не требуется.
Изменены четыре общих класса; рецепты сечений, материальные законы,
формулы интегрирования, критерии приёмки и допуски не менялись.

Время измерено от штатного запуска до завершения записи Results, отчёта
и схемы. Повторы выполнялись последовательно, без параллельных расчётов.

| Случай, сетка 10 мм | До, с | После: три повтора, с | Медиана после, с |

Для всех повторов совпали статусы, λ, метод, выбранный путь и координаты

при пропорциональном увеличении всего сочетания.

## Отдельно 2×, 3×, 4× и бисекция

Нагрузки получены масштабированием подтверждённого предела по λ*NMxy
с сохранением отношения N:M пользовательского примера. Затем проверялся
штатный Auto, который вправе выбрать другой путь.

| Нагрузка от пропорционального предела | До, с | После, с | Статус до/после |
| --- | ---: | ---: | --- |
| 0,5× | 1,281 | 1,344 | OK / OK |
| 0,9× | 1,250 | 1,313 | OK / OK |
| 2× | 1,406 | 1,258 | FAIL / FAIL |
| 3× | 1,258 | 1,281 | FAIL / FAIL |
| 4× | 1,273 | 1,242 | FAIL / FAIL |

λ и предельные плоскости совпали точно. При явно выбранном LoadMultiplier
перегрузки 2×/3×/4× заняли 1,313/1,453/1,633 с. Каждый поиск выполнил
7 делений интервала [0;1] до ширины 0,0078125 при заданном допуске 0,01.
Дополнительного уточнения bracketFinalizationRecovery не было.
Слишком мелкая бисекция причиной задержки в этих проверках не являлась.

отсутствие выдуманного предела, реальная численная неудача начального НДС
