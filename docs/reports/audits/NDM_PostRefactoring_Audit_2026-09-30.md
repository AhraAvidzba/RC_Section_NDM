## 1. Подтвержденные технические проблемы

### T01. Secant может вернуть не найденный корень, а удаленную нижнюю границу

**Приоритет:** высокий.  
**Места:** `CLoadMultiplierSearch.SearchBySecant`, строки 14375–14444; `UpdateSecantBracket`, 14602–14610; `FinalizeAfterProbe`, 14447–14454; `CCapacitySolver.FinalizeLoadMultiplierSearch`, 12087–12103.

После вычисления `x2` и `f2` код обновляет границы. Если `f2 >= 0`, новая точка становится верхней границей. Затем при малой невязке `Abs(f2)` финализируется **`bracketLow`**, а не `x2`. Нижняя граница при этом может оставаться далеко от корня.

Аналогичная проблема есть в проверке `Abs(f1) <= tolerance` в начале итерации: финализируется не точка, для которой проверена невязка.

Контрольный пример:

```text
f(lambda) = lambda / 0.75 - 1
начальная скобка: [0; 1]

Secant находит:
x2 = 0.75
f2 = 0

UpdateSecantBracket:
bracketHigh = 0.75
bracketLow = 0

Финализация:
lambda = bracketLow = 0
```

`FinalizeLoadMultiplierSearch` устанавливает `mConverged = True`. В `CLimitSearchResult.InitializeFromCapacitySolver` проверка неуспеха по нагрузке записана как `LambdaUltimate > 0 And LambdaUltimate < 1`; при нуле она не выполняется, и состояние может получить `rsSuccess`.

**Требуемый результат исправления:** подтверждать критерий именно для возвращаемой точки. При остановке по невязке возвращать проверенную точку либо близкую допустимую границу с подтвержденной точностью. Не объявлять поиск сошедшимся только из-за того, что у другой точки была малая невязка.

**Тест:** линейная целевая функция с точным корнем внутри широкой скобки; отдельно проверить корень ниже 1 и равный нулю как настоящий физический исход, а не результат ошибки.

### T02. Bisection считает исчерпание итераций успешным завершением

**Приоритет:** высокий для ограниченного числа итераций.  
**Места:** `CLoadMultiplierSearch.SearchByBisectionCore`, 14234–14274; `SearchCrackByBisection`, 14180–14195; `CCrackWidthCalculator.LimitSearchFinalizeCrackFormationLoadMultiplier`, 18216–18234.

Внутри цикла:

```vb
If MaxIterations > 0 And Iterations >= MaxIterations Then Exit Do
```

После цикла без дополнительной проверки:

```vb
SearchByBisectionCore = True
```

Для CrackFormation положительный лимит итераций передается в этот метод. Верхняя граница затем принимается как найденная точка образования трещины. Финализатор проверяет сходимость равновесия solver-а, но не факт достижения требуемой точности поиска.

Контрольный пример:

```text
корень = 0.2
начальная скобка = [0; 1]
tolerance = 0.001
MaxIterations = 1

После одной итерации:
скобка = [0; 0.5]
ширина = 0.5 > tolerance
возвращаемая lambda_crc = 0.5
результат общего цикла = True
```

**Требуемый результат:** выход из-за лимита итераций отличать от достижения критерия. Допустимую приближенную границу возвращать только как явно обозначенный неполный результат, а не как точное `LIMIT_FOUND`.

### T03. Численная несходимость при lambda = 0 превращается в BaseFail

**Приоритет:** высокий.  
**Места:** `CLoadMultiplierSearch.RunCapacitySearch`, 13972–14002; `CCapacitySolver.LimitSearchEvaluateCapacityLoadMultiplier`, 11814–11845; `LimitSearchHandleCapacityInitialFailure`, 11850–11858; `CLimitSearchResult.InitializeFromCapacitySolver`, 13546–13577; `CResultStatusPolicy.ExternalStatus`, 740–770.

Цепочка:

1. При `lambda = 0` возвращен `NumericalFailure`.
2. `LimitSearchHandleCapacityInitialFailure` безусловно устанавливает `mInitialLambdaRejected = True`.
3. В `InitializeFromCapacitySolver` ветка `InitialLambdaRejected And Not InvalidInput` находится раньше проверки численной несходимости.
4. Формируется `rsCheckFailed + rcInitialStateBeyondLimit`.
5. Policy выводит `BaseFail`.

Получается физическое утверждение «базовая нагрузка уже не несется» там, где равновесие просто не удалось найти.

**Требуемый результат:** `BaseFail` выдавать только при подтвержденном физическом исходе. Неуспех численного решения не является доказательством превышения несущей способности.

**Тест:** физически допустимая постоянная N в моментной траектории и искусственно малый лимит итераций внутреннего решения. Ожидается численная ошибка, а не `BaseFail`.

**Дополнительная осторожность:** `FailedProbeReachedPhysicalLimit`, 12486–12499, распознает предел по деформациям несошедшейся итерации. Это эвристика, не равнозначная проверенному равновесному состоянию; ее нельзя незаметно использовать как достоверное доказательство для нового внешнего `BaseFail`.

### T04. Техническая граница поиска и неудачная скобка смешаны с физическим отсутствием трещины

**Приоритет:** высокий.  
**Места:** `CLoadMultiplierSearch.RunCrackFormationSearch`, 14040–14105; `FindCrackFormationBracket`, 14109–14176; `CCrackWidthCalculator.FinishNoCrack`, 19298–19309; `CCapacitySolver.LimitSearchHandleCapacityBracketNotFound`, 11861–11865.

В CrackFormation имеются два опасных случая:

- После достижения конечного `LimitSearchCrackBracketLimit` с отрицательной невязкой вызывается `FinishNoCrack`.
- После неудачных расчетов верхней точки `FindCrackFormationBracket` может присвоить верхней границе последнюю сходящуюся нижнюю точку и вернуть `True`. Верхняя невязка при этом остается отрицательной. Следующая ветка снова вызывает `FinishNoCrack`.

`FinishNoCrack` может назначить `rsSuccess + rcCriterionNotReached`. Однако ни конечный лимит lambda, ни неудача решения дальше по траектории не доказывают физическую недостижимость критерия.

Для Capacity исчерпание `MaxLambda` без найденной границы, наоборот, по умолчанию превращается в `STATE_NUMERICAL_FAILURE`.

Во всем экспорте `rcSearchBoundReached` найден только в объявлении enum и преобразовании имени кода, но не в формировании рабочего результата.

**Требуемый результат:** различать физическую недостижимость, техническую границу, исчерпание итераций и численную неудачу. Не превращать последний рассчитанный участок в утверждение обо всей траектории.

### T05. Успешный исход «трещины нет» ошибочно трактуется как найденная точка образования

**Приоритет:** высокий для соответствующего пути.  
**Места:** `CLoadMultiplierSearch.RunCrackFormationSearch`, 14040–14105; `CCrackWidthCalculator.FindGeneralFormationLambda`, 18056–18078; `CheckGeneralFormation`, 18011–18050; `EnsurePostCrackState`, 18601–18651; `FormationLoads`, 18686–18692.

`FindGeneralFormationLambda` возвращает только `searchResult.Succeeded`. Но успех Search может означать корректно установленное отсутствие трещины, а не наличие `lambda_crc`.

`CheckGeneralFormation` после этого проверяет только `mFormationPathFallbackPsi1`, затем вызывает `EnsurePostCrackState`. При отсутствии найденных усилий образования `FormationLoads` выбрасывает ошибку `vbObjectError + 3733`.

Пример ветки: фиксированный `LambdaN`, сжимающая N, ненулевой постоянный момент ниже трещинообразования; Search возвращает корректный исход отсутствия точки, но общий код пытается построить `PostCrackState`.

**Требуемый результат:** ветвиться по конкретному исходу и наличию найденной предельной точки, а не только по Boolean `Succeeded`. При отсутствии нормальной трещины не создавать фиктивные Pre/Post-state; независимую продольную проверку не блокировать.

### T06. Потребители не умеют работать с cache-hit без LastRunner

**Приоритет:** высокий для reuse-сценариев.  
**Места:** `CStateProvider.GetOrSolve`, 28329–28375; `CCrackWidthCalculator.BuildPreCrackState`, 18552–18596; `EnsurePostCrackState`, 18601–18651; `CBatchSectionCalculator.RunProfileState`, 23345–23410; `RunCrackWidth`, 23418–23524.

Provider при попадании в кэш возвращает готовый `CSectionStateResult`, а `LastRunner` остается `Nothing`. Это нормальный контракт: новый расчет не запускался.

Но:

- `BuildPreCrackState` требует solver из `LastRunner` и при его отсутствии создает ложный `NumericalFailure`.
- `EnsurePostCrackState` ведет себя аналогично, даже если `mPostCrackState.Converged = True`.
- `RunProfileState` возвращает `provider.LastRunner`, который при reuse равен `Nothing`.
- `RunCrackWidth` после проверки самого state обращается к `runner.ResultSolver` без проверки `runner`.

**Следствие:** корректно найденное и сохраненное НДС может давать ложный NumFail или ошибку обращения к отсутствующему объекту при попытке переиспользования.

**Требуемый результат:** downstream должен получать необходимые данные из конечного state либо через отдельный стабильный контракт доступа к оценке напряжений. Наличие готового НДС не должно требовать наличия runner последней попытки или нового solve.

### T07. Repository возвращает разные версии одного named state

**Приоритет:** высокий для повторных попыток.  
**Места:** `CStateRepository.StoreState`, 28512–28516; `StoreForRequest`, 28521–28530; `FindEquivalent`, 28534–28539; `FindState`, 28553–28563.

`StoreForRequest` сначала добавляет результат в `mStates`, затем проверяет его пригодность для reusable-словаря. `StoreState` отказывается принимать второй объект того же `StateType`.

Сценарий:

```text
Первая попытка:
  failed state записан в mStates
  reusable-словарь пуст

Вторая попытка:
  успешный state не заменяет failed state в mStates
  успешный state попадает в reusable-словарь

FindEquivalent -> success
FindState / StateAt -> прежний failure
```

Это рассогласование вывода, визуализации и расчетного reuse.

**Требуемый результат:** согласовать отображение текущего итогового named state и reusable-поиск. Историю неудачных попыток хранить отдельно либо обеспечить явное замещение и единую актуальную запись. Физический FAIL при найденном равновесии не следует путать с неуспешным solve.

**Пропущенный тест:** `TestStateRepositoryReusesOnlyConvergedStates`, 48207–48252, проверяет отказ и успех в двух разных repository. Он не проверяет замену failed → success в одном экземпляре.

### T08. Подробный блок трещин может показывать OK при ошибке образования трещины

**Приоритет:** высокий для достоверности вывода.  
**Места:** `CCrackSummaryWriter.PutCombination`, 30588–30614; `CrackOverallStatus`, 30991–30995; `CCombinationResult.CrackMeta`, 26967–26970.

Writer самостоятельно агрегирует только результаты ширины и продольных трещин. В него не включены formation и current state.

Контрольный сценарий:

```text
FormationResult = NumFail
CurrentCrackedState = OK
WidthResult = N/A (BlockedByDependency)
LongitudinalResult = OK

Подробный CrackOverallStatus = OK
```

В то же время `CCombinationResult.CrackMeta` учитывает Formation/Current/Width и видит ошибку. Поэтому подробный блок способен противоречить batch summary.

**Требуемый результат:** writer должен получать готовый итог именно своего блока, включая фактические причины блокировки обязательных зависимостей, а не выбирать собственный набор результатов для агрегирования.

## 2. Невыполненные архитектурные условия

### A01. Общий численный код появился, но общий Search все еще зависит от двух конкретных доменных монолитов

**Выполнено:** действительно существуют общие `SearchByBisectionCore` (14234–14274) и `RunUltimateNewtonCore` (17194–17234). Неверно утверждать, что сделана только новая маршрутизация.

**Не завершено:**

- `CLimitSearchRequest` хранит `CCapacitySolver` и `CCrackWidthCalculator`, а не независимый контракт критерия/оценки точки.
- `CLimitSearchCoordinator` содержит отдельные `ExecuteCapacity` и `ExecuteCrackFormation`, crack-specific порядок смены путей и доменную трактовку fallback.
- Brent/Secant жестко обращаются к `request.CapacitySolver`.
- Подготовка capacity-скобки и crack-скобки остается отдельными процедурами с разной обработкой исходов.

Отдельные адаптеры сами по себе допустимы. Проблема не в названии классов, а в том, что новая инженерная проверка потребует изменения общего Search и расширения request новыми конкретными calculator-ами.

**Где смотреть:** `CLimitSearchCoordinator` 12976–13242; `CLimitSearchRequest` 13250–13443; `CLoadMultiplierSearch` 13887–14629.

### A02. Capacity probes обходят общий state-solve pipeline

`CCapacitySolver.ProbeOnce`, 12315–12370, создает `New CSectionSolver`, самостоятельно настраивает его, старт и retries, вызывает обычный `solver.Solve`.

Это не специальная оценка заданной плоскости деформаций. Значит, исключение для `EvaluateStrainPlane` здесь неприменимо.

Настройки и схема перехода нагрузок разных стратегий могут отличаться как solve-options, но общий механизм реального решения и оформления результата должен быть один. Перенос нельзя выполнять путем простого изменения математического поведения: сначала описать и сохранить все необходимые параметры probes.

### A03. CrackFormation выделен главным образом оболочкой

`CCrackFormationCalculator`, 17365–17403, вызывает `crack.CheckFormationBeforeWidth` существующего `CCrackWidthCalculator` и упаковывает результат.

В `CCrackWidthCalculator` остались formation, управление Pre/Post-state, callbacks Search, геометрия расчетной зоны, выбор арматуры, напряжения и коэффициенты.

Чистая финальная формула действительно вынесена, как и продольная проверка. Но это не завершает согласованное разделение большого crack-класса. Не нужно создавать дополнительные пустые оболочки: нужно передать реальную ответственность в подходящие существующие или переименованные сущности.

### A04. CLimitSearchResult не является полностью самостоятельным общим результатом

**Места:** `CLimitSearchResult`, 13449–13713.

- Для Capacity result получает lambda, усилия и solver-снимок.
- `CaptureCrackSnapshot` записывает только флаги/причину/диагностику; общие численные поля limit-точки остаются сброшенными.
- Result сохраняет ссылку на `CCrackWidthCalculator`, а `DiagnosticLog` читает его текущее изменяемое состояние.
- В `InitializeFromCapacitySolver` уже выполняется инженерская проверка `lambda < 1`, вместо разделения успешности поиска и результата проверки сочетания.

Нужен самостоятельный снимок найденной точки/исхода с одинаковым общим контрактом. Инженерная трактовка должна выполняться выше.

### A05. Writer-ы еще содержат инженерскую логику

Примеры:

| Класс | Остаточная ответственность | Строки |
|---|---|---|
| `CCrackSummaryWriter` | Собственная агрегация общего статуса Crack | 30991–30995 |
| `CCrackSummaryWriter` | Расчет запасов как `1 / Utilization` | 30836–30846 |
| `CStrengthSummaryWriter` | Расчет минимального запаса по предельным деформациям | 38844–38867 |
| `CStabilitySummaryWriter` | Выбор `OK/FAIL/N/A` по применимости и прохождению проверки | 38069–38079 |

Даже если формула короткая, это противоречит принятому контракту пассивного writer-а. Эти значения и решения должны приходить подготовленными.

### A06. Централизация статусов и комментариев неполная

- `StatusPriority` отдельно реализован в `CResultStatusPolicy` (872–889) и в `CCombinationResult` (27090–27107). Изменение приоритета в одном месте не гарантирует согласованной агрегации.
- `CCapacitySolver.ClassifyNumericalFailure` (12565–12576) продолжает распознавать точную численную причину по подстрокам свободного `StopReason`.
- `MarkFormationPathFallback` (19317–19324) для трещины в постоянной части ставит `rcCheckPassed`, а не согласованный `rcInitialStateBeyondLimit`.
- `AppendMetaComment` (27179–27192) фильтрует комментарии по внешнему проблемному статусу. `rsSuccessWithWarning` отображается как OK, поэтому предупреждение исключается из составного комментария.

Имеются правильные enum и единый словарь отображения, но этого недостаточно для полного выполнения требования.

## 4. Почему зеленых тестов пока недостаточно для приемки

В progress-файле, строки 213–217, заявлены успешная сборка и полный Run-AllTests без ошибок:
UI 308/0, Batch 644/0, Regression baseline 39/0.

Эти результаты здесь не повторялись. Кроме того, тесты могут не охватывать дефектные ветви.

Примеры ограничения имеющихся тестов:

1. `TestStateRepositoryReusesOnlyConvergedStates` проверяет failed и successful состояния в разных repository, а не последовательность двух попыток в одном.
2. `RunBaselineCase` в `modTestRegressionBaseline` (53472–53510) проверяет сходимость и равновесие и печатает baseline. Сам этот метод не сравнивает все новые результаты с сохраненным Git-baseline. Такое сравнение может быть во внешних скриптах, но из этого VBA-экспорта оно не подтверждается.
3. Объявление `rcSearchBoundReached` не означает наличия рабочего пути, формирующего такой исход.
4. Сохранение хороших результатов стандартных сценариев не проверяет корректность cache-hit, неудачной скобки и неверной агрегации подробного блока.

Не нужно менять ожидаемые тестовые значения, чтобы они повторяли найденные ошибки. Сначала определить требуемый контракт и добавить тест, воспроизводящий дефект.

## 5. Обязательные проверки перед окончательной приемкой

| Проверка | Ожидаемый результат |
|---|---|
| Secant точно попадает в корень внутри широкой скобки | Возвращена проверенная точка, а не удаленная нижняя граница |
| Bisection исчерпал MaxIterations до нужной точности | Не объявляется точный успешно найденный предел |
| Допустимая базовая нагрузка + намеренная численная несходимость при lambda=0 | NumFail, не BaseFail |
| Физически подтвержденное превышение предела при lambda=0 | Capacity BaseFail |
| Критерий не достигнут к MaxLambda при корректных расчетах | SEARCH_BOUND_REACHED, не доказательство физического отсутствия |
| Верхняя crack-точка не сходится | Нет фиктивного утверждения о физическом отсутствии трещины |
| Фиксированный LambdaN со сжатием и моментом ниже трещинообразования | Корректная ветка без запроса несуществующего PostCrackState |
| Успешный PostCrackState уже в repository, новый runner не создается | Нет ложного NumFail и нет дополнительного solve |
| CurrentCrackedState получен из кэша | Width и longitudinal работают без runner.ResultSolver на Nothing |
| Failed → success в одном repository | FindEquivalent, FindState, StateAt и вывод согласованы |
| Formation NumFail, current state OK, longitudinal OK | Общий статус подробного Crack-блока не OK |
| Успешный fallback с предупреждением | Важный ResultComment не теряется при агрегации |
| Новая тестовая цель поиска через общий контракт | Не требуется отдельная копия Search и новый конкретный calculator в общем request |

После этих проверок повторить общий набор тестов, сравнить результаты и фактическое число запусков solver-а с baseline, проверить соответствие Results/Summary и экспорт/визуализацию.

## 6. Рекомендация по дальнейшим действиям

Не возвращаться к многократной редактуре migration plan и не начинать рефакторинг заново.

1. Исправить подтвержденные технические дефекты и добавить регрессии.
2. Завершить уже согласованные границы общего state-solve, Search и доменных калькуляторов.
3. Перенести оставшиеся статусы/запасы из writer-ов и устранить дублирующие источники результата.
4. Повторно проверить реализацию и обновить progress-отчет по фактическим критериям, а не по наличию новых классов.

**Критерий завершения:** корректные конечные результаты и статусы, действительно переиспользуемые states, общая численная инфраструктура без дублирования обычного solve и пассивный вывод. Само наличие классов с согласованными именами не является достаточным доказательством выполнения плана.
