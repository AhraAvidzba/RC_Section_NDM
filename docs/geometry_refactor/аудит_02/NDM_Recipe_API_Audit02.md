# NDM. Аудит 02: конкретное упрощение рецептов и единый API

**Версия:** 1.0, 14.10.2026.  
**Расположение:** `docs/geometry_refactor/аудит_02/NDM_Recipe_API_Audit02.md`.  
**Исполнитель:** Codex, реализация согласованной цели по этапам.  
**Предмет:** сократить техническую рутину в рецептах без потери возможностей, изменения инженерного поведения и появления нескольких конкурирующих API.

> Это подробное задание на следующий этап, а не повтор первоначального крупного рефакторинга. Главное конкретное изменение: вместо трёх параллельных массивов точек, радиусов и имён ввести один удобный общий описатель вершин и перевести на него все применимые рецепты. Остальные изменения должны поддерживать эту же цель, а не создавать второй конструктор.

## 0. Как применять документ к текущей ветке

Внешнему проверяющему доступен экспорт `VBA_All_Code(20261012-212248).txt`. В рабочем репозитории Codex код может быть новее. Ниже разделены:

- **Наблюдения по доступному экспорту:** исходная мотивация, а не утверждение о состоянии HEAD.
- **Предлагаемый целевой контракт:** конкретная конструкция, которую требуется реализовать или сопоставить с уже существующим эквивалентом.
- **Ограничения пользователя:** обязательны независимо от имён существующих классов.

Сначала прочитай фактические исходники, собственный аудит и его отчёт, действующее ТЗ, AGENTS и последние решения пользователя. Сопоставь требования с актуальным кодом. Не возвращай удалённые компоненты только потому, что они упомянуты в примерах старой версии.

Названия новых вспомогательных методов ниже являются рабочими. Допускается использовать уже существующие эквиваленты или предложить более удачное имя, но результат должен быть одним каноническим API. Зафиксируй соответствие в `API_MAP.md`; обнови все примеры и потребителей, а не оставляй две версии интерфейса. Существенное изменение поведения, расширение объёма или противоречие явному решению пользователя сначала согласуй.

Примеры с новым `CPolygonSpec`, новыми помощниками options и политикой имён показывают **целевой код после реализации**. Они не выдаются за уже существующий или выполненный VBA. Codex должен превратить их в компилируемые проверенные примеры фактического API.

## 1. Что именно обсуждено и должно получиться

### 1.1. Оставить один архитектурный маршрут

```text
Config / программные исходные значения
    -> снимок ввода и нормализация в единственном классе-рецепте
    -> описание исходных геометрических данных
    -> CSectionDefinitionBuilder
    -> зарегистрированные пути + роли Outer/Opening + правила + аннотации
    -> Finish
    -> CSectionDefinition
    -> общий CSectionBuilder и существующие исполнители
    -> CSectionModel + данные визуализации
```

Один новый тип сечения требует одного короткого класса-рецепта и одной регистрации. Его формат ввода может отличаться от других типов. Дополнительный специализированный Reader, GeometryBuilder, RebarBuilder или AnnotationBuilder на каждый тип не допускается.

### 1.2. Упростить данные, а не создать второй язык

Разные операции необходимы: окружность не равна многоугольнику, независимое армирование не равно проекции, наклонный размер не равен горизонтальной проекции. Эти возможности сохранить.

Но для одинакового действия должен быть один способ использования. Например, описание скруглённого многоугольника во всех штатных рецептах должно передаваться через один формат, а не в одном классе через объект, в другом через три массива, в третьем через произвольный Dictionary.

**Не добавлять:**

- `OuterPolygon`, `BuildRoundedSection`, `BuildEverything` и аналогичные составные публичные команды, дублирующие обычную последовательность создания пути и назначения роли;
- отдельный «короткий API» рядом со «старым API»;
- Offset для `PathGroup`;
- Custom, его таблицы и именованные диапазоны;
- новый интерпретатор формул/DSL на листе Config;
- расчётные ломаные вместо аналитических дуг;
- новую геометрическую математику ради изменения формы вызова.

### 1.3. Что считается реальным сокращением

Удаляется обслуживание массивов, повторяющиеся проверки, вычисление одинаковых настроек дополнительных рядов, формирование технических ID и диагностических строк. Не удаляются содержательные условия, объясняющие форму и армирование.

Условия `Simple/Tapered`, независимость сторон, включение носа в боковой путь, направления обхода, отличия дополнительных рядов и значения концевых режимов остаются понятными из рецепта.

Не считать улучшением объединение десяти инструкций через `:` или перенос кода в новый класс с названием конкретного сечения.

## 2. Конкретная исходная рутина

В доступном экспорте `CSectionRecipeRoundedRectangle.AddGeometry`:

1. Создаёт `points(0 To 5)`, `radii(0 To 5)`, `names(0 To 5)`.
2. Ведёт `count` и вызывает собственный `AddCorner`.
3. Создаёт ещё `vertices`, `assignedRadii`, `vertexIDs` фактической длины.
4. Копирует заполненную часть трёх массивов.
5. Сохраняет массивы в `sizes` для повторного использования при offset.
6. Передаёт три массива в `facade.RoundedPolygon` и позднее в `OffsetRoundedPolygon`.
7. Сам перебирает сегменты для формирования `CONTOUR_LINE_i` / `CONTOUR_ARC_i`.

В `AddReinforcement` и подобных методах других рецептов повторяются настройка политики публикации, совпадений, групп, подготовка зависимых рядов, суммы радиусов, проверки длин и привязки к источнику.

Это ориентиры для поиска. Актуальность каждого блока проверь в HEAD. Таблица исходных мест приведена в разделе 18.

## 3. A02-01. Общий описатель вершин `CPolygonSpec`

### 3.1. Назначение и данные

Ввести **один общий класс описания исходного многоугольника**, предварительное имя `CPolygonSpec`. Если равнозначный компонент уже существует, использовать его.

Одна запись объединяет:

| Поле | Смысл |
|---|---|
| `VertexID` | Смысловое имя исходной вершины, например `TR`, `RightNose` |
| `X`, `Y` | Координаты исходной вершины во внутренних единицах |
| `FilletRadius` | Назначенный радиус сопряжения в этой вершине; ноль означает отсутствие скругления |
| `SourceReference` | Необязательное текстовое происхождение исходных данных; без ссылки на Excel |

Это описание **исходных вершин до скругления**, а не готовых точек касания, не список арматурных стержней и не каталог аннотационных привязок.

Не создавать класс на каждую точку. Внутри допустим один закрытый массив записей или иной компактный контейнер. Индексы, ёмкость, рост массива и согласованность полей скрываются от рецептов.

### 3.2. Минимальный внешний контракт

| Член | Предлагаемый контракт |
|---|---|
| Создание | `Set polygon = New CPolygonSpec` |
| Добавление | `AddVertex(vertexID, x, y, Optional filletRadius = 0, Optional sourceReference = "")` |
| Завершение ввода | `Seal()` |
| Чтение состояния | `IsSealed`, `Count` |

Не добавлять равноправные синонимы `AddPoint`, `AppendCorner`, `Point`, `Vertex` для той же операции. Для исходной вершины используется `AddVertex`.

Внутренние геометрические алгоритмы могут получать данные через `Friend`-метод копирования или чтения, например `CopyKernelData`. Он не становится обычным интерфейсом автора рецепта.

### 3.3. Жизненный цикл и проверки

```text
New -> AddVertex ... -> Seal -> использование фасадом
```

Выбран явный `Seal`: это одна понятная строка, а не скрытая смена состояния при случайном чтении.

`AddVertex` проверяет непустой уникальный ID, представимость чисел, допустимость радиуса и состояние объекта. Не менять принятую политику регистра идентификаторов. Геометрические допуски не размножать.

`Seal` проверяет полноту структуры и минимальное число вершин для многоугольника. Порядок сохраняется буквально. Не сортировать вершины по углу, координате или имени. Первую вершину в конце повторно не добавлять: замыкание является частью операции построения многоугольника.

После `Seal` добавление и изменение запрещены. Повторный `Seal` может быть безопасным бездействием; поведение документировать и проверить.

**Не переносить в описатель:** вычисление касаний, скругление, offset, пересечения, проверку сложной топологии, сборку бетона, арматуру, аннотации. Эти операции остаются в соответствующем существующем геометрическом владельце. Простая проверка структуры не заменяет геометрическую валидацию.

### 3.4. Владение и повторное использование

Описатель не знает `CSectionDefinitionBuilder`, `CSectionDefinition`, Workbook, Range, solver или стандарт СП. В нём нет `ApplyToFacade`, самостоятельной регистрации либо обратной ссылки на фасад.

Один sealed-описатель можно использовать для построения исходного пути и нескольких эквидистантных путей. Фасад/геометрический алгоритм не должен изменять его при offset.

В готовом пути не хранить ссылку на mutable-исходники. Если сохраняется ссылка на sealed-описатель ради происхождения, её read-only контракт должен быть реальным; иначе хранить необходимые значения. Не копировать большие данные без необходимости.

Для другого набора размеров создаётся новый описатель. Не вводить глобальный кэш, keyed только по `as`, или изменяемый singleton.

### 3.5. Не смешивать три вида точек

| Сущность | Пример | Где живёт |
|---|---|---|
| Исходная вершина | `TR = (B/2, H/2)` | `CPolygonSpec` |
| Точка готового сегмента | Начало/конец `Edge.TR`, точка дуги по параметру | Подготовленный `CGeometryPath` |
| Именованная привязка аннотации | `Slope.A`, `Slope.B` | Определение через `Anchor` / `PathAnchor` |

При скруглении исходная вершина обычно не лежит на фактическом контуре. Поэтому размер до `TR` и размер до точки касания являются разными задачами.

**Не регистрировать все вершины автоматически как anchors с теми же ID.** Это создаёт скрытые сущности и опасное смешение исходной и фактической геометрии. Использовать явный `Anchor` для заданной координаты и `PathAnchor` для фактической точки пути.

## 4. A02-02. Один формат аргументов геометрического фасада

### 4.1. Меняем существующие операции, а не добавляем синонимы

Целевые сигнатуры фасада:

```vb
' Контракт будущей реализации, не готовое тело функции.
' Public Function RoundedPolygon( _
'     ByVal pathID As String, _
'     ByVal polygon As CPolygonSpec) As CGeometryPath
'
' Public Function OffsetRoundedPolygon( _
'     ByVal pathID As String, _
'     ByVal polygon As CPolygonSpec, _
'     ByVal distance As Double) As CGeometryPath
```

Фасад принимает sealed-описатель, вызывает действующую математику, регистрирует подготовленный путь ровно один раз и возвращает его.

Сигнатуры с `vertices, radii, vertexIDs` после миграции исчезают из API автора рецептов. **Не делать** `RoundedPolygonV2`, `RoundedPolygonFromSpec`, `RoundedPolygonEx` или Variant-аргумент, который распознаёт несколько несовместимых форм входа.

Во внутреннем численном алгоритме три массива могут временно или постоянно оставаться оптимальным представлением. Это не второй публичный API. Преобразование из описателя реализуется в одном общем месте, а не в каждом рецепте и не отдельно в каждом тестовом helper.

### 4.2. Что не меняется

`CirclePath`, `LinePath`, `ArcPath`, `RectanglePath`, `AdjacentRectangles`, `Chain`, `Offset`, `Transform`, `ConstrainLine`, `Outer`, `Opening`, `PathGroup` сохраняют самостоятельный геометрический смысл и единый контракт регистрации.

Не заставлять круг описываться четырьмя вершинами только ради внешнего сходства вызовов. Не превращать прямоугольную сборку в универсальный CAD Union. Не переводить `RectSet` на другую математику объединения без необходимости.

### 4.3. Путь, роль и регистрация

Каноническая последовательность остаётся явной:

```vb
Private Function DescribeConcrete( _
    ByVal facade As CSectionDefinitionBuilder, _
    ByVal polygon As CPolygonSpec) As CGeometryPath

    Dim boundary As CGeometryPath
    Set boundary = facade.RoundedPolygon("Boundary", polygon)

    facade.Outer "OUTER", boundary.ID

    Set DescribeConcrete = boundary
End Function
```

В примере `facade` уже инициализирован вызывающим рецептом, `polygon` уже sealed. `RoundedPolygon` создаёт и регистрирует путь. `Outer` назначает ему роль, не повторяя построение.

`AddPath` сохраняется как **граница регистрации внешнего уже подготовленного пути**, если такая возможность реально нужна. После `facade.RoundedPolygon`, `LinePath`, `Chain` и других создающих методов `AddPath` не вызывается. Повторный ID должен давать понятную ошибку, а не автоматически создавать второй объект.

### 4.4. Offset не унифицировать ценой неверной математики

Сохранить различие:

- `Offset`: смещение подготовленного пути по действующему signed-left контракту.
- `OffsetRoundedPolygon`: построение смещённого скруглённого многоугольника из исходного описания, с принятой обработкой исчезающих сегментов.

Это разные входные постановки, а не два стиля выполнения одного действия. Не подменять вторую первой из-за похожего имени. Не обещать универсальное смещение любой самопересекающейся фигуры.

Сохранить аналитические дуги, их центры/радиусы/углы, правила сопряжений, направление обхода и F02-привязки к исчезнувшим сегментам. Для обычного offset дуги проверить принятую формулу изменения радиуса; исчезновение дуги не исправлять фиктивной прямой или молчаливым уменьшением `as`.

**Offset группы независимых путей не реализовывать.**

## 5. Полный пример новой подготовки вершин остроносого сечения

Ниже конкретная замена ручных массивов в одном классе-рецепте. Скалярная структура показана вместе с методом, поэтому `sizes` не является необъяснённой переменной.

```vb
' Внутри CSectionRecipeRoundedRectangle.
Private Type TRoundedInput
    B As Double
    H As Double
    SideTypes(1 To 2) As String
    Widths(1 To 2) As Double
    R1(1 To 2) As Double
    R2(1 To 2) As Double
    MainHeader As Long
    ExtraHeader As Long
    GeometrySource As String
End Type

Private Function DescribePolygon( _
    ByRef sizes As TRoundedInput) As CPolygonSpec

    Dim polygon As CPolygonSpec
    Set polygon = New CPolygonSpec

    polygon.AddVertex "TL", _
        -sizes.B / 2#, sizes.H / 2#, sizes.R1(1), _
        sizes.GeometrySource

    polygon.AddVertex "TR", _
        sizes.B / 2#, sizes.H / 2#, sizes.R1(2), _
        sizes.GeometrySource

    If sizes.SideTypes(2) = "Tapered" Then
        polygon.AddVertex "RightNose", _
            sizes.B / 2# + sizes.Widths(2), 0#, sizes.R2(2), _
            sizes.GeometrySource
    End If

    polygon.AddVertex "BR", _
        sizes.B / 2#, -sizes.H / 2#, sizes.R1(2), _
        sizes.GeometrySource

    polygon.AddVertex "BL", _
        -sizes.B / 2#, -sizes.H / 2#, sizes.R1(1), _
        sizes.GeometrySource

    If sizes.SideTypes(1) = "Tapered" Then
        polygon.AddVertex "LeftNose", _
            -sizes.B / 2# - sizes.Widths(1), 0#, sizes.R2(1), _
            sizes.GeometrySource
    End If

    polygon.Seal
    Set DescribePolygon = polygon
End Function
```

`ReadDimensions` по-прежнему заполняет размеры и данные диагностики. Массивы `vertices/radii/vertexIDs` из `TRoundedInput` удаляются. `CPolygonSpec` передаётся отдельной объектной переменной между приватными методами рецепта; не требуется создавать ещё один класс исходных данных формы.

В рецепте больше нет `points(0 To 5)`, временных массивов фактической длины, `count`, собственного `AddCorner` и копирующего цикла. Ограничение «не больше шести вершин» относится к данной форме, но не зашивается в общий описатель.

Если уже существующая адресная диагностика более точная, чем `GeometrySource` целиком, сохранить её: каждая вершина должна получать подходящие источники координат и радиуса. Не терять детальность ошибки ради сокращения примера.

### 5.1. Как меняется главный метод рецепта

После внедрения описателя последовательность должна читаться так:

```text
Получить table и units из context
ReadDimensions -> sizes
DescribePolygon(sizes) -> polygon
создать и Initialize facade
AddGeometry(facade, sizes, polygon) -> outer
AddReinforcement(facade, table, units, sizes, polygon)
AddDimensions(facade, sizes, outer)
Finish -> definition
```

Это план изменения действующих приватных методов, не отдельный новый маршрут. `polygon` объявляется как `CPolygonSpec` и создаётся один раз на вызов рецепта.

### 5.2. Полный пример выделения осевой траектории

```vb
Private Function AxisPath( _
    ByVal facade As CSectionDefinitionBuilder, _
    ByVal polygon As CPolygonSpec, _
    ByVal groupID As String, _
    ByVal axisDistance As Double, _
    ByVal sourceReference As String) As CGeometryPath

    On Error GoTo InvalidPath

    Dim offsetPath As CGeometryPath
    Set offsetPath = facade.OffsetRoundedPolygon( _
        "Offset." & groupID, polygon, axisDistance)

    Select Case groupID
        Case "B.Top"
            Set AxisPath = facade.Chain( _
                groupID, offsetPath.ID, _
                "Edge.TL", 0#, "Edge.TL", 1#)

        Case "B.Bottom"
            Set AxisPath = facade.Chain( _
                groupID, offsetPath.ID, _
                "Edge.BR", 1#, "Edge.BR", 0#, False)

        Case "H.Left"
            Set AxisPath = facade.Chain( _
                groupID, offsetPath.ID, _
                "Edge.TL", 0#, "Edge.BR", 1#, False)

        Case "H.Right"
            Set AxisPath = facade.Chain( _
                groupID, offsetPath.ID, _
                "Edge.TL", 1#, "Edge.BR", 0#)

        Case Else
            SectionRecipeError "CSectionRecipeRoundedRectangle", _
                "Неизвестный путь армирования: " & groupID, _
                sourceReference
    End Select

    Exit Function

InvalidPath:
    SectionRecipeGeometryError _
        "CSectionRecipeRoundedRectangle", sourceReference
End Function
```

Это эскиз целевого метода на основе доступной версии. Если текущая ветка имеет улучшенные селекторы/F02-привязки, сохранить их, изменив передачу исходных данных, а не откатывать к старому фрагменту. Не менять машину ошибок только ради точного повторения этого примера.

Отдельный `offsetPath` каждого активного пути допустим. Устранение повторных математических подготовок при одинаковом `as` не является обязательной задачей этого этапа: сначала сохранить поведение и измерить, есть ли проблема. Не вводить общий mutable-кэш и не менять пользовательские ID путей.

## 6. A02-03. Технические идентификаторы контуров

В рецепте должны оставаться смысловые ID (`TL`, `TR`, `RightNose`, `H.Right`), но не циклы вида «для каждого сегмента проверить sweep и склеить служебный CONTOUR_LINE_i».

### 6.1. Конкретный предлагаемый механизм

Добавить в существующий контракт `Outer` / `Opening` **одну явную политику публикации имён**, если аналог ещё отсутствует. Например, дополнительный необязательный аргумент `namingPolicy` со значениями:

- `PreserveSegmentIDs`: прежнее поведение без явного массива ID;
- `SequentialByKind`: получить `CONTOUR_LINE_i` / `CONTOUR_ARC_i` по существующему порядку;
- явные внешние ID: сохраняются там, где они реально нужны для импорта/происхождения, с действующей проверкой.

Имена enum рабочие. Проверить другие действующие семейства и их префиксы; описание префикса/пространства имён должно быть данными, не `Select Case` по типу сечения. Не присваивать всем контурам одинаковые ID, если область имеет несколько Outer/Opening.

Предложение применения:

```vb
Private Sub PublishRoundedOuter( _
    ByVal facade As CSectionDefinitionBuilder, _
    ByVal boundary As CGeometryPath)

    facade.Outer loopID:="OUTER", pathID:=boundary.ID, _
        comment:="Прямой участок контура скругленного прямоугольника.", _
        arcComment:="Дуга контура скругленного прямоугольника.", _
        namingPolicy:=SequentialByKind
End Sub
```

`namingPolicy` здесь новый предлагаемый параметр. Реализация формирования ID находится у владельца публикации контуров; фасад лишь передаёт политику.

### 6.2. Сохранение поведения

Проверить точное совпадение ID, порядка, комментариев, LoopID/Role и координат относительно актуального baseline. Не вводить раздельную нумерацию прямых и дуг, если прежде использовался общий номер сегмента.

Сочетание явного массива ID и несовместимой политики должно быть ошибкой, а не скрытым приоритетом одного из параметров.

Не удалять `Chain` для выбора начала опубликованного контура: эта операция задаёт порядок обхода. Она не является лишней только потому, что исходный путь тоже замкнут.

## 7. A02-04. Общая подготовка правил армирования без второго API

### 7.1. Выбранный вариант

Для этого этапа **не вводить отдельную конкурирующую команду `RebarRows`/`BuildReinforcement` рядом с существующими методами**. Не создавать обязательный новый язык всех правил ради сокращения двух дополнительных рядов.

Обсуждавшийся общий описатель армирования реализовать прежде всего за счёт развития уже существующего `CRebarRuleOptions` и небольших общих операций подготовки его данных. Это более экономная конкретизация идеи, не требующая нового класса на каждый ряд.

Канонические команды регистрации остаются:

- `RebarByCount`, `RebarByMaxStep`, `RebarByFixedStep`, `RebarAtStations` для разных независимых распределений;
- `RebarDependent` для зависимого смещения;
- `RebarProjected` для проекции.

Все команды по-прежнему формируют один формат правил и используют одного исполнителя. Разные способы распределения не являются дублированием архитектуры.

### 7.2. Помощник для общих политик

Предлагаемое расширение `CRebarRuleOptions`:

```vb
' Контракт, не тело реализации.
' Public Sub SetPublication( _
'     ByVal annotationGroup As String, _
'     ByVal publication As ERebarPublication, _
'     ByVal coincidence As ERebarCoincidence)
```

Он заполняет строго три соответствующих поля. Не включает скрыто `PerPath`, `ExcludeBoth`, `FromPathMiddle`, `CheckCenter` или поведение проекций.

Если современная версия уже имеет аналогичную фабрику/конструктор options, использовать её вместо добавления синонима. Прямой доступ к отдельным настройкам не является вторым маршрутом сборки: это один объект параметров с одним способом регистрации правила.

### 7.3. Помощник для контактного зависимого ряда

Предлагаемая сигнатура в том же классе:

```vb
' Общий enum разместить в существующем модуле типов, если эквивалента ещё нет.
Public Enum ERebarOffsetAxis
    RowNormal = 1
    RowTangent = 2
End Enum
```

```vb
' Контракт метода CRebarRuleOptions, не исполняемая заготовка.
' Public Sub ConfigureDependentContact( _
'     ByVal baseDiameter As Double, _
'     ByVal diameter As Double, _
'     ByVal axis As ERebarOffsetAxis, _
'     ByVal directionSign As Double, _
'     ByVal everySecond As Boolean, _
'     Optional ByVal interveningDiameterSum As Double = 0#)
```

Он вычисляет только расстояние между осями по принятому контактному расположению:

```text
distance = baseDiameter / 2 + interveningDiameterSum + diameter / 2
```

Далее задаёт `NormalOffset` либо `TangentOffset` со знаком `directionSign`, второй компонент обнуляет, устанавливает `everySecond`. Проверяет диаметры, сумму и направление. Он **не знает координат стержней, пути, нормали в конкретной точке, типа сечения и Config**.

Поля публикации, совпадений, проверки положения, выбора касательной, источника и политики проекции этот метод не меняет. Они передаются отдельно и явно. В частности, `SuccessfulProjectionOrdinal` нельзя случайно заменить обычной нумерацией пути.

Если действующий общий слой уже содержит этот расчёт расстояния, вызвать его, а не завести вторую формулу.

`interveningDiameterSum` означает сумму диаметров номинально расположенных между основным и данным стержнем элементов. Для существующего третьего ряда это `d2` только при предусмотренном одинаковом направлении размещения, иначе ноль. Сохранить действующую логику: отсутствие конкретного второго стержня из-за `EverySecondBar` не должно автоматически уменьшать предусмотренное расстояние третьего ряда, если baseline этого не делает.

Зависимое расположение с произвольными `NormalOffset` и `TangentOffset` остаётся возможно через те же options и `RebarDependent`. «Контактное размещение» и «явные межцентровые смещения» имеют разный смысл исходных данных, но один механизм регистрации и исполнения.

### 7.4. Полный пример описания ряда с дополнительным стержнем

```vb
Private Sub DescribeRightReinforcement( _
    ByVal facade As CSectionDefinitionBuilder, _
    ByVal axisPath As CGeometryPath, _
    ByVal count As Long, _
    ByVal diameter As Double, _
    ByVal extraDiameter As Double, _
    ByVal startSetback As Double, _
    ByVal endSetback As Double, _
    ByVal sourceReference As String)

    Dim mainOptions As CRebarRuleOptions
    Dim extraOptions As CRebarRuleOptions

    Set mainOptions = New CRebarRuleOptions
    mainOptions.SetPublication _
        "H.Right", PublishPerSourcePosition, KeepPublishedOwner
    mainOptions.EndMode = ExcludeBoth
    mainOptions.StartSetback = startSetback
    mainOptions.EndSetback = endSetback
    mainOptions.IncomingTangentAtJoint = True
    mainOptions.SourceReference = sourceReference
    mainOptions.Comment = "Правая боковая группа, основной ряд"

    facade.RebarByCount _
        "H.Right.Main", axisPath.ID, count, diameter, mainOptions

    If extraDiameter > 0# And count > 0 And diameter > 0# Then
        Set extraOptions = New CRebarRuleOptions
        extraOptions.SetPublication _
            "H.Right", PublishPerSourcePosition, KeepPublishedOwner

        extraOptions.ConfigureDependentContact _
            baseDiameter:=diameter, diameter:=extraDiameter, _
            axis:=RowNormal, directionSign:=-1#, everySecond:=False

        extraOptions.SourceReference = sourceReference
        extraOptions.Comment = "Правая боковая группа, дополнительный ряд"

        facade.RebarDependent _
            "H.Right.Row2", "H.Right.Main", extraDiameter, extraOptions
    End If
End Sub
```

Пример иллюстрирует именно подготовку options; выбор `RowNormal` и `-1` относится к принятой ориентации правой боковой цепочки. В других рецептах знак явно выбирается по их реальным направлениям, а не копируется автоматически.

**Не наследовать все настройки основного ряда через неограниченный Clone:** его StartSetback, EndSetback, EndMode, исходная касательная и параметры проекции не обязаны быть параметрами зависимого ряда. Новый options для зависимого правила должен получать только требуемые значения.

### 7.5. Что удалить после переноса

Общие части локальных `AdditionalOptions` / `ExtraOptions`, вычисление одинаковых межцентровых расстояний и повторную настройку общих политик перевести на одни помощники.

Если приватный метод после этого только пересылает те же аргументы, удалить. Если он ещё интерпретирует конкретный формат Config или важное направление данной грани, оставить эту содержательную часть в рецепте.

Не заменять один длинный приватный метод десятью почти пустыми специализированными обёртками. Не добавлять отдельные `CRebarRuleOptionsForRoundedRectangle` и аналоги.

## 8. A02-05. Короткое чтение ввода и адресная диагностика

Расширить существующий `CSectionInputTable`, если аналоги ещё отсутствуют:

```vb
' Предлагаемые контракты:
' PositiveLength(row, column, units) As Double
' NonNegativeLength(row, column, units) As Double
```

Оба используют существующий `Length` и тот же механизм ошибки с адресом. Первый проверяет `> 0`, второй `>= 0`. Не реализуют второй раз чтение чисел или преобразование единиц.

Применение в рецепте:

```vb
Private Sub ReadBaseDimensions( _
    ByVal table As CSectionInputTable, _
    ByVal units As CUnitSystem, _
    ByRef width As Double, _
    ByRef height As Double)

    Dim valueRow As Long
    valueRow = table.RowByKey("B", 2) + 1

    width = table.PositiveLength(valueRow, 2, units)
    height = table.PositiveLength(valueRow, 3, units)
End Sub
```

Не подменять ограничения, отличающиеся от нуля. Например, проверка `W > GEOM_TOLERANCE` не всегда равна `W > 0`; оставить явную проверку или использовать существующий общий вариант ограничения с той же границей.

Составные условия `as > d/2`, совместимость прямоугольников и выбор активных полей по типу стороны остаются в рецепте либо передаются общему валидатору как конкретные условия с адресами. Общий reader не должен знать имена сечений.

Поиск строк и столбцов, не зависящий от текущей итерации, выполнить один раз на чтение блока. Не терять проверку неоднозначных заголовков. Сохранить смысл пустоты/нуля для выключения рядов и отказ на недопустимом тексте.

**Неактивные W/R2, выключенные ряды и неиспользуемые подтипы не начинают проверяться из-за рефакторинга.** Обновление справки не является поводом менять компоновку Config или создавать новые named ranges.

## 9. A02-06. Аннотации, включая наклонный размер

Сохранить существующие возможности аннотаций через единый фасад: пользовательские anchors, привязки к пути, линейные размеры, радиус/диаметр, длину пути, текст, подписи фактической арматуры.

### 9.1. Полный пример наклонного размера

```vb
Private Sub DescribeSlopeDimension( _
    ByVal facade As CSectionDefinitionBuilder, _
    ByVal shapePath As CGeometryPath)

    facade.PathAnchor "Slope.A", shapePath.ID, "Edge.TR", 0#
    facade.PathAnchor "Slope.B", shapePath.ID, "Edge.TR", 1#

    facade.Dimension _
        annotationID:="DIM_SLOPE", _
        startAnchorID:="Slope.A", _
        endAnchorID:="Slope.B", _
        name:="L", measurement:="Aligned"
End Sub
```

Предусловие: исходный путь зарегистрирован, `Edge.TR` существует и имеет ненулевую длину. Размер показывает длину фактического прямого участка между его концами, не расстояние между виртуальными вершинами до скругления.

Для виртуального исходного отрезка объявить `Anchor` по исходным координатам. Не менять одну постановку на другую автоматически.

### 9.2. Обязательный контракт

- `Horizontal`: горизонтальная проекция между привязками.
- `Vertical`: вертикальная проекция.
- `Aligned`: истинное расстояние между привязками; размерная линия параллельна этому направлению.
- Длина пути из нескольких сегментов остаётся другой величиной и не подменяется хордой между концами.
- Геометрическое значение вычисляется по модельным данным. Пиксели, шрифт, раскладка надписей относятся к общему layout.
- Не вводить `Dimension30Degrees`, `DimensionForNose` и подобные специальные команды.

Сохранить существующее поведение поворота текста. Если код пока умеет только 0/90 градусов, не считать это поводом самовольно переписать layout; точно описать ограничение и согласовать изменение отдельно. Наклонная размерная линия при этом должна оставаться наклонной.

Не сводить все измерения к одному методу ценой потери смысла. Габарит пути/группы, заданная проектная длина, длина цепочки и расстояние между двумя anchors могут оставаться разными операциями одного API. У равнозначных исторических aliases должен остаться один канонический вариант после проверки потребителей.

## 10. Карта единого API после этапа

| Задача автора рецепта | Канонический способ | Чего больше не должно быть |
|---|---|---|
| Исходные вершины с радиусами | `CPolygonSpec.AddVertex` + `Seal` | Три обслуживаемых вручную массива в каждом рецепте |
| Скруглённый многоугольник | `facade.RoundedPolygon(pathID, polygon)` | Второй публичный вариант с массивами/V2/Ex |
| Смещённый скруглённый многоугольник | `OffsetRoundedPolygon(pathID, polygon, distance)` | Повторная упаковка массивов в рецепте |
| Прямая, дуга, окружность | Действующие `LinePath`, `ArcPath`, `CirclePath` | Замена окружности ломаной для единообразия |
| Прямоугольник/смежные прямоугольники | Действующие общие операции | Алгоритм Union внутри рецепта |
| Выбрать часть пути | `Chain` с явными привязками/направлением | Выбор «короткой стороны» без правила |
| Назначить бетон | `Outer` / `Opening` | Конкурирующий `OuterPolygon` |
| Зарегистрировать внешний путь | `AddPath` только для пути извне | Повторная регистрация пути, созданного фасадом |
| Основной ряд | Существующий метод выбранного распределения + общие options | Новый независимый раскладчик или альтернативная команда для того же правила |
| Контактный зависимый ряд | Общая подготовка options + `RebarDependent` | Формулы и sign-ветки, скопированные в несколько помощников |
| Проекция | `RebarProjected` с явными настройками | Превращение проекции в равномерный ряд |
| Наклонный размер | `Anchor/PathAnchor` + `Dimension(..., "Aligned")` | Особая аннотация для отдельного сечения |
| Публикация определения | `Finish` | Ручное заполнение внутренних полей definition |

Если текущая версия имеет другие имена, заполнить таблицу фактическими именами и сохранить единственность каждой строки. Не оставлять перечень «можно так, а можно по старому».

## 11. Перенос всех существующих семейств

| Семейство | Требуемый перенос | Что особенно сохранить |
|---|---|---|
| `RoundedRectangle` | Убрать параллельные массивы, использовать один spec для исходного контура и offsets; общие options и имена | Независимые Simple/Tapered, 4/5/6 вершин, точные дуги, ориентация B/H, F02, концевые режимы, W и W' |
| `HollowRectangle` | Одинаковый `CPolygonSpec` для наружного контура и отверстия там, где нужны вершины/радиусы; те же общие помощники рядов | Outer/Opening, смещённое отверстие, направления offset, конечные проекции, отсчёт успешных проекций, подписи внутренних рядов |
| `RectSet` | Сохранить общую сборку прямоугольников; убрать повторяющиеся технические ID/options/проверки | Rectangle/LSection/TwoRectangles, острые углы, нижний выступ Г-сечения, смещение верхнего прямоугольника, восемь граней, направления и полная база отсчёта setbacks |
| `Circle` | Сохранить аналитическую окружность; применить общие помощники там, где смысл совпадает | ClosedUniform, отсутствие дубля первого стержня, направление и старт, действующие дополнительные ряды |

**Не вводить `CPolygonSpec` в Circle или простой RectSet искусственно.** Унификация относится к одинаковым операциям. Но все действительные вызовы RoundedPolygon/OffsetRoundedPolygon в штатных рецептах, тестах и примерах должны перейти на выбранный единый формат.

Если источник из AutoCAD использует другой входной тип, сохранить адаптер импорта и его единственный переход в общую модель. Этот этап не переписывает CAD-import.

## 12. Границы ответственности и защита завершённого аудита

### 12.1. Распределение

|---|---|

| `CPolygonSpec` | Целостность исходных данных вершин, порядок, источники и запрет изменения после Seal |
| `CRebarRuleOptions` / существующий общий аналог | Подготовка нормализованных параметров правила; простая контактная связь диаметров, но не координатный расчёт |
| Фасад | Регистрация и единый удобный контракт, вызов общих операций |

| Аннотации/layout | Модельные измерения и размещение без изменения физической арматуры |
| Общий сборщик | Последовательность сборки; без анализа названия фигуры |

### 12.2. Не запускать заново предыдущий аудит

Ранее обсуждались циклическая зависимость Path/Query, привязки аннотаций в арматуре, mutable-выдача результатов сборки и обёртка cover-query в калькуляторе характеристик. Они могли быть уже исправлены.

Проверить, что новый этап не возвращает эти проблемы. Не делать повторный рефакторинг уже исправленных частей только по старому дампу. Существующие тесты их защиты использовать как smoke/regression.

Не считать любой публичный метод или массив «легаси». Удалять заменённые способы и ненужные обёртки, а не полезные уникальные операции. Не добавлять интерфейс на каждый небольшой контейнер ради формального SOLID.

## 13. Полный демонстрационный пример целевого использования

Это программный тестовый пример, не замена Config и не новый штатный тип. Он показывает новую работу с точками и прежний единый маршрут до Finish. Все локальные переменные объявлены. Новые методы должны быть реализованы до компиляции этого примера.

```vb
Private Function BuildAudit02DemoDefinition() As CSectionDefinition

    Dim facade As CSectionDefinitionBuilder
    Dim polygon As CPolygonSpec
    Dim shapePath As CGeometryPath
    Dim boundary As CGeometryPath
    Dim offsetPath As CGeometryPath
    Dim rightAxis As CGeometryPath
    Dim options As CRebarRuleOptions

    Dim b As Double
    Dim h As Double
    Dim w As Double

    b = 600#
    h = 1000#
    w = 200#

    Set polygon = New CPolygonSpec
    polygon.AddVertex "TL", -b / 2#, h / 2#, 80#
    polygon.AddVertex "TR", b / 2#, h / 2#, 120#
    polygon.AddVertex "RightNose", b / 2# + w, 0#, 80#
    polygon.AddVertex "BR", b / 2#, -h / 2#, 120#
    polygon.AddVertex "BL", -b / 2#, -h / 2#, 80#
    polygon.Seal

    Set facade = New CSectionDefinitionBuilder
    facade.Initialize "Audit02Demo"

    Set shapePath = facade.RoundedPolygon("Shape", polygon)
    Set boundary = facade.Chain( _
        "Boundary", shapePath.ID, _
        "Edge.BL", 0#, "Edge.BL", 0#, _
        forward:=True, fullLoopIfSame:=True)

    facade.Outer "OUTER", boundary.ID

    Set offsetPath = facade.OffsetRoundedPolygon( _
        "Offset.H.Right", polygon, 50#)
    Set rightAxis = facade.Chain( _
        "H.Right", offsetPath.ID, _
        "Edge.TL", 1#, "Edge.BR", 0#)

    Set options = New CRebarRuleOptions
    options.SetPublication _
        "H.Right", PublishPerSourcePosition, KeepPublishedOwner
    options.EndMode = ExcludeBoth
    options.StartSetback = 100#
    options.EndSetback = 150#
    options.IncomingTangentAtJoint = True

    facade.RebarByCount _
        "H.Right.Main", rightAxis.ID, 15, 20#, options
    facade.RebarRowExtentLabel _
        "H.Right", "H.Right.Main", 1#, 0#, 50#, True

    facade.PathAnchor "Slope.A", shapePath.ID, "Edge.TR", 0#
    facade.PathAnchor "Slope.B", shapePath.ID, "Edge.TR", 1#
    facade.Dimension _
        "DIM_SLOPE", "Slope.A", "Slope.B", "L", "Aligned"

    facade.HorizontalDistance _
        "DIM_B", "B", -b / 2#, b / 2#, h / 2#, 1#
    facade.VerticalExtent _
        "DIM_H", boundary.ID, "H", -b / 2#, -1#

    Set BuildAudit02DemoDefinition = facade.Finish
End Function
```

Не выдавать этот пример за инженерный подбор достаточного армирования. Его задача: проверить читаемость и работу API. Для расчётной приёмки использовать актуальные штатные модели с ранее принятыми нагрузками.

Для демонстрации полноценного добавления нового типа Codex должен отдельно включить в гайд один компилируемый `ISectionRecipe`-пример на итоговых методах. Это учебный `.cls`/fixture, не обязательный новый пункт Geometry.Type в рабочей книге. Не создавать несколько учебных классов-помощников для того, чтобы единственный рецепт выглядел коротким.
