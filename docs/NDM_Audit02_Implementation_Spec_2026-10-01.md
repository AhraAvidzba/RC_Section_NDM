# NDM: второй аудит и ТЗ на реализацию

**Версия:** 1.0 от 2026-10-01.  
**Проект:** NDMProgramm, Excel/VBA, `RC_Section_NDM.xlsm`.  
**Назначение:** самостоятельное задание Codex для выполнения в режиме цели от исходной контрольной точки до проверенного результата. Это ТЗ на реализацию, а не запрос только на разработку плана.

## 1. Цель и приоритет требований

Закончить переход к согласованной архитектуре, исправить подтвержденные остаточные проблемы первого аудита, убрать дублирование результатов и внедрить единый численный Extension для активных диаграмм материалов. Сохранить физическую модель, корректные численные результаты и работоспособность расчета без Extension.

Основные объекты архитектурной разгрузки: `CBatchSectionCalculator`, `CCrackWidthCalculator`, `CCapacitySolver`, `CCombinationResult`. Поиск старых дублирующих flat fields и совместимых API распространяется на весь проект, включая потребителей результатов.

### 1.1. Что является обязательным

Требования с идентификаторами `R`, `A`, `E`, `S`, `C`, `Q`, `D`, `W` и итоговый Definition of Done обязательны в пределах описанной применимости. Имена новых методов и внутренних полей, приведенные как примеры, не являются требованием создать именно такой API. Существующие классы и контракт их ответственности имеют приоритет перед изобретением дополнительных сущностей.

Раздел 3 описывает факты и риски, выявленные статическим чтением присланного экспорта. Последующие разделы задают требуемое поведение. Не выдавать планируемое поведение за уже существующую реализацию.

### 1.2. Соотношение с предыдущими документами

Использовать предыдущий архитектурный план, migration plan и `docs/NDM_PostRefactoring_Audit_2026-09-30.md` как историю решений и источник обязательных регрессионных проверок. Не откатывать проект к старой архитектуре и не повторять уже исправленные пункты механически.

Это ТЗ уточняет и заменяет прежние ограничения в следующих местах:

1. Прежнее разрешение Extension только для DirectState заменяется общим разрешением для всех реально используемых активных диаграмм и расчетных маршрутов. Физические пределы и критерии приемки остаются исходными.
2. Прежнее требование вынести из writer-ов даже элементарную арифметику не действует. Простые вычисления для представления, например коэффициент запаса `1 / utilization`, разрешены в writer-ах. Инженерные проверки и назначение статусов там по-прежнему запрещены.
3. Временные flat-поля и forwarding API не нужно сохранять только потому, что они были оставлены на промежуточном этапе. Потребители переводятся на канонические объекты, временный слой удаляется.
4. Сохранение численной математики не означает сохранение ошибочной интерпретации несошедшейся итерации как доказанного физического предела. Исправлять это по разделам R03 и S, не подгоняя тестовые числа.

При конфликте с фактическим репозиторием сначала проверить исходники и условия задачи. Не уменьшать объем ТЗ и не переопределять физическую модель для удобства реализации. Подлинное противоречие, требующее изменения согласованных ожидаемых чисел, оформлять отдельно с воспроизведением.

## 3. Остаточные замечания по фактическому коду

### R01. Cache-hit CurrentCrackedState и отсутствие LastRunner

**Наблюдение.** `CStateProvider.GetOrSolve` при reuse возвращает готовое состояние без нового `LastRunner`. `CBatchSectionCalculator.RunProfileState` передает этот runner далее. `CurrentCrackedStateReady` проверяет наличие состояния, сходимость и физический диапазон, но последующий вызов в `RunCrackWidth` использует `runner.ResultSolver`.

Навигация: `CBatchSectionCalculator.RunProfileState`, `RunCrackWidth`, `CurrentCrackedStateReady`; участок экспорта примерно 24472–24724. Тест из closure называется `TestCrackFormationCacheHitWithoutLastRunner`, то есть его имя само по себе не подтверждает проверку текущего состояния в batch.

**Риск.** При корректном cached CurrentCrackedState и реально требуемом расчете ширины возможен доступ к `Nothing`, хотя НДС уже есть. Это архитектурно тот же незакрытый класс ошибки, что и Old-T06.

**Исправить.** Достаточным входом для потребителя сделать каноническое найденное состояние и нужные материал/геометрию. Не требовать живого runner-а только ради чтения результата. Если существующей формуле необходим вычисленный solver snapshot, его восстановление поручить подходящему существующему слою, не запускать заново поиск равновесия и не создавать локальные разные способы восстановления в каждом consumer-е.

**Приемка.** Интеграционный тест проходит с заранее сохраненным CurrentCrackedState, `LastRunner = Nothing`, образованной трещиной и включенной шириной. Числа совпадают с путем без кэша; лишнего `CSectionSolver.Solve` нет.

### R02. Capacity: техническая граница поиска и последний непроверенный интервал

**Наблюдение.** `CCapacitySolver.LimitSearchHandleCapacityBracketNotFound` выставляет `STATE_NUMERICAL_FAILURE` и сохраняет `lowLambda`, хотя комментарий описывает достижение `Capacity.MaxLambda` без верхней физической границы. Навигация: примерно 12361–12365.

В `CLoadMultiplierSearch.FindCapacityBracket` следующая проба получается удвоением `highLambda`; цикл продолжается только пока `highLambda <= maxLambda`. При перескоке через MaxLambda оставшийся интервал может не исследоваться. Сохраненную acceptable-точку дополнительно использует pure-axial retained fallback.

**Исправить.** Разделить достижение технической границы и численную неудачу. Обеспечить корректную последнюю пробу на разрешенной границе, когда следующий шаг ее перескакивает. Не выдавать последнюю допустимую нагрузку за найденную несущую способность только потому, что дальнейший поиск остановлен.

Retained-данные можно сохранить для диагностики или подтвержденного специального метода. Их наличие не является доказательством достижения физического предела. Существующие корректные аналитические и осевые решения не удалять.

**Приемка.** Отдельно проверены предел до MaxLambda, предел ровно на границе, предел в интервале между последним удвоением и MaxLambda, а также отсутствие найденного предела к MaxLambda. Последний случай получает `rcSearchBoundReached`, если физическая недостижимость не доказана.

### R03. Несошедшаяся плоскость еще может выглядеть физическим отказом

**Наблюдение.** В `CCapacitySolver.ProbeOnce` после неуспеха runner-а вызывается `FailedProbeReachedPhysicalLimit`. Этот helper при числе итераций больше одной и utilization не меньше 1 возвращает признак физического предела по последней несошедшейся плоскости. Далее код пробы может попасть в обработку отказа начальной точки. Навигация: `ProbeOnce`, `FailedProbeReachedPhysicalLimit`, `LimitSearchHandleCapacityInitialFailure`; примерно 12817–12890 и 13022–13038.

**Проблема.** Две или больше итераций сами по себе не превращают пробную плоскость в равновесие. Исправленный конечный mapping `NumericalFailure -> NumFail` не защищает от неверно классифицированной входной пробы.

**Исправить.** Не назначать доказанный физический отказ, BaseFail или найденный предел только по несошедшейся итерации. Helper допускается сохранить как явно неподтвержденную численную подсказку для изменения шага/повтора поиска. Финальная классификация должна опираться на проверенное состояние или на отдельное надежное основание, а не на счетчик итераций.

Для финального Capacity достаточно непосредственно подтвердить его собственное равновесие, попадание на путь и физический критерий с заданной точностью. Не требуется бессмысленно повторять уже проверенные пробы. В точке `lambda = 0` неподтвержденное превышение деформаций не разрешает BaseFail.

**Приемка.** Есть тест с неуспешным solve после нескольких итераций и выходом промежуточных деформаций за предел. Без доказанного исхода это NumFail. Отдельный тест с сошедшимся extension-состоянием корректно проходит новую доменную классификацию.

### R04. Общий Search и его result еще не полностью независимы

**Наблюдения.**

- `ILimitSearchProblem` уже существует, но содержит `DomainContext As Object`, а также специальные formation-операции, не имеющие смысла для Capacity.
- `CUltimateStrainSearch` через `DomainContext` получает конкретные `CCapacitySolver` и `CCrackWidthCalculator`.
- `CLimitSearchCoordinator` знает специальную политику путей CrackFormation.
- `CLimitSearchResult.CaptureCrackSnapshot` после сброса сохраняет главным образом флаги и диагностику. Общие численные поля найденной точки не заполняются аналогично Capacity.
- `CLimitSearchResult.InitializeFromCapacitySolver` трактует `lambda < 1` как инженерный отказ уже в общем результате поиска.
- Успешный crack fallback с предупреждением может упрощаться до обычного success при построении search-result.

Навигация: `ILimitSearchProblem` от 1599; `CLimitSearchCoordinator` от 13762; `CLimitSearchResult` от 14265; `CUltimateStrainSearch` от 18060.

**Исправить.** Завершить разделение численного механизма и инженерной задачи по A04–A06. В существующих adapters/калькуляторах оставить физический смысл пути, критерия и принятия результата; в Search оставить численные процедуры. Не заменять прямую зависимость неограниченным late-bound доступом к тому же калькулятору.

`CLimitSearchResult` должен самодостаточно описывать исход поиска и найденную точку, когда она есть. Факт успешного нахождения Capacity при `lambda < 1` и отрицательный результат проверки заданной нагрузки являются разными фактами.

**Приемка.** Общие численные алгоритмы тестируются без конкретных Capacity/Crack-калькуляторов. Из search-result можно прочитать фактическую crack-точку и диагностику без доступа к исходному живому калькулятору. Предупреждения не теряются.

### R05. Реального владельца CrackFormation пока нет

**Наблюдение.** `CCrackFormationCalculator.CheckFormation` принимает `CCrackWidthCalculator`, вызывает его `CheckFormationBeforeWidth` и упаковывает ответ. Formation-обязанности остаются в Width. Навигация: примерно 18372–18404.

В `CCrackWidthCalculator.MarkFormationPathFallback` ветка трещины от постоянной части устанавливает `rsSuccessWithWarning + rcCheckPassed`. Специальная причина теряется. Навигация: примерно 20425 и далее.

**Исправить.** Перенести саму formation-ответственность, а не только внешний вызов. Уточнить machine code начальной трещины и сохранить согласованную возможность расчетного fallback с `psi_s = 1` без фиктивной точки образования. Подробности в A03 и S03.

**Приемка.** Formation можно выполнить без создания Width-калькулятора. Width получает результат formation как вход, не является его скрытым рабочим хранилищем и не повторяет поиск.

### R06. Физические признаки некоторых состояний задаются константами

**Наблюдение.** `CCapacityResult.StoreCapacityStateIfAvailable` передает в `InitializeFromSolver` значения `False, True` для ExtensionUsed и WithinPhysicalRange. Аналогичные предположения есть при подготовке части crack-состояний. `CSectionStateResult.InitializeFromPlane` также требует проверки контракта: готовая плоскость сама по себе не доказывает найденное равновесие.

**Исправить.** После глобализации Extension получать признаки из проверенного состояния и фактически использованных диаграмм. Не предполагать допустимость только по имени `CapacityState`/`PreCrackState`/`PostCrackState`. Чистая оценка плоскости допустима, но не должна автоматически свидетельствовать об успешном поиске равновесия.

**Приемка.** Состояние вне физического диапазона невозможно сохранить как допустимое за счет константных флагов. Валидные старые физические состояния сохраняют численные значения и корректный статус.

### R07. Дублированные результаты и риск устаревшей канонической ветви

**Наблюдение.** `CCombinationResult` хранит `CStrengthResult`, `CCrackResult`, `CStabilityResult` и repository, одновременно копируя их данные в большое количество flat fields. Это явно видно в `StoreCapacityResult`, `StoreCrackAggregateResult`, `StoreCrackFormationResult`, `StoreCrackWidthResult`, `StoreStabilityResult`.

Дублирование встречается и глубже: `CDirectStateResult` отдельно хранит плоскость, усилия, невязки и другие данные НДС. При этом его `StoreSolver` не обновляет ExtensionUsed так же, как `StoreStateResult`. Поэтому простая замена всех чтений flat fields на текущий typed объект без проверки полноты может проявить ранее скрытую рассинхронизацию.

**Исправить.** Сначала обеспечить полный и согласованный канонический result-tree, затем переводить потребителей и удалять вторичные поля. Проверить обе ветки, обычный solve и reuse, а также повторные расчеты на тех же экземплярах.

**Приемка.** Источник каждого результата однозначен; общее число механизмов копирования/синхронизации действительно уменьшается. Нет ситуации, когда sheet читает одно значение, typed consumer другое, а диагностический экспорт третье.

### R08. Асимметричные физические пределы арматуры

**Наблюдение.** `CCapacityCalculator.CreateConfiguredSolver` берет максимум модулей сжимающего и растягивающего пределов арматуры в один `SteelStrainLimit`. `CCapacitySolver.UpdateCriticalState` затем использует `Abs(strain) / mSteelStrainLimit` для обоих знаков. Навигация: примерно 11022–11042 и 13040–13076.

**Риск.** При разных заданных пределах меньший предел может не учитываться как управляющий, тогда как общая проверка physical range уже различает направления. Это особенно важно перед расширением обеих ветвей.

**Исправить.** Проверить все маршруты Capacity и UltimateStrain на согласованное использование физических ограничений для каждого знака деформации. Не менять сами пользовательские/нормативные значения и не подменять пару пределов максимумом без обоснованного контракта материала. Для материалов без такого API сохранить их явный тестовый контракт.

**Приемка.** Новые тесты с различными пределами растяжения и сжатия останавливаются на соответствующем физическом ограничении. Существующие корректные baseline-числа сохраняются. Обнаруженное противоречие старого expected физическому контракту не маскировать обновлением expected.

### R09. Безопасные проверки отсутствующих объектов

В изменяемых участках убрать проверки, предполагающие короткое замыкание `And`, `Or` или ленивый `IIf` в VBA. Например, доступ к `spec.IsComplete` не должен находиться в одном выражении с `spec Is Nothing`, если допускается отсутствующий объект.

Проверить таким образом входы state/search/result, ветки optional results, assertion-код новых тестов и output. Не делать ради этого несвязанный переписанный проект целиком. Отсутствие внутреннего обязательного объекта не превращать автоматически в ошибку пользовательского ввода.

## 4. Требуемое распределение ответственности

### A01. Не дробить классы ради количества строк

Сначала составить таблицу переноса: исходный класс/группа методов, реальная ответственность, новый существующий владелец, потребители, проверка неизменности результата. Переносить законченные обязанности вместе с необходимым состоянием. Не разносить один алгоритм по случайным файлам.

Не являются выполнением цели:

- удаление комментариев и пустых строк;
- уплотнение нескольких операторов в одну строку;
- перенос всего монолита в `Helper`, `Manager`, `Service` или стандартный модуль;
- замена 140 полей на 140 однострочных прокси в том же facade;
- сохранение старых алгоритмов рядом с новыми на неопределенный срок;
- уменьшение Batch за счет такого же чужого монолита внутри другого класса.

Новый production-класс допустим только при выявленной самостоятельной ответственности, для которой нет подходящего существующего владельца. Обоснование записать в план до добавления: почему существующие владельцы не подходят, жизненный цикл, зависимости, какие дубли/связи исчезают. Никакой квоты «обязательно N новых классов» нет; предпочтительная реализация обходится существующими классами.

### A02. CBatchSectionCalculator остается оркестратором

Оставить управление пакетом сочетаний, последовательностью запрошенных расчетов, передачей контекста, обработкой ошибок одного LC и сбором готовых результатов. Batch не становится местом физических формул и поиска равновесия.

Удалить большую скалярную витрину результатов после миграции consumers. Выдавать результат сочетания/его типизированные ветви компактным API, например `ResultAt(index) As CCombinationResult`, либо эквивалентным уже существующим способом. Это пример, не требование вводить дополнительный facade.

Настройки должны нормализоваться у существующих владельцев своей ответственности; общие solver-параметры передаются согласованно. Устранить лишние цепочки копирования одних настроек через несколько классов. Не передавать worksheet внутрь численных циклов и не читать Config при каждой пробе/каждом волокне.

Отчетное форматирование и повторяющиеся операции представления передать подходящему существующему отчетному слою, в том числе `CExecutionReport`, где это соответствует его задаче. Batch может сообщать факт этапа и передавать готовые данные. Не переносить инженерные проверки в отчет ради сокращения Batch.

### A03. Отделить образование трещин от ширины

`CCrackFormationCalculator` должен реально владеть:

- подготовкой доменной задачи трещинообразования и ее критерия;
- выбором/интерпретацией пути, включая согласованную Auto-политику;
- передачей задачи в общий Search;
- различением найденного предела, трещины от постоянной части, доказанного недостижения, технической границы и численной ошибки;
- подготовкой необходимых PreCrackState/PostCrackState через общий state pipeline;
- выдачей `CCrackFormationResult` с фактическими данными и метаданными.

В `CCrackWidthCalculator` оставить определение входов формулы ширины по требуемым физически допустимым состояниям: напряжения арматуры, соответствующие зоны/ряды, площади, характерные размеры и коэффициенты. Формульную часть использовать через существующий `CCrackWidthFormulaCalculator`, не создавать вторую копию формулы.

Использовать `CSectionPropertiesCalculator` для действительно общих характеристик сечения, а не превращать его в склад специальных правил трещин. Специфичная ширине обработка растянутой зоны может оставаться в Width, если это одна цельная ответственность.

`CLongitudinalCrackCalculator` сохраняет самостоятельную проверку продольных трещин. Отсутствие нормальной трещины не является основанием пропустить нужную проверку по сжатому бетону.

Исключить взаимные зависимости Formation -> Width -> Formation. Общие входы передаются объектами существующего контекста/результатов, а не возвратом огромного mutable Width-калькулятора в formation и search.

### A04. Capacity: инженерная задача отдельно от численного поиска

`CCapacityCalculator` отвечает за инженерную постановку: материал/spec, путь и начало поиска, нужные физические критерии, интерпретацию найденного предела относительно заданного сочетания, выдачу `CCapacityResult`.

`CCapacitySolver` разгрузить от обязанностей, уже принадлежащих общему Search, result-объектам и общему state pipeline. Допустимо оставить в нем цельную оценку capacity-пробы/критерия и действительно capacity-специфичные операции, если это обосновано итоговой картой ответственности. Его название не является основанием сохранить в нем копию общего поиска.

Обычные пробы равновесия идут через `CStateSolutionRunner` и `CSectionSolver`. Численные матрицы, интегрирование и алгоритм НДС не переписывать ради названий классов. Специальные оценки плоскости для residual/Jacobian/UltimateStrain не выдавать за обычный solve и не запрещать только потому, что они низкоуровневые.

### A05. Общий Search без скрытого знания инженерных калькуляторов

Сохранить и завершить использование `CLimitSearchCoordinator`, `CLoadMultiplierSearch`, `CUltimateStrainSearch`, `CLoadPathMath`, `CLoadPathVector`.

Общий численный слой должен получать задачу через явный контракт: путь/целевые величины, оценку пробы, критерий и необходимые численные данные. Он не должен приводить `DomainContext` к `CCrackWidthCalculator` или `CCapacitySolver`, читать сотни чужих полей или определять внешние статусы Capacity/Crack.

Доменные adapters `CCapacityLimitSearchProblem` и `CCrackLimitSearchProblem` архитектурно допустимы, даже если часть методов делегирует вызовы. Их назначение: отделить постановку задачи от численного механизма. Не удалять их только из-за размера и не плодить дополнительные adapters, повторяющие тот же переход.

Упростить `ILimitSearchProblem` так, чтобы общая часть не разрасталась за счет специфических no-op-операций каждой новой инженерной задачи. Использовать существующие владельцы и минимальный контракт, а не обязательно новый набор интерфейсов.

Для одной и той же численной операции не оставлять две независимые реализации bracket/bisection только с разными именами Capacity и Crack. Общую математику и обработку точности/лимитов объединить через контракт задачи; действительно разные специальные методы сохранить с описанной причиной.

Auto-переключение физического пути принадлежит доменной постановке. Переключение численного метода может принадлежать coordinator-у. `LoadMultiplier` и `UltimateStrain` остаются разными численными стратегиями: задача не состоит в насильственном превращении всех методов в один алгоритм.

### A06. Самодостаточный CLimitSearchResult

Общий результат поиска хранит свой исход, а не живой калькулятор как единственный источник данных. Минимально нужны:

- `CResultMeta`, сведения о запрошенном/фактическом методе и диагностике;
- однозначный признак наличия действительно найденной предельной точки, отличный от успешного завершения процедуры без точки;
- фактическая lambda, усилия и подтвержденное состояние найденной точки, когда они определены;
- при необходимости последняя допустимая проба/границы как явно диагностические данные, не выдаваемые за найденный предел;
- физические признаки и точность принятого состояния либо ссылка на канонический проверенный state snapshot.

Не требуется добавлять отдельный класс на каждый флаг или повторно хранить плоскость, если она уже есть в canonical state. Snapshot чисел/метаданных не должен меняться при следующем использовании solver-а или калькулятора.

Для Capacity `lambda < 1` само по себе не является неуспехом численного поиска. Инженерный FAIL заданного LC формируется в Capacity-слое. Для CrackFormation успешный поиск точки за текущим LC и отсутствие трещины при текущем LC также разделяются.

### A07. Один источник результатов по всему проекту

Ориентир использования существующих сущностей:

| Данные/обязанность | Предпочтительный существующий владелец |
| --- | --- |
| Пакет сочетаний и порядок запуска | `CBatchSectionCalculator` |
| Результаты одного LC и доступ к ветвям | `CCombinationResult` |
| Результаты прочностной ветви | `CStrengthResult`, `CDirectStateResult`, `CCapacityResult` |
| Единственное найденное НДС, физические признаки, provenance | `CSectionStateResult` |
| Образование, ширина и продольные трещины | `CCrackFormationResult`, `CCrackWidthResult`, `CLongitudinalCrackResult`, объединение `CCrackResult` |
| Устойчивость/расчетные усилия после ее учета | `CStabilityResult` и соответствующий calculator |
| Повторное использование конечных состояний | `CStateProvider`, `CStateRepository`, `CStateRequest` |
| Подготовка материальных диаграмм | `CMaterialModelProvider`, `CMaterialModelSpec`, параметры материалов |
| Напряжение/касательная/физические границы диаграммы | `CMaterialDiagram` |
| Общее исполнение НДС и стартовые приближения | `CStateSolutionRunner`, `CStateGuessBuilder`, `CSectionSolver` |
| Статусы, их отображение и согласованная агрегация | `CResultMeta`, `CResultStatusPolicy`, `CBatchStatusPolicy` |
| Вывод и форматирование | существующие writer-ы, `CExecutionReport`, readers/export-слои по назначению |

Перед удалением flat-поля установить, действительно ли это дубль той же величины. Исходные и расчетные усилия, разные точки приведения моментов, разные material role, Pre/Post/current-state и физическое значение/его представление в единицах пользователя не являются автоматически одним и тем же.

В частности:

1. У `CCombinationResult` удалить дубли результатов, повторные meta/status-хранилища и методы синхронизации, если источником уже служит typed ветвь.
2. У `CDirectStateResult` проверить необходимость отдельной копии данных `CSectionStateResult`. Сохранить смысл узла direct-result, но не параллельное mutable НДС.
3. Проверить такие же дубли у `CCapacityResult`, calculator-ов, providers, readers и экспортов. Рабочие численные данные алгоритма не удалять только потому, что часть их затем входит в финальный snapshot.
4. Перевести production-код и тесты на новые пути доступа в пределах этапа. Не оставлять массовую совместимость только ради старых тестовых accessor-ов.
5. Отдельно учитывать сериализованные таблицы Results. Плоский табличный формат вывода допустим; он не требует плоского дублированного хранения в доменной модели.
6. Не заменять типизированные объекты универсальным `Dictionary`/`Variant`-мешком только ради меньшего количества строк.

### A08. Writer-ы и сохранение целостных классов

`CSectionSolver`, цельные geometry/plotter-классы и writer-ы не дробить по размеру. Допустимы минимальные изменения, необходимые для устранения подтвержденного дефекта, перехода на typed consumers и глобального Extension.

В writer-ах разрешены единицы, округление, компоновка, подписи, арифметика представления и простой коэффициент запаса. До деления на utilization проверять доступность величины и ноль. Не создавать вымышленный бесконечный/нулевой запас для NumFail, BaseFail или отсутствующего результата.

Writer не выбирает физический критерий, не исправляет result-code, не запускает solver, не вычисляет самостоятельно инженерный FAIL и не извлекает смысл из `StopReason`. Итоговые статусы и важные комментарии должны совпадать в summary, подробном блоке, отчете и экспорте.

## 5. Global Diagram Extension

### E01. Единственная общая настройка

Для этого ТЗ принять канонический ключ **`General.DiagramExtension`** со значениями `Yes/No` в принятом формате Config. Пользовательская подпись: **«Численное продолжение диаграмм»**. Разместить строку в блоке общих настроек, не в блоке Solver и не среди отдельных material role.

Для новой книги рекомендуемое значение по умолчанию: `Yes`. Явное пользовательское `No` при миграции сохранить. Во всех расчетах использовать одно эффективное значение для данного запуска.

Старый `Solver.DirectState.DiagramExtension` удалить из актуального интерфейса, defaults и текущего рабочего API. Нормальная новая реализация не должна содержать двух независимых переключателей, один из которых незаметно переопределяет другой.

### E02. Миграция Config без потери пользовательских значений

Найти реальный источник генерации Config/справки/книги в репозитории и изменить его, а не только конкретную созданную книгу.

Правила миграции:

- есть только старый ключ: перенести его значение в новый и убрать старую рабочую строку;
- есть только новый: использовать его;
- есть оба: новый является явным каноническим значением; при различии выдать понятное предупреждение миграции и удалить дублирование после успешного сохранения;
- нет обоих: использовать документированный default новой книги;
- некорректное значение канонического ключа: ошибка настройки, а не молчаливая замена на `Yes`.

Миграцию старого значения выполнять до добавления defaults: автоматически созданное новое `Yes` не должно перекрыть ранее заданное пользователем `No`. Правило приоритета нового ключа относится к действительно существующему каноническому значению, а не к только что подставленному default.

Поддержка старого ключа допускается только в явно выделенной точке миграции/чтения старого формата. Runtime-калькуляторы его больше не читают. Миграция повторно выполняется безопасно и не переставляет строки/значения при каждом запуске. Проверить named ranges, validation, ссылки «Подробнее», соседние настройки и сохранение книги.

### E03. Область действия

Единое разрешение распространяется на все существующие маршруты, которые действительно вычисляют напряжения/равновесие по соответствующим диаграммам:

- прямое НДС прочностной ветви и текущее CrackedState;
- начальную точку, внутренние пробы и проверку итоговой точки Capacity;
- CrackFormation, включая LoadMultiplier, UltimateStrain и Auto-fallback;
- PreCrackState и PostCrackState;
- внутренние state-вызовы других расчетов, если они используют материальные диаграммы.

Не создавать дополнительных вызовов НДС в формулах устойчивости только для того, чтобы они «использовали Extension». Аналитические характеристики, нормативные сопротивления, коэффициенты и формулы Stability сами по себе не меняются. Техническая касательная расширенной ветви не становится новым нормативным модулем для них.

Запретить остаточный выбор «extended только потому, что StateType = StrengthState/CrackedState». Реестр фактических маршрутов и их настройки записать в progress.

### E04. Только активные физические ветви

Extension продолжает активную ветвь, но никогда не создает выключенную физическую работу материала.

| Ветвь эффективной material model | Extension при общем Yes |
| --- | --- |
| Работающий сжатый бетон | Разрешено численное продолжение за его физическим пределом |
| Работающий растянутый бетон (`ctkUseDiagram`) | Разрешено продолжение за физическим пределом растяжения |
| Выключенный растянутый бетон (`ctkIgnore`) | Запрещено: при растяжении `sigma = 0`, `Et = 0` |
| Работающая арматура в растяжении/сжатии | Разрешено для соответствующих активных ветвей |
| Тестовый материал без конечного физического предела/extension API | Сохранить его исходный material API, не выдумывать предел |

Активность определяется **эффективным spec конкретного расчета**, не чужой настройкой другого purpose. Например, Ignore для Strength не запрещает активную tensile-ветвь отдельной CrackInitiation-модели. И наоборот, расширение CrackInitiation не должно включать растянутый бетон в PostCrack/CrackedState.

Положительная деформация отключенного растянутого бетона не является сама по себе ни использованием extension, ни нарушением tensile-предела отсутствующей ветви.

### E05. Неизменность физической модели

Внутри исходной физической диаграммы сохранить точки, напряжения, принятую касательную, плато, предельные деформации и правила material role. Не добавлять малый наклон к физическому плато ради сходимости. Граница физического диапазона остается включенной с существующим согласованным допуском.

`UltimateCompressionStrain`, `UltimateTensionStrain`, физические сопротивления и критерии должны по-прежнему описывать физическую модель, а не край технического продолжения.

Для одинаковой физически допустимой конечной точки расчеты On/Off должны совпадать в пределах прежних допусков. Особенно проверить значения точно на узлах диаграммы: добавление технической точки не должно незаметно изменить старое правило выбора касательной на физической границе.

### E06. Использовать существующий механизм, не изобретать новую физику

В текущем `CMaterialModelProvider.DiagramWithExtension` уже есть техническое линейное продолжение; исходный механизм использует жесткость порядка `0.01 * E` и далекие технические границы деформации `±10`. При планировании подтвердить значения по реальному коду.

Это отправная точка для обобщения, а не новая нормативная ветвь. Сохранить существующий закон для уже расширявшихся ветвей, если нет конкретного технического дефекта. Новую активную tensile-ветвь бетона продолжать согласованно тем же численным принципом. Не вводить дополнительные пользовательские коэффициенты/режимы без необходимости.

Техническая граница должна быть за физическим пределом соответствующей ветви. Если пользовательский физический предел сам выходит за фиксированную техническую константу, нельзя молча обрезать материал или пропустить требуемое продолжение. Обработать случай безопасно и явно в рамках выбранного механизма.

Напряжения и касательные должны быть конечными, согласованными между evaluator-ами; не допускать overflow и ложного равновесия на бесконтрольном clamp. Достижение технического края продолжения не является физическим пределом несущей способности.

### E07. Отдельные факты результата

В существующей result/state-модели должны быть различимы:

1. `Converged`: выполнен критерий численной сходимости данного solve.
2. `WithinPhysicalRange`: конечная проверенная плоскость удовлетворяет физическим ограничениям активных ветвей.
3. `ExtensionUsed`: хотя бы один реально учитываемый элемент конечного найденного состояния находится в техническом продолжении использованной диаграммы.
4. Эффективное разрешение Extension в контексте расчета, необходимое для воспроизводимости и выбора модели.

Имена существующих свойств предпочтительно сохранить там, где их смысл подходит. Не создавать параллельные противоречащие флаги.

`Extension = Yes` не означает `ExtensionUsed = True`. Выход пробной Newton-итерации в продолжение с последующим возвратом в физический диапазон не означает физический отказ конечного состояния. При необходимости отдельно фиксировать «использовалось в ходе итераций», но этот диагностический факт не заменяет три первых признака и не ухудшает инженерный статус сам по себе.

При неуспешном solve отсутствие проверенного диапазона не трактовать как доказанное физическое превышение. Поле False в таком случае нужно читать совместно с отсутствием сходимости; нельзя делать общий вывод `Not WithinPhysicalRange -> FAIL` без проверки результата.

### E08. Extension дает вспомогательное равновесие, не дополнительную несущую

Сошедшееся состояние за физическими границами является решением вспомогательной численной модели. Оно годится для диагностики, поиска/уточнения физической границы и предусмотренной доменной классификации, но не для выдачи допустимого физического НДС.

Не утверждать, что один такой корень доказывает отсутствие любого другого физического решения у произвольной нелинейной задачи. Соблюдать принятую ветвь решения/продолжение нагрузки; при неоднозначности не подменять доказательство эвристикой. Улучшение статусов нужно получать за счет более достоверных данных, не путем массового переименования NumFail.

Итоговая физическая точка Capacity/CrackFormation проверяется по исходному критерию, целевым усилиям, пути и допускам. Запрещено принять extension-точку как новую большую `Nult/Mult/lambdaUlt` либо обрезать ее деформации до предела без повторной проверки равновесия.

### E09. Согласованность всех численных стратегий

Для LoadMultiplier разрешены extended-пробы с явной классификацией допустимой/недопустимой стороны. Для UltimateStrain техническое продолжение может помогать промежуточным оценкам и решению системы, но целевой residual использует физический предел, а не конец extension.

Не заменить существующий критерий CrackFormation универсальной константой только из-за удобства нового API: фактическое правило может зависеть от принятой диаграммы и напряженного состояния. Сохранить существующую инженерную методику.

Финализация после Brent/Secant/Bisection/UltimateStrain/Auto не должна зависеть от того, каким методом была получена одна и та же подтвержденная точка. Методическая проверка результата проводится одинаково.

### E10. Off является полноценным режимом

При `General.DiagramExtension = No` расчет использует обычные диаграммы и прежние корректные численные маршруты. Не разрешать скрытый extension в retry/guess-builder, в analytical fallback или через устаревший provider API.

При нормальных условиях все ранее поддерживаемые расчеты должны работать без extension. Отсутствие сходимости в сложном случае Off возможно и не исправляется принудительным включением общей настройки за спиной пользователя.

При этом не удалять методы начальных приближений и warm-start, которые существуют независимо от extension и используются обычными диаграммами.

## 6. Статусы и инженерная интерпретация

### S01. Сохранить InternalStatus + ResultCode

Сохранить разделение внутреннего статуса, уточняющего машинного кода и внешнего статуса. Использовать существующие `EResultInternalStatus`, `EResultCode`, `EResultKind`, `CResultMeta`, политики.

Код не определяется парсингом `StopReason`, `ResultComment` или текста отчета. Форматирование диагностической строки допустимо, обратное восстановление из нее инженерного смысла нет.

В определении каждого затрагиваемого enum/code нужен русский комментарий «что это означает». В слое interpretation нужен русский комментарий «что этот исход означает здесь и как он влияет на продолжение/вывод». Не смешивать общее определение с частным внешним названием.

### S02. Начальная точка Capacity

Для пути `Target(lambda) = Offset + lambda * Base` исходная точка это полный Offset, не обязательно только N. Учитывать постоянные моменты и принятую точку приведения нагрузок.

| Подтвержденный исход при lambda = 0 | Действие |
| --- | --- |
| Равновесие допустимо и начальный критерий не нарушен | Продолжать поиск |
| Установлено нарушение исходного физического критерия | `rsCheckFailed + rcInitialStateBeyondLimit`; внешний Capacity-статус `BaseFail` |
| Найдено вспомогательное extended-равновесие, и по предусмотренной проверке подтвержден неприемлемый старт выбранного пути | То же доменное `BaseFail`, с комментарием о физическом пределе и auxiliary-модели |
| Равновесие не найдено; есть только пробные превышения деформаций | `rsNumericalFailure` с соответствующим code, внешний `NumFail` |
| Ошибка входа или настройки | `InputErr` по typed причине |
| Внутренняя ошибка контракта | `CalcErr`, не выдавать за input/physical failure |

Отдельно проверить точную границу предела при lambda = 0 и существующий tolerance: не объявлять «уже превышено» из-за округления. Не выдумывать положительную capacity lambda для такого случая и не делить на нулевую lambda. Конкретная граничная трактовка должна соответствовать принятому физическому критерию, быть явно описана и покрыта тестом.

`BaseFail` относится только к результату Capacity. Это оценка начальной части выбранного пути, а не утверждение об отсутствии любых допустимых состояний при любых дальнейших изменениях нагрузки.

### S03. Начальная трещина, фиксированный путь и Auto

Сохранить согласованные варианты `LambdaMxy`, `LambdaN`, `LambdaNMxy` и существующий порядок Auto-переходов. При доказанной трещине от постоянной части:

- фиксированный путь не менять без разрешения пользователя;
- фиксировать `rcInitialStateBeyondLimit` как причину невозможности определить искомую точку на исходном допустимом участке;
- где действующая методика разрешает продолжить расчет ширины от корректного CurrentCrackedState с `psi_s = 1`, использовать осмысленный warning-результат, например `rsSuccessWithWarning + rcInitialStateBeyondLimit` для formation/fallback, а не общий `rcCheckPassed`;
- не создавать фиктивные `PreCrackState`, `PostCrackState`, `sigma_s,crc` и найденную lambda только для заполнения таблицы;
- Auto может попробовать другой разрешенный путь; успешный итог относится к фактически найденной точке, а причина смены пути сохраняется в метаданных/диагностике и пользовательском комментарии.

Не назначать внешний `BaseFail` трещинам. Не переносить негативный статус неудачного первого пути на корректно завершившийся альтернативный путь. Предупреждение о переходе при этом не должно исчезать.

### S04. Критерий недостижим, граница поиска и нет трещины сейчас

Различать три разных ситуации:

1. **Поиск обоснованно установил недостижимость критерия на рассматриваемой траектории/в применимом расчетном диапазоне.** `rcCriterionNotReached`; отсутствие трещины трактуется в crack-слое. Нет фиктивной предельной точки.
2. **Достигнут лишь технический MaxLambda/лимит поиска, а недостижимость не доказана.** `rcSearchBoundReached`; это не доказанное отсутствие трещины и не точная несущая способность. В текущем словаре допускается внешний NumFail с точным понятным комментарием. Отличать от общей numerical failure по code.
3. **Физическая crack-точка найдена при lambda больше текущей нагрузки.** Поиск точки успешен, но при текущем LC трещины нет. Не затирать факт найденного предела общим утверждением о его недостижимости. Не создавать ненужные post-состояния лишь ради единообразия; сохранять действующую семантику запрошенных расчетов.

Знак сжимающей N сам по себе не является универсальным доказательством отсутствия растяжения для любой геометрии, армирования и точки приложения. Использовать существующие специальные аналитические ветви только в их области применимости. Если применимость/доказательство отсутствует, не превращать search bound в физический вывод.

### S05. Неприемлемый CurrentCrackedState

Если CurrentCrackedState не найден или вышел за физические пределы, зависимые формулы ширины/продольных трещин не получают статус OK и не выполняются по недопустимым напряжениям. В result-tree сохранить первичную причину состояния, а зависимому этапу назначить `BlockedByDependency`.

Агрегация всего crack-результата должна видеть обязательную отказавшую ветвь, даже если width-meta сама является N/A. Численные auxiliary-данные допускается показать только как явно диагностические.

### S06. Psi и sigma_s,crc

В текущем коде `AutoPsi` уже ограничивает вычисляемый коэффициент диапазоном до 1. Это не новая задача по смене методики. Сохранить верхнее ограничение `psi_s <= 1`, существующее нижнее ограничение, обработку нулевого/сжимающего напряжения и смысл режимов `User`, `Auto`, `AlwaysCalc`.

Добавить направленные тесты на `sigma_s,crc <= 0`, недоступную точку formation при разрешенном fallback и нормальный положительный случай. Не подменять доступное физическое `sigma_s,crc` искусственным значением ради прохождения теста. Для User-параметра сохранить правила его валидации и не вводить молчаливую новую корректировку ввода.

### S07. Согласованность отображения

Summary, подробные блоки прочности/трещин/устойчивости, общий статус LC и текстовый отчет читают один источник метаданных. `SuccessWithWarning` может отображаться как OK по существующей policy, но важный русский комментарий обязателен и не теряется при упаковке результатов.

Отключенный расчет не становится FAIL из-за чужой diagnostic-пробы. Невыполненный обязательный этап не выглядит «успешной проверкой нулевого значения». Различать доступность результата и численное значение 0.

## 7. State pipeline, snapshots и кэш

### C01. Один инструмент поиска равновесия

Сохранить общий маршрут обычного равновесия через `CStateSolutionRunner` и `CSectionSolver`. `StrengthState` и `CapacityState` используют общий инструмент, но Capacity не должен запускать целиком отдельный инженерный Strength-расчет на каждой пробе.

Сохранить текущее исправление runner-а для Object material API. Распознавание специальных возможностей `CMaterialDiagram` допускается в соответствующем материальном/численном слое; не добавлять повсюду предположение, что все тестовые материалы обязаны иметь физические границы.

### C02. Ключ отражает эффективный расчет, а не имя кнопки

При reuse учитывать фактические усилия в согласованной системе координат, material spec/role и реально выбранную численную модель. Эффективное значение Extension или изоляция/инвалидация кэша при его смене должны исключать использование extended-состояния как результата режима Off.

Значения `UseDirectStateExtension = True` недостаточно, если фактический provider мог быть и On, и Off. После миграции старые direct-only разрешения/имена не должны образовывать параллельную политику.

Геометрия, свойства материалов и значимые настройки обязаны соответствовать контексту repository. Это можно обеспечить ключом, неизменяемым scoped контекстом и его инвалидированием. Не требовать большой новый fingerprint-класс, если существующего жизненного цикла достаточно. Результат, найденный с более слабыми допусками, нельзя выдавать как удовлетворяющий более строгому запросу без проверки.

Warm-start, конкретное начальное приближение и номер retry сами по себе не определяют физическое состояние и не должны дробить repository конечных результатов. Если численный режим действительно задает другую ветвь/модель, это должно быть явно описано отдельно от координат начального guess.

### C03. Repository и transient probe-cache не одно и то же

`CStateRepository` хранит конечные запрошенные/сохраненные состояния. Search может иметь небольшой локальный кэш проб одного поиска. Не записывать весь итерационный след как множество named-state.

Сохранить полезный кэш уже вычисленных проб и warm-start. Конкретная структура не предписана: разрешено использовать существующий кэш и перенести его с соответствующей ответственностью. Не создавать новый класс кэша только ради этого ТЗ и не удалять кэш с заменой на повторные дорогие solve.

Проверить согласованность cached lambda, нагрузки, критерия, effective materials и сохраненного состояния. Failed-проба не должна навсегда блокировать повтор при появившемся лучшем старте/расширенной стратегии. Успешный retry обязан заменить соответствующий неуспешный результат.

### C04. Converged не означает допустимый инженерный вход

Reuse сошедшегося auxiliary-состояния допустим для подходящего идентичного диагностического запроса, но downstream не должен считать его физически допустимым только из-за Converged. Диапазон и code проверяются независимо.

Не переиспользовать несошедшееся НДС как готовый successful state. Разрешенные начальные приближения из прошлых попыток являются solve-options, а не «готовым результатом».

### C05. Самодостаточность сохраненного вывода

После расчета отчет, схемы, readers Results и AutoCAD export должны воспроизводить тот же результат без запуска нового равновесия и без зависимости от оставшегося `LastRunner`.

Сохранить достаточно информации об использованной материальной модели/эффективном Extension. Изменение Config после расчета не должно незаметно менять напряжения в старом сохраненном состоянии. Если архитектура требует пересчета после изменения данных, старый snapshot явно инвалидировать и сообщить об этом; не молча интерпретировать его по новым диаграммам.

Не разрешать writer-у угадывать диаграмму по списку «только StrengthState/CrackedState бывают extended». Физические пределы и признаки должны быть восстановимы по самому расчетному контексту/snapshot. Схемы материала продолжают отображать исходную физическую диаграмму; техническое продолжение, если показывается, явно обозначено как численное, не как запас материала.

### C06. Объектная целостность

Проверить `Clear`, `Initialize`, `Clone`, `SetMeta`, повторный запуск и повторное использование экземпляров: ветви и flags предыдущего LC не должны протекать в новый. Не оставлять cycles ссылок Batch/Calculator/Result/Adapter, мешающие освобождению объектов VBA.

Results после формирования не должны изменяться при очередном solve на том же рабочем solver-е. При этом не вводить глубокое копирование всех волокон и массивов на каждом Property Get: безопасность snapshot и производительность решаются согласованным владением, а не тотальным клонированием.

## 8. Тесты и численная приемка

### Q01. Исходный baseline сохранить до правок

На исходном репозитории повторить сборку и все штатные тесты. Зафиксировать коммит, команды, exit codes, полные логи, test counts и численные контрольные результаты. Не считать логи из closure заменой нового запуска.

Разделить существующие тесты на проверяющие обычные диаграммы и явно требующие уже существовавшего direct-state Extension. Нормальные baseline-сценарии дополнительно выполнить с Extension Off и сохранить результаты **до** внедрения общей настройки.

### Q02. Существующий режим Off не ломается

Все существующие проверки поведения обычных диаграмм сохранить и выполнить при глобальном Off. Их численные expected values и принятые tolerance не менять. Допустимы технические изменения путей доступа к typed результату, нового ключа Config и setup/teardown, если смысл и ожидаемые числа прежние.

Не удалять тесты с несходимостью/предельными ветвями потому, что новый On умеет их решать. Они продолжают проверять соответствующее поведение Off. Не заменять сравнение чисел проверкой «объект создан».

### Q03. Существующие Extension-тесты не отключать

Исторические тесты, которые уже явно включали `Solver.DirectState.DiagramExtension = Yes`, должны остаться проверками режима On после переноса ключа. Нельзя механически принудить их к Off и затем считать расхождения поломкой исходного поведения.

Замененные или параметризованные тесты обязаны сохранять покрытие исходных ветвей. Все изменения setup/expected статусов перечислить с причиной; изменение физических expected-чисел для маскировки регрессии запрещено.

### Q04. Парное сравнение On/Off

Для существующих корректно сходящихся физических сценариев автоматически сравнить одинаковые входы при Off и On. Проверять, где величины применимы:

- усилия и моментные reference-системы;
- epsilon0, kappaX, kappaY, напряжения/деформации и экстремумы;
- lambdaCapacity, Nult/Mxult/Myult, управляющий физический критерий;
- lambdaCrc, Ncrc/Mcrc, доступные Pre/Post/current-state;
- a_crc, sigma_s, sigma_s,crc, psi_s, ls, площади/геометрию зоны и utilization;
- результаты Stability и расчетные усилия после нее;
- статусы применимых физических проверок и доступность результатов.

Использовать прежние абсолютные/относительные допуски с учетом единиц; вывести максимальное отклонение по каждому сравнению. Совпадение конечной физики не требует одинаковых итераций, журналов, начальных приближений и длительности выполнения.

| ID | Сценарий | Что обязательно доказать |

## 9. Документация и интерфейс

### D01. Обновить весь актуальный пользовательский и архитектурный контракт

Исторические документы не переписывать как будто новый код существовал раньше; пометить явно замененные ограничения и дать ссылку на актуальную архитектуру.

Русские комментарии в исходниках сохранять читаемыми. Кодировку VBA-файлов определять по реальному репозиторию и его build/import-процессу. Mojibake текстового индексатора не является основанием массово перекодировать корректный VBA. MD хранить в UTF-8.

В справке разделять численный механизм и физические требования используемой методики. Не добавлять непроверенные ссылки на новые СП и не менять нормативные формулы в рамках этого рефакторинга.

### D02. Обязательный смысл комментария и справки Extension

Короткий комментарий рядом с настройкой:

> Численное продолжение активных диаграмм за физическими пределами. Рекомендуется для улучшения сходимости и диагностики. Не увеличивает физические пределы материалов и не разрешает считать состояние в продолжении допустимым. Расчет с обычными диаграммами доступен при No.

Развернутый текст справки, допускается редактура без изменения смысла:

> **Численное продолжение диаграмм (Extension)** является общим численным инструментом решения. Оно продолжает только активные ветви материальных диаграмм за их физическими пределами и помогает нелинейному решателю получать более устойчивые приближения, уменьшать количество некоторых ситуаций NumFail и точнее объяснять результат расчета.
>
> Настройка не изменяет исходную физическую часть диаграмм, сопротивления и предельные деформации. Для корректно найденных физических состояний численные результаты при Yes и No должны совпадать в пределах принятой точности. Равновесие, найденное только в техническом продолжении, не означает дополнительную несущую способность и не принимается как физически допустимое состояние.
>
> Возможность найти вспомогательное равновесие часто позволяет отличить численную неудачу от выхода за физический диапазон. Например, для начальной части выбранного пути Capacity программа может обоснованно выдать BaseFail с пояснением вместо общего NumFail. Такое уточнение возможно не во всех случаях: Extension не гарантирует сходимость любой задачи и не заменяет проверку физического результата.
>
> Рекомендуется использовать Yes. Настройка не обязательна: при нормальных условиях расчет должен корректно работать и при No на обычных диаграммах. Выключенная растянутая ветвь бетона не включается через Extension. Применение определяется материалом и ролью каждого конкретного расчета.
>
> Различайте разрешение продолжения, его фактическое использование в конечном состоянии и физическую допустимость. Промежуточный выход итерации за предел с возвратом в физический диапазон не означает отказ конечного результата.

Уточнить это и в комментариях public API: название Extension не означает изменение engineering limit. Старые утверждения «только DirectState» удалить из актуальных описаний, включая экспорт и reader-ы.

## 11. Definition of Done

Цель выполнена только после подтверждения всех применимых пунктов:

- [ ] R01–R09 закрыты реализацией/проверкой; неподтвержденный в репозитории риск исключен с конкретным доказательством, не общей фразой.
- [ ] Четыре целевых класса разгружены по ответственности; достигнуто реальное уменьшение дублирования, а не косметики.
- [ ] Formation работает независимо от Width, выдает отдельный полный результат и использует общий Search.
