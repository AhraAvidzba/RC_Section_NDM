Задача в режиме «Цель» теперь включает не только СП 35, но и необходимые общие изменения геометрии:

1. единый источник и единое вычисление пересечений с границами сечения, opening и заданными нейтральными линиями для всех классов и расчетов, которым нужны одинаковые геометрические операции, включая СП 35 и СП 63;
2. опциональный импорт внешних контуров и `opening` из заданных слоев AutoCAD;
3. сохранение и показ контуров сгенерированной и импортированной геометрии;
4. корректное ограничение локальной площади взаимодействия первой границей пустоты;
5. сохранение критической области через существующую инфраструктуру аннотаций;
6. реализованный сейчас, а не отложенный экспорт этой области в AutoCAD по переключателю;
7. отдельный сворачиваемый раздел справки о подготовке геометрии в AutoCAD;
8. новые тесты и полная регрессия уже существующих расчетов и общих классов.

**Направления обмена различать:** получение геометрии из AutoCAD является импортом; выгрузка рассчитанной области $A_r$ в AutoCAD является экспортом. При этом настройки AutoCAD должны быть организованы **одним общим блоком `AutoCAD` с подблоками `Common / Import / Export`**. Семантические имена слоев и другие параметры, которые должны быть одинаковыми при импорте и экспорте, находятся в `AutoCAD.Common`; импорт-специфичные параметры — в `AutoCAD.Import`; экспорт-специфичные параметры и визуальное оформление экспорта — в `AutoCAD.Export`.

Расчет СП 35 является потребителем готового НДС. Новые требования не разрешают внедрять в него solver, поиск трещинообразования, повторное решение состояний или отдельную status-policy. Writer-ы и экспортеры остаются пассивными.

**Обязательная централизация геометрии:** выбор источника границ, сами одинаковые операции пересечения, учет opening, обработка касаний и построение бетонных интервалов должны иметь одну общую реализацию. Недостаточно централизовать только хранение контуров, оставив копии вычислений в расчетах. Codex сначала проверяет существующий класс геометрических характеристик/запросов и весь перечень потребителей. Затем либо расширяет подходящую существующую ответственность, либо выделяет один согласованный геометрический компонент с переиспользованием имеющихся низкоуровневых инструментов. Подробный контракт и порядок перехода приведены в разделе 23.

# 1. Нормативная и методическая база

Для реализации используются два уровня источников.

## 1.1. Основной нормативный источник

**СП 35.13330.2011 «Мосты и трубы»**, действующая редакция, применяемая в проекте.

Ключевые положения для этой задачи находятся прежде всего в пп. **7.105, 7.109, 7.110**, таблице **7.26**.

Основные положения СП 35, существенные для алгоритма:

- ширина раскрытия нормальной трещины определяется через напряжение в расчетной растянутой арматуре, модуль упругости арматуры и коэффициент раскрытия трещин;
- коэффициент раскрытия трещин зависит от радиуса армирования `Rr`;
- радиус армирования определяется как

$$
R_r=\frac{A_r}{\sum \beta n d}
$$

- `Ar` – площадь зоны взаимодействия;
- СП 35 предусматривает нормативные радиусы взаимодействия $r=6d$, $r=3d$ и $r=5d$ для соответствующих случаев, описанных в п. 7.110;
- `d` в нормативной формуле – диаметр одного стержня, включая стержни, расположенные в группах;
- `r` откладывается от крайнего ряда, ближайшего к нейтральной оси, с нормативной оговоркой для неполного крайнего ряда;
- зона взаимодействия не должна выходить за нейтральную ось;
- при центральном растяжении зона взаимодействия принимается равной всей площади сечения;
- при многорядном армировании должны корректно учитываться стержни/группы нескольких рядов, попавшие в рассматриваемую область взаимодействия.

В NDM конкретный нормативный множитель для $r$ задается пользовательской настройкой из допустимых вариантов СП 35. Не создавать автоматическую отдельную ветку алгоритма по типу геометрии сечения.

## 1.2. Методический источник

Используется официальное действующее:

**«Методическое пособие. Методические рекомендации по применению СП 35.13330.2011 "Мосты и трубы"», 2017.**

Оно применяется:

- для разъяснения геометрического смысла `Ar`;
- для понимания рисунка **4.42 «Примеры изображения площади взаимодействия Ar»**;
- для трактовки суммирования одиночных, сдвоенных и строенных стержней по рядам;
- для сверки примеров расчета;
- для понимания способа геометрического определения `Ar`.

Методическое пособие **не имеет приоритета над действующим СП 35**.  
При расхождении всегда применять СП 35.

## 1.3. Маркировка происхождения правил

В коде, комментариях и будущей справке желательно различать три типа решений:

- `[SP35]` – прямое требование СП 35;
- `[METHOD]` – пояснение/методика из Методического пособия;
- `[NDM]` – программное допущение или универсализация NDM, прямо не установленная нормативом.

Это разделение обязательно сохранить в будущей пользовательской справке.

# 2. Общий архитектурный принцип: готовое НДС, без решателя внутри проверки

## 2.1. Граница ответственности

Расчет раскрытия трещин по СП 35 является **нормативным и геометрическим постпроцессором уже полученного состояния НДС**, как остальные расчетные проверки проекта.

```text
Генератор / импорт геометрии
  → модель сечения и общий доступ к границам бетона/opening

Существующий координатор расчетов
  → существующий решатель / поиск расчетных состояний
  → готовые состояния и внутренние результаты
  → существующая политика пригодности входа следующего этапа
  → проверка ширины трещин СП 35
       группы → ряды → геометрия Ar → формулы → результат

Результат СП 35
  → существующая инфраструктура аннотаций/результатов
  → пассивный writer / схема / экспортер AutoCAD
```

## 2.2. Что поступает на вход СП 35

Использовать фактические DTO/объекты новой архитектуры, не создавать второе семейство состояний только для этой методики. На входе должны быть доступны:

- уже найденное состояние для расчета ширины: деформации и напряжения арматуры, используемые модули материалов, положение плоскости деформаций/Н.О.;
- существующие ссылки на состояния до/после образования трещины, только если они нужны принятому сценарию; их вывод в таблицу не означает, что их обязан вычислять модуль СП 35;
- модель геометрии и общий сервис пересечений с известными контурами либо с дискретной геометрией;
- параметры методики, физической применимости и необходимые идентификаторы сочетания/результата.

Названия `PreCrackState`, `PostCrackState`, `CrackedState` и другие в MD являются смысловыми ориентирами. Использовать существующие аналоги текущего кода.

## 2.3. Прямые запреты

Из проверки СП 35, построителя $A_r$, writer-а, схемы и экспортера нельзя:

- вызывать solver, Newton/итерации равновесия или поиск точки трещинообразования;
- заново вычислять НДС ради недостающего поля или экспорта контура;
- переключать диаграммы, изменять настройки extension, стартовые приближения, ветви решения или кэши решателя;
- читать внутренние временные данные решателя вместо штатного результата;
- определять внешний статус по собственному списку строк либо изменять внутренний статус;
- получать расчетную геометрию из уже масштабированных экранных фигур Excel/AutoCAD.

Если необходимого состояния нет, существующий координатор обрабатывает отсутствие/непригодность входа по общему контракту. Проверка СП 35 сообщает об этом тем же способом, что другие проверки, но не пытается самостоятельно «добыть» НДС.

## 2.4. Отображение статуса и возможность продолжения

Внешний статус формируется существующей централизованной policy/mapper. Writer только выводит полученное представление. Пригодность состояния для дальнейшего расчета определяется существующим расчетным контрактом/координатором, а не текстом статуса и не writer-ом.

`OK`, `NumFail`, `InputErr`, `CalcErr`, `FAIL` остаются примерами, а не закрытыми списками. Наличие `ExtUsed` само по себе не является поводом добавить новый локальный критерий. Семантику решателя и физической проверки сохранять централизованной.

## 2.5. Допустимое изменение общей геометрии

В объем задачи входит централизация одинаковых геометрических запросов во всех соответствующих потребителях проекта, а не только добавление нового пути для СП 35. Расчеты СП 35, СП 63 и остальные найденные потребители должны получать одинаковые пересечения, интервалы материала и результаты отсечения через общий геометрический контракт раздела 23.

Разрешено расширить подходящий существующий класс геометрии/геометрических характеристик либо выделить один общий компонент, если это лучше сохраняет ответственность классов. Его использование не должно зависеть от названия расчетного СП. Это изменение общего источника и вычисления геометрических результатов, а не изменение нормативных формул или алгоритма решения равновесия.

На старых входах с прежними источниками геометрии результаты сохраняются. Если пользователь добавил более точный контур или ранее отсутствующую пустоту, изменение геометрически зависимых величин допустимо и должно быть объяснимо новым входом и покрыто тестом. Нельзя обещать тождественные числа при изменившейся геометрии, равно как нельзя оправдывать этим постороннюю регрессию.

Централизовать именно совпадающие по смыслу операции. Различающиеся нормативные способы определения зоны и ее размеров остаются в соответствующих проверках. Существующий расчет механических характеристик и внутреннее устройство solver попутно не перерабатывать.

# 3. Настройки расчета трещин

Итоговый блок настроек расчета трещин должен быть **явно разделен на три подблока**.

```text
Crack Settings
├── Common
├── SP63
└── SP35
```

Это должно быть видно и архитектурно, и в пользовательском интерфейсе/таблице настроек.

## 3.1. Common

В общем подблоке находятся настройки, общие для ветки расчета трещин.

Обязательно:

| Настройка | Назначение |
|---|---|
| `Code / Standard` | выбор `SP63` / `SP35` |
| общие параметры результата | только действительно общие параметры |
| предельное раскрытие, если оно уже хранится как общий пользовательский параметр | использовать существующую архитектуру, не дублировать |

**Ключевое требование:** выбор `SP63 / SP35` должен находиться именно в общем подблоке.

Если в проекте уже существует общая настройка, семантически полностью совпадающая с одной из новых настроек СП 35, сначала оценить возможность ее переиспользования. Не создавать дубликат только из-за нового стандарта.

## 3.2. SP63

Подблок содержит существующие настройки методики СП 63.

Не менять уже работающую логику без необходимости.  
Существующие параметры вроде `TensionZoneMode`, `PsiMode` и другие настройки СП 63 должны остаться работоспособными.

Этот документ **не является ТЗ на рефакторинг алгоритма СП 63**.

## 3.3. SP35

Согласованные пользовательские настройки:

### `GroupGapTolerance`

Допуск объединения соседних стержней в одну группу по чистому зазору между поверхностями.

Базовое значение:

```text
GroupGapTolerance = 10 mm
```

### `RowTolerance`

Допуск объединения групп в один ряд по координате вдоль нормали к Н.О.

Базовое значение:

```text
RowTolerance = 50 mm
```

Это отдельная пользовательская настройка и не должна неявно подменяться общим `GeometryTolerance`.

### `RadiusDiameterMode`

Способ выбора диаметра $d_{\mathrm{ref}}$ при наличии нескольких фактических диаметров в рассматриваемой группе или опорном ряду.

Допустимые значения строго:

```text
Max
Min
Average
```

`AreaEquivalent` не использовать.

$$
d_{\mathrm{Max}}=\max(d_i)
$$

$$
d_{\mathrm{Min}}=\min(d_i)
$$

$$
d_{\mathrm{Average}}=\frac{1}{m}\sum_i d_i
$$

Если все стержни одного диаметра, все три режима дают одинаковое значение.

> `[NDM]` СП 35 и Методическое пособие не дают явного алгоритма выбора одного `d` для `r`, когда в рассматриваемой группе/ряду одновременно присутствуют разные диаметры. Поэтому выбор вынесен в пользовательскую настройку.

**Один и тот же `RadiusDiameterMode` должен применяться везде, где в алгоритме строится радиус взаимодействия $r$:**

- для боковых границ локальной области – по стержням якорной группы;
- для границы в сторону Н.О. – по стержням нормативного опорного ряда.

### `InteractionRadiusMode`

Пользователь выбирает нормативный вариант радиуса взаимодействия.

Допустимые значения:

```text
D3   → r = 3d
D5   → r = 5d
D6   → r = 6d
```

Базовое значение:

```text
InteractionRadiusMode = D6
```

В интерфейсе допустимо отображать просто `3d / 5d / 6d`.

Не вводить произвольный числовой коэффициент вместо нормативных вариантов без отдельного согласования.

Для выбранного режима:

$$
r=k_r d_{\mathrm{ref}},
\qquad
k_r\in\{3,5,6\}
$$

Выбранный `InteractionRadiusMode` применяется одинаково:

- при определении бокового радиуса вокруг якорной группы;
- при откладывании радиуса от опорного ряда в сторону Н.О.

В справке обязательно пояснить, для каких случаев п. 7.110 СП 35 устанавливает $3d$, $5d$ и $6d$.

### `RebarProfile`

Профиль арматуры для выбора нормативной формулы коэффициента $\psi$.

Допустимые значения:

```text
Periodic
Smooth
```

Базовое значение:

```text
RebarProfile = Periodic
```

То есть по умолчанию принимается **арматура периодического профиля**, а не гладкая.

Если в текущей архитектуре уже существует полностью эквивалентная настройка `RebarProfile`, ее следует переиспользовать, а не создавать вторую.

## 3.4. Единый блок настроек AutoCAD

Настройки AutoCAD оформить **одним общим верхнеуровневым блоком** с тремя подблоками:

```text
AutoCAD
├── Common
├── Import
└── Export
```

Визуальное оформление и логика группировки должны повторять уже существующие составные блоки на листе настроек, **например блок решателя**:

- общий заголовок;
- внутри визуально различимые подблоки;
- единый стиль подписей, объединений, отступов и разделителей;
- без создания отдельной разрозненной таблицы только для новых параметров.

Этот блок независим от `Crack Settings / Common / SP63 / SP35`: настройки трещин отвечают за расчетную методику, а `AutoCAD` — за обмен геометрией и результатами с AutoCAD.

### 3.4.1. `AutoCAD.Common`

В `Common` размещать параметры, которые имеют **общий семантический смысл и должны быть согласованы в обоих направлениях обмена**.

В первую очередь:

| Смысл настройки | Условное техническое имя | Начальное значение |
|---|---|---|
| Слой внешнего контура сечения | `SectionContourLayer` | Пусто |
| Слой контуров пустот | `OpeningContourLayer` | Пусто |

Если в текущем проекте уже существуют общие имена слоев для других сущностей, которые используются и импортом, и экспортом, оценить их перенос/объединение в этот же подблок, **но не проводить широкий несвязанный рефакторинг только ради косметики**.

Принцип:

> одна семантическая сущность → одно согласованное имя слоя → один источник настройки.

Не дублировать, например, `SectionContourLayer` отдельно в `Import` и `Export`, если импортируемый и экспортируемый внешний контур должны использовать один и тот же слой.

Пустое значение общей настройки слоя означает, что соответствующая опциональная семантика слоя пользователем не задана. Конкретное поведение при импорте/экспорте определяется соответствующим подблоком и существующей policy.

### 3.4.2. `AutoCAD.Import`

В `Import` оставлять **только настройки, влияющие именно на процесс чтения/валидации/создания модели из AutoCAD**, например:

- включение/отключение отдельных импортируемых сущностей, если такая настройка уже существует;
- импорт-специфичные допуски;
- поведение при отсутствующем/пустом слое;
- настройки выбора источника/объекта, которые не имеют смысла при экспорте;
- прочие уже существующие параметры импорта.

Новые `SectionContourLayer` и `OpeningContourLayer` **не должны дублироваться здесь**, если они размещены в `AutoCAD.Common`.

Импортер читает значения слоев из `AutoCAD.Common`.

### 3.4.3. `AutoCAD.Export`

В `Export` размещать **только экспорт-специфичные параметры**, включая:

| Настройка | Условное техническое имя | Начальное значение |
|---|---|---|
| Выгружать контур расчетной области трещин | `ExportCrackInteractionContour` | `False` / Выкл. |

Также здесь должны оставаться параметры, которые не влияют на расчетную модель и нужны только для оформления/вывода в AutoCAD, например:

- цвета линий;
- типы/веса линий;
- размеры текста;
- визуальные параметры аннотаций;
- опции выгрузки отдельных типов объектов;
- иные чисто экспортные свойства.

Не переносить такие визуальные параметры в `AutoCAD.Common`, если они не нужны импорту и не определяют общую семантику геометрии.

Переключатель `ExportCrackInteractionContour` является **универсальным для выбранной методики расчета нормальных трещин**.

При `Standard = SP35` он выгружает конечную область взаимодействия, фактически использованную для критического результата СП 35.

При `Standard = SP63` он выгружает конечную расчетную область бетона, фактически использованную текущей методикой СП 63 при определении ширины раскрытия трещин.

Переключатель влияет только на выгрузку сохраненной геометрии, но не на ее расчет, хранение, НДС, выбор стандарта или статусы. Начальное значение «Выкл.» сохраняет прежний состав экспорта.

Если в текущем проекте уже существует настройка `ExportSP35InteractionContour`, выполнить аккуратную миграцию/переименование в универсальную настройку без создания двух параллельных флагов.

### 3.4.4. Архитектурное требование к настройкам

Не должно появиться трех независимых источников истины для одного параметра.

Предпочтительная зависимость:

```text
AutoCAD.Common
   ├── semantic layer names / shared exchange semantics
   ↓
AutoCAD.Import
   └── import-only behavior

AutoCAD.Common
   ├── semantic layer names / shared exchange semantics
   ↓
AutoCAD.Export
   └── export-only behavior / visualization
```

Codex должен сначала изучить текущую архитектуру настроек и встроить эту структуру в существующий settings-контракт, а не создавать параллельную систему.


# 4. Предварительная обработка арматуры

Одним из первых этапов СП 35 после получения расчетного состояния необходимо сформировать **группы растянутых стержней**.

После формирования групп последующая топологическая работа ведется прежде всего с группами, но реальные стержни внутри группы не теряются.

## 4.1. Какие стержни участвуют

На вход топологического анализатора передаются арматурные элементы, пригодные для рассматриваемого расчета и находящиеся в растяжении согласно расчетному состоянию.

Для каждого исходного стержня должны быть доступны как минимум:

- `Id`;
- координаты центра `x, y`;
- номинальный диаметр `d`;
- площадь `As`;
- напряжение $\sigma_s$;
- деформация;
- модуль `Es`;
- при необходимости сведения о профиле арматуры; расчетная формула $\psi$ выбирается пользовательской настройкой `RebarProfile`;
- сведения, требуемые для исключения элементов, которые СП 35 не разрешает учитывать в `Rr`.

## 4.2. Критерий объединения в группу

Группы определяются **не только по математическому касанию**.

Для пары стержней `i`, `j`:

$$
L_{ij} = \sqrt{(x_i-x_j)^2+(y_i-y_j)^2}
$$

чистый зазор между поверхностями:

$$
gap_{ij} = L_{ij} - \frac{d_i+d_j}{2}
$$

Если

$$
gap_{ij} \le \mathrm{GroupGapTolerance},
$$

между стержнями создается связь.

Все стержни одной связной компоненты графа относятся к одной группе.

Пример:

```text
A -- B -- C
```

Если `A` связан с `B`, а `B` связан с `C`, все три принадлежат одной группе даже при отсутствии прямой связи `A-C`.

> `[NDM]` Ненулевой допуск является программным решением NDM. Таблица 7.26 СП 35 непосредственно описывает группы без просветов между стержнями. Это обязательно отметить в справке.

## 4.3. Исходная группа и фактически включенные стержни

После формирования:

- исходная связная группа сохраняется для построения боковых границ;
- после всех отсечений включаются только стержни, оси которых внутри или на границе конечной области;
- допускается включить часть исходной группы; β и n относятся к этой части;
- реальные диаметры и координаты каждого стержня внутри группы сохраняются;
- при вычислении $\sum \beta n d$ используются реальные диаметры стержней, а не условный единый диаметр группы.

## 4.4. Центр группы

Центр группы принимать как центр тяжести площадей стержней:

$$
x_g = \frac{\sum A_i x_i}{\sum A_i},
\qquad
y_g = \frac{\sum A_i y_i}{\sum A_i}
$$

Это особенно важно для групп с разными диаметрами.

Именно этот центр используется:

- для проверки попадания группы в локальный сегмент;
- для локальных координат;
- для определения принадлежности ряду;
- для поиска соседних групп.

## 4.5. Коэффициент β

Для обычных стержней:

| Размер группы | β |
|---:|---:|
| 1 | 1.00 |
| 2 | 0.85 |
| 3 | 0.75 |
| 4 и более | 0.75 |

Для размеров 1–3 значения следуют таблице 7.26 СП 35.

Для группы **более 3 стержней**:

$$
\boxed{\beta = 0.75}
$$

то есть использовать минимальный табличный коэффициент для обычной группы из трех стержней.

> `[NDM]` Распространение $\beta = 0.75$ на группы из 4 и более обычных стержней – программное допущение NDM и должно быть явно описано в справке.

# 5. Локальная система координат

Для общего случая с нейтральной осью расчет локальной геометрии вести в системе:

- `n` – нормаль к нейтральной оси;
- `t` – направление вдоль нейтральной оси.

Для каждой группы:

$$
n_g = \mathbf n \cdot \mathbf x_g,
\qquad
t_g = \mathbf t \cdot \mathbf x_g
$$

Направление `n` должно быть определено однозначно, с учетом стороны растяжения.

Не привязывать алгоритм к глобальным `X/Y`.

Это позволяет одинаково обрабатывать:

- `Mx`;
- `My`;
- `Mxy`;
- произвольный наклон Н.О.;
- повернутые и несимметричные сечения.

---

# 6. Определение рядов арматуры

Ряд определяется по координате **по нормали к Н.О.**, а не по совпадению стержней на одной нормали.

Группы могут быть смещены вдоль `t`.

Схема:

```text
        ●●●       ← ряд 3

   ●●             ← ряд 2

       ●●●         ← ряд 1
```

Это нормальная многорядная схема.

Группы относятся к одному ряду, если:

$$
|n_i-n_j|\le \mathrm{RowTolerance}
$$

Пользовательская настройка:

```text
RowTolerance = 50 mm
```

по умолчанию.

`RowTolerance` используется именно для распознавания одного ряда и не должен смешиваться с `GroupGapTolerance`, который отвечает за объединение стержней внутри одной группы.

# 7. Якорные группы и кандидаты на проверку

## 7.1. Основное принятое правило

**Якорной** считается растянутая группа, расположенная по наружному контуру армирования рассматриваемой растянутой стороны сечения.

Именно для якорной группы:

- строится самостоятельная локальная область взаимодействия;
- вправо и влево вдоль `t` откладываются боковые расстояния;
- ее растягивающее напряжение используется при вычислении собственного $a_{\mathrm{cr}}$;
- затем внутри ее локальной области учитываются второстепенные группы других рядов.

Если при расчете одной якорной группы в ее область взаимодействия попали другие группы по направлению к Н.О., эти группы являются **второстепенными рядами** данного локального расчета.

При надежно работающей фильтрации якорных групп такие второстепенные группы:

- участвуют в формировании рядов;
- участвуют в выборе опорного ряда;
- участвуют в $\sum \beta n d$, если попали в расчетную область;
- **не запускают собственный якорный расчет**, если они уже однозначно относятся к внутреннему ряду относительно наружного контура.

Если центр второстепенной группы лежит на границе соседнего локального участка, группа по принятому правилу NDM может полностью участвовать и в соседнем локальном расчете.

## 7.2. Как определять якорные группы

Сначала использовать уже имеющуюся в проекте информацию о геометрии, контуре и взаимном расположении арматуры.

Не создавать отдельный сложный геометрический классификатор только ради исключения лишних прогонов.

Предпочтительный результат:

```text
outer contour
────────────────────────
     ●       ●       ●       ← anchor groups

        ●       ●            ← secondary row

           ●                 ← secondary row
────────────────────────
```

То есть якорные группы – наружные группы растянутого армирования, от которых локальная зона развивается внутрь сечения в сторону Н.О.

## 7.3. Разрешенный fallback

Если надежное выделение только контурных групп:

- требует отдельной сложной новой подсистемы;
- плохо определяется для импортированной/дискретной геометрии;
- создает риск нестабильной классификации,

разрешается **не вводить специальный фильтр якорей**, а перебрать все растянутые группы как потенциальные якорные.

Это допустимый fallback NDM:

- он может дать лишние прогоны;
- внутренние группы могут дать близкие/дублирующие результаты;
- итоговый выбор выполняется по максимальному рассчитанному $a_{\mathrm{cr}}$;
- Codex не должен ради небольшой экономии прогонов усложнять архитектуру и плодить отдельные классы.

## 7.4. Расчет по якорям

Для каждой якорной группы `G_anchor`:

```text
G_anchor
   ↓
local segment
   ↓
secondary groups / rows
   ↓
Ar
   ↓
Rr
   ↓
ψ
   ↓
a_cr
```

После расчета всех якорей:

$$
a_{\mathrm{cr,final}}=\max(a_{\mathrm{cr},i})
$$

Сохраняется якорная группа, давшая максимум.

**Для разных типов геометрии сечения не создавать отдельные ветки алгоритма.** Один и тот же механизм применяется ко всем поддерживаемым и импортированным геометриям сечения.

# 8. Формирование локального участка по ширине

Локальный участок строится вокруг якорной группы `G_anchor`.

Боковое направление – `t`, то есть вдоль Н.О.

## 8.1. Радиус взаимодействия для боковой локализации

Для якорной группы определить $d_{\mathrm{ref,anchor}}$ по пользовательской настройке `RadiusDiameterMode`.

Затем определить боковой радиус по выбранному `InteractionRadiusMode`:

$$
r_{\mathrm{side}}=k_r d_{\mathrm{ref,anchor}},
\qquad
k_r\in\{3,5,6\}
$$

Здесь используется **тот же** `RadiusDiameterMode`, который затем применяется при определении $r$ от опорного ряда в сторону Н.О.

Это принято сознательно: одна и та же величина радиуса взаимодействия не должна определяться по разным правилам выбора диаметра в разных направлениях.

## 8.2. Соседние якорные группы

Для определения боковой ширины ориентироваться на ближайшие **якорные** группы в ряду рассматриваемой якорной группы.

Второстепенные группы более глубоких рядов не должны сами по себе делить боковой участок `G_anchor`; они проверяются на попадание уже после формирования локального сегмента.

Пусть расстояния по `t` между центром `G_anchor` и ближайшими соседними якорными группами своего ряда:

```text
sLeft
sRight
```

Тогда:

$$
l_{\mathrm{Left}}=
\min\left(
r_{\mathrm{side}},
\frac{s_{\mathrm{Left}}}{2}
\right)
$$

$$
l_{\mathrm{Right}}=
\min\left(
r_{\mathrm{side}},
\frac{s_{\mathrm{Right}}}{2}
\right)
$$

Если соседней якорной группы с одной стороны нет:

$$
l=r_{\mathrm{side}}
$$

с последующим ограничением фактической геометрией сечения.

Для равномерного ряда:

$$
b_{\mathrm{local}}
=
2\min\left(r_{\mathrm{side}},\frac{s}{2}\right)
=
\min(2r_{\mathrm{side}},s)
$$

> `[NDM]` Срединная граница между соседними якорными группами и ограничение боковой ширины величиной $r_{\mathrm{side}}$ являются принятой универсальной геометрической реализацией NDM.

# 9. Принадлежность второстепенных групп локальному участку

После построения боковых границ рассматриваются группы других рядов.

**Не требуется**, чтобы они лежали на одной нормали с `G_anchor`.

Правило:

$$
t_{\mathrm{Left}}\le t_g\le t_{\mathrm{Right}}
$$

При окончательном отборе каждого растянутого стержня его ось:

- находится внутри локальной зоны - стержень учитывается;
- лежит точно на границе - стержень учитывается;
- находится снаружи - стержень не учитывается.

Центр исходной группы не заменяет эту проверку и не может исключить стержень,
попавший в конечную область. Число стержней, β, сумма диаметров и расшифровка
рядов для конкретного кандидата используют один и тот же фактический состав.

Схема:

```text
|                         |
|            ●●●          |  secondary, входит
|                         |
|   ●●                    |  secondary, входит
|                         |
|        ●●●              |  anchor
|                         |
```

Если все стержни второстепенной группы находятся за боковой границей:

```text
|                         |
|                             ●●●   не входит
|                         |
|   ●●                    |         входит
|                         |
|        ●●●              |         anchor
|                         |
```

Если ось стержня лежит ровно на общей границе двух соседних локальных участков,
этот стержень учитывается в обоих участках. Остальной состав исходной группы
проверяется отдельно по фактическому положению каждого стержня.

## 9.1. Дополнительное ограничение при наличии opening

Попадание по координате `t` является предварительным отбором, а не достаточным условием включения. До назначения опорного ряда исключить группы за пустотой, недоступные из рассматриваемой локальной стенки по направлению нормали. Группа в противоположной стенке пустотелого сечения не должна попадать в знаменатель только потому, что ее центр проецируется в ту же полосу.

После окончательного построения области ось каждого растянутого стержня
проверяется относительно фактической локальной области бетона, а не ее
ограничивающего прямоугольника. Учитывается вошедшая часть каждой исходной
группы. Арматура в полости или за первым разрывом бетона не включается.

Для самой входной модели геометрически невозможные положения арматуры обрабатываются существующей валидацией. Не создавать отдельные статусы и не пытаться исправлять их в writer-е.

# 10. Выбор ряда и радиуса в сторону нейтральной оси

После определения всех групп, попавших в локальный участок:

1. предварительно проверить принадлежность локальной бетонной стенке, исключив группы за opening, затем сгруппировать допустимые группы в ряды по `n` с учетом `RowTolerance`;
2. определить крайний ряд, ближайший к Н.О.;
3. проверить нормативное правило площади крайнего ряда.

`[SP35]` Если в крайнем ряду установлено менее половины площади арматуры по отношению к площади арматуры **в каждом из остальных рядов**, $r$ следует откладывать от предпоследнего полного ряда.

Площадь ряда считать по реальным площадям всех вошедших в локальный участок групп этого ряда.

После выбора нормативного опорного ряда определить $d_{\mathrm{ref,row}}$ по **той же пользовательской настройке `RadiusDiameterMode`**, что использовалась для бокового радиуса.

Если в опорном ряду несколько различных диаметров:

- `Max` → максимум всех фактических $d_i$ в этом ряду;
- `Min` → минимум;
- `Average` → среднее арифметическое всех фактических $d_i$ в этом ряду.

Далее использовать тот же `InteractionRadiusMode`:

$$
r_{\mathrm{NA}}=k_r d_{\mathrm{ref,row}},
\qquad
k_r\in\{3,5,6\}
$$

и отложить $r_{\mathrm{NA}}$ **в сторону Н.О.**

Зона не должна пересекать Н.О.

Таким образом:

- боковая граница использует $r_{\mathrm{side}}$ по диаметрам якорной группы;
- внутренняя граница использует $r_{\mathrm{NA}}$ по диаметрам опорного ряда;
- режим выбора диаметра и нормативный множитель $k_r$ в обоих случаях одинаковы.


# 10A. Общий движок расчетной области для СП 35 и СП 63

## 10A.1. Область применения общего геометрического движка

В текущей задаче новый геометрический класс подключается **только к расчетам трещин**, которым нужна геометрия расчетной области.

В первую очередь это:

- нормальные трещины по СП 63;
- нормальные трещины по СП 35;
- другие существующие классы расчета трещин — только если они используют те же операции построения/пересечения области и такое подключение действительно требуется текущей архитектурой.

**Расчет устойчивости не переводить на новый geometry engine.**

Для устойчивости сохранить существующую логику работы по дискретной сетке и существующий pipeline без изменения алгоритма, данных и результатов.

Также без отдельной необходимости не переводить на новый класс:

- расчеты прочности/несущей способности;
- поиск равновесия;
- расчет геометрических характеристик;
- другие независимые расчетные модули.

Новый класс проектируется универсально с точки зрения геометрии, но **его фактический набор потребителей в этой задаче ограничен подсистемой трещин**.

Если существующий низкоуровневый геометрический helper уже используется устойчивостью или другим незатронутым расчетом, не менять его публичный контракт/поведение ради этой задачи. При необходимости новый crack-geometry class может использовать тот же низкоуровневый primitive либо совместимую делегацию, но устойчивость должна остаться функционально прежней.


Геометрическое построение области бетона, участвующей в расчете ширины раскрытия трещин, должно иметь **одну общую реализацию** для СП 35 и СП 63.

Это не означает, что нормативные правила двух СП становятся одинаковыми.

Каждая методика сама определяет свои расчетные параметры:

- направление/Н.О.;
- нижнюю/внутреннюю ограничивающую границу;
- локальную ширину или иной нормативный предел;
- режим полной/эффективной растянутой зоны;
- другие специфичные для стандарта параметры.

После этого обе методики передают в **один общий геометрический движок области** геометрический запрос вида:

```text
Section concrete domain
+ standard-specific clipping/boundary request
→ final calculation region
→ Area
→ outer loops + inner loops
```

Общий движок должен:

1. использовать достоверные outer/opening, если они известны;
2. при отсутствии достоверного внешнего контура работать по дискретной бетонной геометрии;
3. учитывать opening/пустоты;
4. возвращать **конечную геометрию области**, а не только число площади;
5. вычислять площадь именно по этой возвращенной геометрии;
6. отдавать тот же объект/снимок writer-у, схеме и AutoCAD-экспорту.

Ключевое требование:

> **Число площади, использованное в нормативной формуле, и геометрия, экспортируемая в AutoCAD, должны представлять одну и ту же область.**

Не допускаются две независимые версии:

```text
AreaForCalculation
AreaForDrawing
```

если они строятся разными алгоритмами.

Допустимо одно вычисление:

```text
CrackInteractionRegion.Geometry
CrackInteractionRegion.Area
```

где `Area` вычислена из `Geometry`.

Для СП 35 сохраняются его правила якорной группы, рядов, $r$ и выбора критического результата.

Для СП 63 сохраняются его действующие нормативные правила (`TensionZoneMode`, эффективная/полная зона и т.д.). Рефакторинг должен заменить только дублирующую геометрическую механику построения/обрезки области, не меняя нормативную формулу СП 63.


# 11. Площадь взаимодействия Ar: единый геометрический движок без контрольной аппроксимации

## 11.1. Главный принцип

В рамках этой реализации **один общий геометрический класс/движок используется только расчетами трещин**, которым требуется геометрическая область бетона. Сам класс при этом остается независимым от конкретного СП.

Никакой отдельной геометрической ветки для СП 35 или СП 63 быть не должно. **Устойчивость, прочность и другие расчетные подсистемы в эту миграцию не включать.**

Расчетный модуль стандарта передает только геометрические ограничения:

- направление;
- Н.О. или другую ограничивающую линию;
- нижнюю/внутреннюю границу;
- боковые границы/локальную ширину, если они нужны методике;
- режим полной/эффективной зоны;
- другие чисто геометрические ограничения.

Общий класс возвращает:

```text
FinalRegion.Geometry
FinalRegion.Area
FinalRegion.OuterLoops
FinalRegion.InnerLoops
```

и не знает, какой СП вызвал его.

## 11.2. Если достоверный контур известен

Если внешний контур и/или `opening` известны из штатного генератора геометрии, валидированного импорта AutoCAD или другого надежного источника проекта, использовать их **фактическую геометрию напрямую**.

В этом режиме:

- не строить аппроксимации;
- не заменять дуги/скругления/ломаные искусственными контрольными точками;
- выполнять clipping по фактическому outer contour;
- учитывать все известные `opening` как реальные внутренние границы;
- если область входит в `opening`, обрезать ее по фактической грани пустоты;
- не продолжать область через пустоту к противоположной стенке.

## 11.3. Если внешний контур неизвестен

Если явного достоверного outer contour нет, общий класс должен **восстановить фактическую границу по дискретным бетонным элементам**.

Базовый принцип:

1. получить ребра/границы бетонных элементов;
2. исключить внутренние общие ребра соседних бетонных элементов;
3. оставшиеся граничные сегменты собрать в замкнутые цепочки;
4. классифицировать outer loops и inner/opening loops;
5. определить связанную бетонную область;
6. выполнить clipping этой области по переданным расчетным ограничениям;
7. вернуть конечную замкнутую геометрию и площадь.

На грубой сетке итоговый контур может быть ступенчатым. Это нормально.

Именно эта фактическая граница дискретной бетонной области участвует в вычислении площади, сохраняется в результате, используется схемой и экспортируется в AutoCAD.

Не сглаживать ее только ради визуальной красоты, если это изменяет расчетную площадь.

## 11.4. Пустоты при отсутствии явных opening

Если `opening` не заданы явно, но пустота реально присутствует в дискретной бетонной геометрии, общий движок должен определить ее как внутреннюю границу по граничным ребрам бетонных элементов.

Если пустота:

- полностью лежит внутри расчетной области — она формирует отдельный inner loop;
- пересекает границу расчетной зоны — она формирует вырез/изменение outer loop;
- находится за первой стенкой бетона — противоположная стенка не считается продолжением той же локальной области автоматически.

Если пустота не отражена ни явным контуром, ни дискретной геометрией, программа не должна угадывать ее существование.

## 11.5. Нейтральная линия и другие ограничения

Н.О. и другие линии передаются в общий класс как обычные геометрические ограничения.

Общий класс выполняет пересечения, clipping по полуплоскости, выбор нужной стороны, учет outer/opening и возврат конечной топологии.

Он **не вычисляет Н.О.**, не вызывает solver и не принимает нормативных решений.

## 11.6. Полное отсутствие специальной аппроксимации контура

Не использовать отдельную логику контрольных точек/нормалей для восстановления неизвестного контура.

При неизвестном контуре единственный fallback — фактическая топология дискретных бетонных элементов.

# 11.7. Площадь, внутренние кольца и компоненты

Финальная область должна быть представима как одна или несколько замкнутых компонент:

```text
outer loop(s)
- inner opening loop(s)
```

Все outer/inner loops должны быть замкнутыми.

Площадь, используемая в расчете:

$$
A=
\sum A_{\mathrm{outer}}
-
\sum A_{\mathrm{opening}}
$$

должна вычисляться по **тем же самым кольцам**, которые сохраняются и затем могут быть экспортированы.

Если opening целиком находится внутри области, он экспортируется отдельной замкнутой внутренней полилинией.

Если opening пересекает внешнюю границу расчетной зоны, он формирует вырез/изменение наружного контура по корректной топологии; не создавать фиктивное внутреннее кольцо там, где геометрически уже нет замкнутой дырки.


Для явной геометрии бетонная область описывается как:

$$
\Omega_c=
\left(\bigcup_i\Omega_{\mathrm{outer},i}\right)
\setminus
\left(\bigcup_j\Omega_{\mathrm{opening},j}\right)
$$

Локальный результат должен удовлетворять:

$$
\Omega_{A_r}\subseteq\Omega_c\cap\Omega_{\mathrm{tension}}
$$

$$
\Omega_{A_r}\cap\Omega_{\mathrm{opening}}=\varnothing
$$

и правилу локального бетонного интервала без перехода через полость. Одного булева вычитания пустоты недостаточно, если после него ошибочно сохранилась противоположная стенка, до которой алгоритм «перепрыгнул».

Площадь определяется по итоговой геометрии, а не по первоначальному прямоугольнику/ломаной до обрезки:

$$
A_r=\operatorname{Area}(\Omega_{A_r})
$$

Сохранять все необходимые внешние компоненты, внутренние кольца и их принадлежность. Если итог нельзя представить одним простым полигоном, не сшивать его искусственными отрезками через пустоту.

В экспорте, аннотации и численном результате должна использоваться одна и та же итоговая геометрия. Ее площадь обязана совпадать с сохраненным $A_r$ в пределах принятой точности геометрических операций.

## 11.8. Проверка принадлежности групп после геометрической обрезки

Предварительный отбор внутренних рядов выполняется по ширине и доступному локальному бетону до выбора опорного ряда. После обрезки области повторно проверить принадлежность групп по центру итоговой области. Если предварительная выборка и итог расходятся, нельзя оставить в знаменателе удаленную группу. Устранить несогласованность геометрическим отбором/локальным пересмотром состава, без вызова solver и без поиска НДС.

# 12. Центральное растяжение

Для **центрального растяжения** не применять локальный сегмент вокруг отдельной группы.

`[SP35]`

$$
\boxed{A_r = A_{\mathrm{section}}}
$$

то есть зона взаимодействия принимается равной всей площади сечения.

В этом режиме:

- не строить искусственное направление от ЦТ к выбранной группе;
- не ограничивать `Ar` локальной шириной `2r`;
- использовать всю фактическую площадь бетона **за вычетом всех opening**, а не площадь внешней оболочки. Набор внешних колец и пустот сохраняется и доступен экспорту. Локальное ограничение одной стенкой здесь не заменяет правило всей площади сечения.

Для выбора расчетного напряжения использовать наиболее растянутое фактическое значение $\sigma_s$. При практически одинаковых значениях допускается выбрать любой из равных максимумов.

# 13. Сумма βnd

Для конкретного локального расчета в знаменатель входят все группы, которые приняты принадлежащими итоговой зоне взаимодействия.

Удобная программная форма:

$$
\sum \beta n d
=
\sum_{groups\,g}
\left(
\beta_g \sum_{i \in g} d_i
\right)
$$

Таким образом `n` не теряется:

- для одинаковых диаметров $\sum_i d_i = nd$;
- для разных диаметров используются реальные `d_i`.

Пример:

группа из трех `Ø32 + Ø25 + Ø20`:

$$
0.75(32+25+20)
$$

группа из двух `Ø22 + Ø20`:

$$
0.85(22+20)
$$

группа из трех `Ø16`:

$$
0.75(16+16+16)
$$

Не заменять реальные диаметры в $\sum \beta n d$ диаметром `d_ref`.

`d_ref` используется только там, где требуется построить конкретный нормативный `r`.

# 14. Расчет Rr, ψ и a_cr

После определения `Ar`:

$$
R_r=\frac{A_r}{\sum \beta n d}
$$

Единицы контролировать явно.

Рекомендуемый внутренний подход:

- геометрию и площади хранить в базовых единицах проекта;
- перед нормативной формулой $\psi$ явно переводить $R_r$ в сантиметры, поскольку формулы СП 35 сформулированы для $R_r$ в см;
- не допускать скрытых смешений мм/см.

Формула $\psi$ выбирается пользовательской настройкой `RebarProfile`.

Для:

```text
RebarProfile = Periodic
```

используется:

$$
\psi=1.5\sqrt{R_r}
$$

Для:

```text
RebarProfile = Smooth
```

используется:

$$
\psi=0.35R_r
$$

По умолчанию:

```text
RebarProfile = Periodic
```

Итоговая ширина раскрытия считается по формуле СП 35 с фактическим растягивающим напряжением якорной группы и соответствующим $E_s$.

Если в якорной группе несколько стержней и из-за пространственного разнесения их напряжения различаются, для данного якорного расчета использовать максимальное растягивающее напряжение среди стержней якорной группы:

$$
\sigma_{s,\mathrm{anchor}}
=
\max_{i\in G_{\mathrm{anchor}}}(\sigma_{s,i})
$$

Второстепенные группы влияют на геометрию `Ar`, выбор ряда и $\sum\beta nd$, но их напряжения не подменяют напряжение текущей якорной группы.

# 15. Выбор максимального результата

Для всех рассчитанных якорных групп сформировать результаты:

```text
AnchorResult[1]
AnchorResult[2]
...
AnchorResult[n]
```

Если включен разрешенный fallback с перебором всех растянутых групп, массив строится по всем таким группам.

Итог:

$$
\mathrm{CriticalResult}
=
\operatorname*{arg\,max}_i
\left(
a_{\mathrm{cr},i}
\right)
$$

Финальный результат должен ссылаться на конкретный `CriticalAnchorGroupId`.

Внутренние/второстепенные группы сохраняются в диагностике критической зоны как `IncludedGroupIds`, но не подменяют идентификатор якорной группы.

# 16. Сохранение критической области как результата и геометрической аннотации

## 16.1. Хранить саму использованную область

Для расчета нормальных трещин необходимо сохранять не только численную площадь, но и **конечную геометрию, по которой эта площадь рассчитана**. Для СП 35 это геометрия критической группы; для СП 63 — геометрия расчетной зоны, фактически использованной выбранной методикой: после ограничения Н.О., радиусом, наружными границами и opening.

Результат должен быть доступен после завершения расчета без повторного получения НДС, группировки или геометрического расчета. Переключатель экспорта не влияет на факт хранения результата.

Минимальная смысловая структура, адаптируемая к существующим типам:

```text
CriticalInteractionZone
    Result / combination / state identity
    Section / geometry revision
    AnchorGroupId
    Components / outer loops / opening loops
    Area
    Geometry source and boundary provenance
    IncludedGroupIds / SecondaryGroupIds / IncludedRowIds
    ReferenceRowId
    GroupGapTolerance / RowTolerance
    RadiusDiameterMode / InteractionRadiusMode / RebarProfile
    dRefSide / dRefRow / rSide / rNA
    LocalAxisN / LocalAxisT / NeutralAxisData
    Units / model coordinate system
    Existing availability / actuality metadata
```

Это не перечень обязательных новых классов или новый enum статусов. Использовать фактические носители результата и геометрии проекта.

## 16.2. Переиспользовать существующие аннотации

Предпочтительно хранить/сериализовать эту геометрию как семантическую аннотацию в существующей инфраструктуре, где уже передаются контуры сечения и другие геометрические объекты.

В первую очередь найти текущую таблицу/контракт аннотаций, в том числе `rngNDMSectionAnnotations`, **если этот диапазон сохранен в новой архитектуре**, и соответствующие builder/reader/writer/plotter. Это ориентир для поиска, а не указание создать диапазон со старым именем.

Добавить универсальный смысловой тип/роль вроде «расчетная область нормальных трещин» / `CrackInteractionRegion` в существующий контракт либо подходящее расширение уже имеющегося типа. Обязательно хранить признак используемого стандарта (`SP63` / `SP35`). Обязательно хранить идентификатор владельца расчета/сочетания и связь с критической группой.

Нельзя маркировать область $A_r$ как обычный внешний контур сечения или как `opening`: она не должна случайно менять расчетную геометрию модели.

## 16.3. Одно геометрическое содержание, разные потребители

Расчетный результат владеет используемым геометрическим снимком или ссылкой на неизменяемые данные существующей модели. Аннотация является его согласованным представлением для хранения/схемы/экспорта. Не создавать две независимо рассчитываемые области, одна «для числа», другая «для картинки».

Если текущая таблица аннотаций предназначена только для визуализации и не хранит топологию/координаты модели с нужной точностью, одного такого представления недостаточно для расчетной геометрии. Сохранить корректный объект в текущем result/geometry-контракте и сериализовать его штатным механизмом, не заставляя расчет читать экранную таблицу.

В таблице/аннотации сохранять координаты модели, а не пиксели или координаты после масштабирования схемы. Все кольца, компоненты и пустоты должны переживать сериализацию/чтение.

## 16.4. Срок жизни, актуальность, повторный запуск

При повторном расчете заменить аннотации именно соответствующего результата, не удаляя контур сечения, opening, арматуру и чужие расчетные аннотации. Не накапливать наложенные копии.

Если новый расчет не дал области, устаревшая область от предыдущего запуска не должна выдаваться за текущую. Использовать существующий механизм сброса/актуальности результатов. Аналогично реагировать на изменение сечения, пустот, арматуры, сочетания и настроек построения.

В пакетном расчете результат относится к конкретному сочетанию. Не экспортировать «последний глобальный контур» вместо области выбранного сочетания и выбранного стандарта.

## 16.5. Экспорт входит в текущую реализацию

# 18. Подробная таблица результатов – новая шапка и правила вывода

## 18.1. Скриншоты задают относительную компоновку, а не абсолютные адреса

В папке задания лежат три изображения с актуальной шапкой.

Codex должен использовать их как эталон:

- порядка блоков;
- относительных ширин;
- объединений ячеек;
- актуальных названий;
- пустых разделительных столбцов.

**Абсолютное положение на листе со скриншотов не копировать.**

Шапка, как и в существующей реализации, должна быть привязана к именованному диапазону:

```text
rngCrackSummaryAnchor
```

`rngCrackSummaryAnchor` – исходная точка позиционирования всей шапки и данных подробного расчета трещин.

Все блоки должны размещаться через **относительные смещения от `rngCrackSummaryAnchor`**, а не через жестко заданные адреса вроде `A:BT`.

Скриншоты показывают только пример того, где этот якорь оказался на конкретном листе.

Если `rngCrackSummaryAnchor` является многоячейчным диапазоном, использовать ту anchor-точку/верхнюю левую ячейку, которую уже использует существующий код проекта. Не менять сложившуюся семантику именованного диапазона.

Если фактический шаблон книги уже обновлен пользователем, **не перерисовывать его поверх существующей шапки без необходимости**. Необходимо прежде всего корректно привязать запись результатов к структуре от `rngCrackSummaryAnchor`.

Предпочитать существующий механизм относительных смещений, именованных диапазонов, заголовков или метаданных. Не вводить новые абсолютные номера столбцов.

### Относительный порядок блоков

## 18.3. Блок «Начало трещинообразования»

Актуальная структура со скриншота:

### Осевое растяжение

```text
A_red, m2
R_bt,ser, MPa
N_crc, tf
λ_crc
```

### Изгиб N + M

```text
Method
N_crc, tf
Mxy_crc, tf*m
λ_crc
```

### PreCrackState (до трещины)

```text
ε_bc
ε_bt
равновесие
```

Поле `равновесие` выводится через **существующую централизованную систему статусов** проекта.

Наиболее типичные значения в штатной ситуации:

```text
OK
NumFail
InputErr
CalcErr
```

Это **не жесткий список допустимых статусов** и не основание менять внутренний статус решателя. Writer остается пассивным: получает внутренний результат и выводит внешний статус через уже существующую централизованную policy/mapper-логику проекта.

В необычных, но формально допустимых исходных данных возможны и другие статусы, предусмотренные общей системой. Например, если пользователь задаст очень большую предельную деформацию бетона при растяжении, согласованную с диаграммой, точка трещинообразования теоретически может оказаться за физической областью диаграммы бетона при сжатии; тогда возможен статус вроде `FAIL`, если именно так это состояние классифицирует общая policy.

Для `PreCrackState`:

- `ε_bc` выводить фактически получившийся;
- `ε_bt` **всегда выводить**, потому что состояние до образования трещины рассчитывается с растянутым бетоном;
- не подменять деформации нормативными предельными значениями, если таблица предназначена для фактически найденного состояния.

### PostCrackState (после трещины)

```text
ε_bc
ε_bt
равновесие
```

Поле `равновесие` также выводится через **общую централизованную status-policy** проекта.

Наиболее вероятные значения в обычных расчетах:

```text
OK
NumFail
InputErr
CalcErr
```

Но это не закрытый набор и не локальное ограничение для `PostCrackState`. Любой внешний статус должен получаться тем же централизованным путем, что и для остальных расчетных состояний.

Для `PostCrackState`:

- `ε_bc` выводить фактически получившийся;
- `ε_bt` выводить только если растянутый бетон активен в соответствующем расчетном состоянии;
- если растяжение бетона отключено, ячейку `ε_bt` оставлять пустой;
- правила вывода деформаций должны быть теми же, что уже используются в подробном блоке расчета несущей способности.

### равновесное состояние при заданных нагрузках

```text
state
ε_bc
ε_bt
ExtUsed
статус
```

Поле `статус` выводится **без отдельной логики для трещин СП 35**, через существующий централизованный механизм преобразования внутреннего результата во внешний статус.

В обычных ситуациях здесь наиболее вероятны:

```text
OK
NumFail
InputErr
CalcErr
FAIL
```

но это **не жесткое ограничение**. Теоретически допустим любой статус, который общая система проекта корректно выводит для данного внутреннего результата решения.

Writer не должен переопределять статус, подгонять внутренний результат под ожидаемый набор, иметь отдельную ветку формирования статусов только для трещин или дублировать существующую policy/mapper-логику.

Решение о возможности продолжать расчет ширины трещин должно использовать **существующую централизованную семантику пригодности состояния**. Если текущая архитектура уже умеет определять, можно ли продолжать расчет после данного результата/статуса, необходимо переиспользовать именно этот механизм, а не проверять локальный hard-coded список.

Типичный смысл `OK`, `NumFail`, `InputErr`, `CalcErr`, `FAIL` сохраняется таким, как он уже определен в общей системе проекта. Например, если `FAIL` в текущей архитектуре означает найденное равновесие за физической областью диаграмм (`ExtUsed`), дальнейший расчет трещин не должен продолжаться. Но это должно вытекать из общей policy, а не из отдельной ветки writer-а.

Для этого блока:

- `ε_bc` выводить фактический;
- `ε_bt` оставлять пустым, если растянутый бетон отключен;
- `ExtUsed` выводить существующим в проекте способом, не менять его формат без необходимости;
- семантику поля `state` сохранить из текущей архитектуры.

Перед любыми изменениями, связанными со статусами, Codex должен найти существующую централизованную реализацию status-policy/mapper. В рамках этой задачи **не менять ее без реальной необходимости**. Writer-ы должны оставаться пассивными: получать уже сформированный внутренний результат и выводить внешний статус тем же способом, что и остальные части программы.

**После всего блока «Начало трещинообразования» обязательно оставить один пустой столбец-разделитель перед блоком нормальных трещин по СП 35.**

## 18.4. Блок «нормальные трещины по СП 35»

### Коэффициент раскрытия трещин

```text
A_r
β
n
d
R_r
ψ
```

### Напряжения

```text
rebars
n_rebars
σ_s
E_s
```

### ширина раскрытия нормальных трещин

```text
a_crc
a_crc,ult
a_crc,ult / a_crc
статус
```

Типографику индексов и точное оформление брать со скриншота.

Этот блок должен заполняться **по критическому результату СП 35**, то есть по якорной группе/локальной области, давшей максимальное $a_{\mathrm{cr}}$.

Важное ограничение:

> Значения `β`, `n`, `d`, `rebars` являются обязательной подробной расшифровкой **всех рядов, участвовавших в критическом расчете СП 35**. Они не должны выводиться одним агрегированным значением по якорной группе.

Формат вывода должен быть **обязательно построчным по расчетным рядам в одной ячейке**, как на эталонном скриншоте пользователя.

Пример:

```text
β       1 ряд: 0.75 | 2 ряд: 0.85 | 3 ряд: 1.00
n       1 ряд: 3    | 2 ряд: 2    | 3 ряд: 1
d       1 ряд: 32, 32, 32 | 2 ряд: 25, 20 | 3 ряд: 12
rebars  1 ряд: R1, R2, R3 | 2 ряд: R6, R7 | 3 ряд: R12
```

Общие правила форматирования:

- сегменты рядов разделяются строкой ` | `;
- каждый сегмент начинается строго в виде `N ряд: ...`;
- нумерация рядов должна соответствовать внутреннему расчетному порядку рядов, используемому для критической области;
- внутри `d` перечисляются **реальные номинальные диаметры всех стержней данного ряда**, через `, `;
- внутри `rebars` перечисляются идентификаторы фактически вошедших стержней данного ряда через `, `;
- `n` – число фактически вошедших стержней данного ряда;
- `β` – коэффициент, примененный к соответствующей группе/ряду в расчетной сумме;
- не заменять список диаметров одним `d_ref`;
- не заменять список `rebars` только идентификатором якорной группы.

Если в одном расчетном ряду оказалось **несколько отдельных групп** с различными `β`, нельзя молча сворачивать их в один коэффициент. В таком случае сохранить явную расшифровку внутри сегмента ряда в стабильном порядке групп, например:

```text
β  2 ряд: 0.85, 1.00
```

и аналогично обеспечить однозначное соответствие `n`, `d` и `rebars` этим группам. Если текущая структура результата позволяет хранить группы отдельно, форматировать строку уже на уровне writer, не теряя исходную топологию.

Внутренний расчет $R_r$ при этом всегда использует полную согласованную сумму:

$$
\sum \beta n d
$$

по всем фактически включенным группам всех рядов критической области.

Остальные поля:

- `n_rebars` – общее число фактических стержней, вошедших в критическую расчетную область;
- `σ_s` – расчетное напряжение критической якорной группы;
- `E_s` – модуль арматуры, используемый в формуле;
- `A_r`, `R_r`, `ψ`, $a_{\mathrm{crc}}$ – итоговые значения критической области.

При смешанных модулях/типах арматуры не изобретать усреднение `E_s` без нормативного/архитектурного основания. Сначала использовать уже существующие ограничения модели и фактический расчетный стержень/группу.

### Статус блока СП 35

Использовать общую систему статусов проекта и существующий подход блока СП 63.

Не выводить фиктивные численные значения, если существующий координатор/контракт пригодности входов не разрешил этот расчет. Перечни строковых статусов в этом MD являются примерами. Writer и экспортер не вводят локальных списков разрешенных статусов и не переопределяют решение общей policy.

Завершенный расчет ширины, который не выполнил проверку допустимого раскрытия, не равен отсутствию результата: его корректная область $A_r$ сохраняется и может экспортироваться. Отличать невыполнение проверки от невозможности рассчитать область.

При превышении допустимого раскрытия использовать существующую семантику успешности/невыполнения проверки, согласованную с соседним блоком СП 63. Не вводить новый отдельный словарь статусов только для СП 35.

## 18.5. Один пустой столбец-разделитель после СП 35

Один разделительный столбец должен оставаться визуально пустым и выполнять роль разделителя между СП 35 и СП 63.

Не использовать его для скрытых дополнительных результатов без отдельного согласования.

## 18.6. Существующий блок «нормальные трещины по СП 63»

Это **существующий работающий блок**.

Требования:

1. содержимое блока СП 63 по расчетной логике не менять;
2. не переименовывать его внутренние поля произвольно;
3. не менять формулы СП 63; на неизмененных входах и прежнем источнике геометрии сохранять результаты. Разрешенное использование достоверных контуров/opening вместо fallback является отдельным изменением входной геометрии, описанным в общем разделе геометрии;
4. в части таблицы адаптировать:
   - новое положение;
   - новые соседние пустые столбцы;
   - обновленный общий layout;
5. точные заголовки брать со второго скриншота;
6. использовать существующие writer/result классы, если они уже есть.

Визуальная перестановка блока не является основанием для рефакторинга алгоритма СП 63.

## 18.7. Пустой разделительный столбец после СП 63

Оставить пустым согласно скриншоту.

## 18.8. Блок «продольные трещины»

Блок сохраняется согласно третьему скриншоту.

Актуальные поля:

```text
σ_b,max
R_bm02
R_bm02 / σ_b
статус
```

Точную запись индексов/символов брать с изображения.

Не менять существующую расчетную логику продольных трещин в рамках этой задачи, кроме необходимой привязки к новой позиции таблицы.

## 18.9. Общий статус и ResultComment

Не создавать второй параллельный механизм агрегации статусов.

Найти существующую логику:

- `общий статус`;
- `ResultComment`;
- статус трещинообразования;
- статус выбранного стандарта нормальных трещин;
- статус продольных трещин.

Расширить ее минимально, чтобы СП 35 участвовал в общей оценке так же архитектурно последовательно, как существующие проверки.

Если расчет по СП 35 не выбран в настройках, его блок должен оставаться неактивным/пустым в соответствии с существующим поведением альтернативных методов, а не выдавать фиктивный `OK`.

## 18.10. Порядок останова ветки трещин

Ветка не должна останавливаться по локально зашитому списку строковых статусов.

Рекомендуемая последовательность:

```text
1. Получить входные данные и расчетные состояния.
2. Для PreCrackState, PostCrackState и состояния при заданных нагрузках
   использовать существующую централизованную policy/семантику результата:
   допускается ли продолжение расчета?
3. Если общая policy считает состояние непригодным для дальнейшего расчета,
   остановить ветку и не формировать фиктивные численные результаты трещин.
4. Если состояние пригодно:
   SP63 → существующий алгоритм;
   SP35 → новый алгоритм этого MD.
5. Выполнить продольные трещины, если они включены/применимы
   по существующей архитектуре.
```

Примеры статусов не являются условиями ветвления. Возможность продолжения определяет существующий координатор на основе внутреннего результата и контракта пригодности состояния. Но конкретное решение должно приниматься общей централизованной логикой проекта, а не новым `Select Case`/`If` внутри writer-а или ветки СП 35.

Не запускать геометрически дорогой поиск областей СП 35, если существующая policy уже определила, что состояние непригодно для дальнейшего расчета.

# 19. Обязательное одновременное создание пользовательской справки

Реализация расчета по СП 35 считается незавершенной, если одновременно с кодом не создана или не обновлена пользовательская справка.

## 19.1. Структура справки – строго по образцу раздела устойчивости

Перед редактированием справки Codex обязан найти существующий **раздел устойчивости** и использовать его как основной визуальный и структурный образец.

Расчет раскрытия трещин должен находиться **под одним общим заголовком и внутри одной общей скрываемой/раскрываемой группы**, как это сделано для устойчивости.

Внутри этой общей группы последовательно располагаются:

```text
Расчет ширины раскрытия трещин
└── одна скрываемая группа
    ├── СП 63
    └── СП 35
```

Предпочтительный порядок:

1. сначала существующая справка по СП 63;
2. затем новая справка по СП 35.

Не создавать две независимые верхнеуровневые скрываемые группы, если раздел устойчивости организован единым контейнером.

## 19.2. Последовательность изложения

Каждая нормативная методика должна объясняться **последовательно, от основной формулы к ее составляющим**, по аналогии с другими расчетными разделами NDM.

Для СП 35 структура должна быть примерно такой:

1. общая формула ширины раскрытия трещины $a_{\mathrm{cr}}$;
2. расшифровка $\sigma_s$ и $E_s$;
3. коэффициент $\psi$;
4. формула $R_r$;
5. площадь взаимодействия $A_r$;
6. сумма $\sum\beta nd$;
7. группы арматуры и коэффициент $\beta$;
8. выбор якорной группы;
9. локальная система `n/t`;
10. боковые границы;
11. второстепенные ряды;
12. выбор опорного ряда;
13. $d_{\mathrm{ref}}$ и настройки `RadiusDiameterMode`;
14. $r$ и настройка `InteractionRadiusMode`;
15. точное использование известного контура либо восстановление замкнутых границ по бетонным элементам при неизвестном контуре;
16. центральное растяжение;
17. выбор максимального результата;
18. сохраняемый критический контур;
19. настройки и диагностический результат.

Не начинать справку с частного алгоритма группировки или геометрии, не показав сначала общую расчетную формулу и смысл ее составляющих.

## 19.3. Что обязательно должно быть отражено

В справке по трещинам обязательно явно указать область применения новой геометрической логики:

> общий geometry/topology engine этой реализации используется расчетами трещин (СП 63/СП 35 и при необходимости другими классами трещин). Расчет устойчивости не переводится на этот механизм и продолжает использовать существующую дискретно-сеточную реализацию.

Не создавать у пользователя впечатление, что импортированный внешний контур или новый движок автоматически изменяют расчет устойчивости.


Справка по СП 35 должна содержать:

- `GroupGapTolerance`, default 10 мм;
- `RowTolerance`, default 50 мм;
- `RadiusDiameterMode = Max / Min / Average`;
- `InteractionRadiusMode = D3 / D5 / D6`;
- `RebarProfile = Periodic / Smooth`, default `Periodic`;
- алгоритм формирования групп;
- центр группы;
- $\beta$, включая $\beta=0.75$ для групп более трех стержней;
- якорные и второстепенные группы;
- разрешенный fallback с перебором всех растянутых групп, если контурные якоря трудно определить надежно;
- смещенные ряды;
- окончательное включение реальных стержней по положению их осей;
- одинаковое применение `RadiusDiameterMode` при боковом и внутреннем построении $r$;
- точное использование фактического внешнего контура и `opening`, если они известны;
- восстановление outer/opening loops по границам бетонных элементов при неизвестном внешнем контуре;
- fallback на дискретную геометрию при отсутствии явного внешнего контура;
- использование существующих классов/инструментов пересечения;
- центральное растяжение;
- расчет $\sum\beta nd$, $R_r$, $\psi$, $a_{\mathrm{cr}}$;
- выбор максимального раскрытия;
- сохранение критического контура `Ar`;
- диагностические данные результата.

## 19.4. Формулы

Все ключевые формулы должны быть приведены в читаемом LaTeX-виде, совместимом с отображением справки на Android.

Минимально:

$$
gap_{ij}
=
L_{ij}
-
\frac{d_i+d_j}{2}
$$

$$
x_g
=
\frac{\sum A_i x_i}{\sum A_i},
\qquad
y_g
=
\frac{\sum A_i y_i}{\sum A_i}
$$

$$
|n_i-n_j|
\le
\mathrm{RowTolerance}
$$

$$
d_{\mathrm{Max}}=\max(d_i)
$$

$$
d_{\mathrm{Min}}=\min(d_i)
$$

$$
d_{\mathrm{Average}}=\frac{1}{m}\sum_i d_i
$$

$$
r=k_r d_{\mathrm{ref}},
\qquad
k_r\in\{3,5,6\}
$$

$$
l_{\mathrm{Left}}
=
\min\left(r_{\mathrm{side}},\frac{s_{\mathrm{Left}}}{2}\right)
$$

$$
l_{\mathrm{Right}}
=
\min\left(r_{\mathrm{side}},\frac{s_{\mathrm{Right}}}{2}\right)
$$

$$
R_r=\frac{A_r}{\sum\beta nd}
$$

$$
\sum\beta nd
=
\sum_g\left(\beta_g\sum_{i\in g}d_i\right)
$$

$$

$$

для периодического профиля и

$$

# 21. Важные пограничные случаи

## 21.1. Ось стержня на границе

```text
inside OR on_boundary → included
```

Стержень учитывается. Остальные стержни исходной группы проверяются отдельно.

## 21.2. Группа более трех стержней

$$
\beta=0.75
$$

как принятое `[NDM]` правило.

## 21.3. Смешанные диаметры

Для $\sum\beta nd$ всегда использовать реальные диаметры.

Для любого построения $r$ использовать `RadiusDiameterMode`.

## 21.4. Смещенные ряды

Не требовать совпадения по одной нормали.

Ряд определяется координатой `n` с учетом `RowTolerance`, локальная принадлежность – координатой `t`.

## 21.5. Второстепенная группа на границе двух участков

Если центр лежит на общей границе, группа полностью входит в оба локальных расчета.

## 21.6. Не удалось надежно выделить контурные якоря

Не создавать сложную новую подсистему. Использовать разрешенный fallback: все растянутые группы являются кандидатами-якорями.

## 21.7. Нет растянутой арматуры

Вернуть корректный `NotApplicable / NoTensionRebar` согласно существующей системе статусов.

## 21.8. Все сечение сжато

Раскрытие нормальных растягивающих трещин равно нулю/не применимо согласно существующей модели результатов.

## 21.9. Отверстия

Opening учитывать в площади, пересечениях, составе рядов, аннотациях и экспорте. Локальная область заканчивается при первом входе в полость и не возобновляется автоматически в противоположной стенке. При отсутствии явного opening пустота определяется по граничным ребрам дискретных бетонных элементов.

При дискретной геометрии не заполнять пустые интервалы оболочкой или ограничивающим прямоугольником. Известные отдельные opening сохраняют приоритет даже при отсутствии явного внешнего контура. Подробные правила приведены в разделе 11 и общем контракте границ ниже.

Для сложных операций пересечений и топологии создать **один отдельный общий геометрический класс/компонент**.

Если часть этих операций сейчас находится в классе геометрических характеристик, вынести вычислительную реализацию в новый общий компонент.

В старом классе оставить собственно характеристики сечения: площадь, центр тяжести, моменты инерции, центробежный момент, главные характеристики и т.д.

При необходимости старые публичные методы пересечений можно временно оставить как тонкие делегирующие оболочки, но независимой второй реализации быть не должно.

Централизовать не только получение внешнего контура, но и одинаковые вычисления: пересечения с внешними/внутренними границами, сортировку и устранение дублей, интервалы бетона, проверку принадлежности и отсечение по переданной нейтральной линии/полуплоскости. Все соответствующие потребители используют общий контракт раздела 23.

## 22.4. Новые классы

Выделение одного общего компонента из перегруженного класса допускается, даже если отдельные операции уже существуют в старом классе: их надо перенести/переиспользовать, а не продублировать.

Не создавать заранее отдельные классы `RebarGroupAnalyzer`, `LocalCoordinateBuilder`, `RebarRowAnalyzer`, `InteractionZoneBuilder`, `SP35FormulaEvaluator` и т.п. только потому, что такое разбиение теоретически возможно.

Также не создавать отдельный новый сервис для каждого вида границы: внешний контур, opening, Н.О., известный контур, сеточный fallback. Это параметры/варианты общей геометрической операции, а не автоматическое основание для отдельного класса.

Сначала использовать существующие классы и небольшие методы. Один общий компонент может вызывать уже имеющиеся низкоуровневые геометрические инструменты. Требование единой реализации не означает обязательного переноса всех существующих примитивов в один огромный файл.

В рабочем журнале кратко записать выбранное размещение ответственности и причину. Новые имена классов/методов определять по стилю проекта, а не по условным обозначениям этого MD.

# 23. Единый геометрический API пересечений для всех расчетов и классов

## 23.1. Обязательный принцип: один запрос, одна общая реализация

**Все классы и расчеты проекта, которым нужны одинаковые геометрические операции с сечением, должны пользоваться общей реализацией.** Требование не ограничивается расчетом трещин СП 35 или парой СП 35/СП 63.

Недостаточно централизовать хранение контуров или выбор «контур / сетка», оставив в потребителях собственные вычисления пересечений, учет opening, сортировку точек или поиск первого выхода из бетона. Эти совпадающие по смыслу операции также должны быть объединены.

Для одинаковой версии геометрии, одинакового запроса, системы координат и численной точности результат не должен зависеть от того, кто его запросил: СП 35, СП 63, другая проверка или инструмент построения схемы. Сравнение выполняется с учетом действующего геометрического допуска.

Это требование к единому вычислительному пути, **не** требование глобального singleton, общего изменяемого результата или обязательного кэширования. Использовать обычный для проекта жизненный цикл геометрического объекта.

## 23.2. Сначала инвентаризация, затем выбор существующего или нового класса

До реализации найти:

- существующий класс/модуль характеристик геометрии и все его публичные геометрические запросы;
- вычисления пересечений прямой, луча и отрезка с контурами/сеткой;
- получение границ по Н.О. и другим заданным направлениям, принадлежность точки бетону, обработку opening;
- построение интервалов материала, отсечение областей и имеющиеся низкоуровневые операции;
- все места вызовов и локальные копии этих операций **в подсистеме расчета трещин**. Отдельно определить, используются ли те же низкоуровневые методы устойчивостью или другими расчетами, чтобы не менять их поведение.

Наличие подходящего класса проверить по коду, а не считать подтвержденным из формулировки задачи. В коротком рабочем журнале составить карту: операция → существующие реализации → потребители → целевой общий метод → тесты.

Если существующий класс соответствует ответственности, расширить его. Если объединение загрязняет класс выдачи характеристик, выделить один общий компонент геометрических запросов с использованием существующих инструментов. При необходимости старые публичные методы оставить тонкими делегирующими обертками без собственных вычислений. Две независимые реализации одной операции не оставлять.

**Обязательное разделение ответственности.** Сложные пересечения, clipping, outer/opening loops, определение бетонной области и fallback по дискретной геометрии должны находиться в одном отдельном общем геометрическом компоненте. Класс геометрических характеристик не должен оставаться вторым владельцем этих вычислений. Сам рефакторинг не является основанием менять формулы, смысл или результаты геометрических характеристик.

Не создавать универсальный геометрический фреймворк или множество мелких новых классов. Низкоуровневые средства, уже имеющиеся в проекте, можно сохранить и использовать за единым контрактом.

## 23.3. Разделение обязанностей

### Граница текущего рефакторинга

Новый geometry/topology class создается как чистый общий компонент, но в рамках этой задачи **его расчетными потребителями являются только классы трещин**.

Не выполнять попутный перевод устойчивости на этот класс.

Для устойчивости:

```text
existing stability geometry / discrete mesh pipeline
→ оставить без изменений
```

Если после выделения общего класса какой-либо старый helper формально остается доступен устойчивости, поведение устойчивости должно быть идентично исходному и подтверждаться только релевантными регрессионными тестами, без изменения алгоритма устойчивости.


| Участник | Ответственность |
|---|---|
| Генератор / importer | Создать или прочитать геометрию; выполнить штатную валидацию и единый переход в координаты модели; сохранить outer/opening и их происхождение |
| Общий геометрический компонент | Выбрать достоверный источник границ; вычислить пересечения; учесть opening; выдать интервалы, принадлежность и геометрическое отсечение по переданным ограничениям |
| Расчетная проверка | Определить нормативные размеры/ограничения и запросить нужную геометрию; применить формулы своего стандарта к результату |
| Координатор / существующая система НДС | Получить расчетное состояние; определить его пригодность по текущему общему контракту; передать готовые данные проверке |
| Writer / схема / exporter | Вывести готовый результат, контуры и аннотации; не восстанавливать расчет Ar и не запускать решатель |

Общий геометрический компонент не должен знать коэффициенты beta, правила r=3d/6d, нормативный выбор рядов, настройку `RadiusDiameterMode`, поиск критического a_cr или разметку Excel. В нем вообще не должно быть веток `If SP35` / `If SP63`: он получает только геометрические данные и ограничения.

При отсечении растянутой области проверка передает уже определенную линию и нужную сторону как геометрические параметры. Общий компонент не получает доступ к внутренностям solver, не вычисляет равновесие, не меняет материалы/extension и не выбирает расчетное сочетание.

Формульный класс СП 63/СП 35 также не становится владельцем общего пересечения с контурами. Сохранить однонаправленные зависимости: потребители → общий геометрический контракт → модель/существующие геометрические примитивы.

## 23.4. Контуры модели, а не только рисунок

Для сгенерированной геометрии внешние контуры и пустоты известны на этапе генерации. Сохранять их в геометрической модели/существующем контракте, а не только в экранных фигурах.

Валидированные контуры из AutoCAD имеют тот же смысл достоверной геометрической границы. Происхождение сохраняется для диагностики, но методика не должна иметь разные вычисления пересечений для «генератора» и «AutoCAD».

В существующей модели/контракте должны быть доступны:

- внешние замкнутые кольца и принадлежность компонентам;
- внутренние кольца opening и их принадлежность;
- известность, полнота и подтвержденная валидность соответствующих границ;
- происхождение: генератор, валидированный импорт, существующая дискретизация;
- единицы и координаты модели;
- версия/идентичность геометрии для актуальности результатов и, при наличии, кэшей.

Не смешивать неизвестный набор пустот с подтвержденным отсутствием пустот. Достоверность относится к конкретным имеющимся границам, а не автоматически ко всему сечению.

**Не заменять достоверными контурами автоматически интеграционную сетку, площади/инерции элементов и источник механических характеристик текущего НДС.** Новый общий компонент отвечает за геометрические запросы; контракт механической модели сохраняется. Несогласованность сетки и контуров проверяется при подготовке геометрии.

## 23.5. Выбор источника и учет opening только в одном месте

Общий компонент выбирает источник. Расчетный потребитель задает запрос, но не повторяет ветвление «контур есть/нет».

| Доступные сведения | Принятое поведение |
|---|---|
| Достоверны внешний контур и сведения о пустотах | Пересекать и отсекать по этим данным без fallback на внешнюю оболочку сетки |
| Внешний контур неизвестен | Использовать прежний поиск по краям бетонной дискретизации |
| Внешний контур известен, отдельные пустоты известны из дискретизации/другого штатного источника | Использовать достоверный внешний контур и не терять известные пустоты |
| Известны только отдельные контуры opening | Учитывать их как пустоты; внешний предел получать прежним способом |
| Явно заданный импортируемый контур невалиден | Выдать штатную диагностику импорта; не объявлять контур достоверным и не скрывать ошибку молчаливым fallback |

«Слой пустот не задан» не равно «в сечении гарантированно нет пустот». При частичных данных fallback применяется только к неизвестной части границ. Дублирующие описания одной пустоты не должны приводить к двойному вычитанию.

При любом запросе к **области бетона** известные opening учитываются автоматически. Для явного контура:

$$
\Omega_c=
\left(\bigcup_i\Omega_{\mathrm{outer},i}\right)
\setminus
\left(\bigcup_j\Omega_{\mathrm{opening},j}\right).
$$

Не заставлять каждый расчет отдельно вычитать отверстия после запроса, который уже обозначен как запрос к бетону. Явное получение только наружного кольца, например для его отрисовки, является другим запросом и не подменяет запрос бетонных интервалов.

## 23.6. Какие операции должны быть общими

Объединить требуемые задачей и найденные дублирующиеся операции. Конкретные имена методов и представления результата определяются по текущему коду; перечисление не является требованием завести отдельный класс на каждый пункт.

1. **Пересечения заданной прямой, луча или отрезка с границами сечения.** Учитывать внешний контур, opening, компоненты и доступный источник. Различать область параметра для прямой, луча и отрезка, а не использовать их как взаимозаменяемые запросы.
2. **Упорядоченный результат и интервалы материала.** Сортировать по ходу запроса, устранять численные дубли единым способом, определять вход/выход, касание и интервалы бетона/пустоты.
3. **Выбор геометрически заданного интервала и первого выхода из него.** По переданной стартовой точке/интервалу, направлению или другому уже используемому проектом геометрическому контексту возвращать нужную стенку, не прыгая через opening. Смысл «какая стенка рассматривается» задает запрос потребителя; общий компонент не угадывает его по названию СП.
4. **Принадлежность точки и положение относительно границ.** Отличать внутренность бетона, границу и пустоту/внешнее пространство. Окончательный отбор реальных стержней по их осям использует общий геометрический ответ; центр исходной группы не заменяет этот отбор.
5. **Пересечения и отсечение по заданным линиям/полуплоскостям.** Это включает уже известную Н.О., параллельные ей границы, заданные нормали, пределы локальной области и их пересечения. При отсечении сохранять все необходимые кольца и компоненты, учитывать opening.
6. **Общие операции над полученной областью.** Пересечение с бетоном, обрезка, обработка внутренних колец и вычисление площади должны переиспользовать имеющиеся общие геометрические средства, а не дублироваться в СП 35/СП 63. Нормативное правило построения самой области остается у потребителя.

Для одной операции можно иметь несколько удобных публичных методов/оберток, если все они используют одно вычислительное основание и согласованные допуски. Не требовать один универсальный метод с большим количеством несвязных флагов.

## 23.7. Нейтральная линия является входной геометрией, а не задачей решателя

Нейтральная линия/плоскость деформаций уже известна из переданного состояния НДС. Общий компонент получает готовую геометрическую прямую, направление и сторону отсечения либо использует штатное геометрическое представление проекта.

Он вычисляет ее пересечения с внешними границами/opening и может отсекать переданную область нужной полуплоскостью. Выбор растянутой стороны и нормативной глубины определяется готовыми данными и методикой снаружи этого компонента.

Если Н.О. не пересекает сечение, это допустимая геометрическая ситуация, а не автоматически численный отказ. Если в соответствующем состоянии Н.О. вообще не определена, нельзя создавать произвольную линию ради универсального метода: потребитель использует предусмотренный своей методикой вариант, например всю площадь при центральном растяжении.


## 23.8. Контракт результата и геометрическая точность

Общий ответ должен позволять различить, когда это нужно запросу:

- отсутствие пересечения как штатный пустой ответ и ошибку/невалидность исходной геометрии;
- точки, а при совпадении линии с ребром также участки совпадения, если такие случаи поддерживаются;
- порядок вдоль запроса, роль outer/opening и принадлежность компоненте;
- вход, выход и касание без перехода между материалом и пустотой;
- отдельные интервалы бетона без искусственного объединения через opening;
- происхождение использованных границ для диагностики точного контура/fallback.

Не заводить обязательное новое семейство DTO только ради этого списка: дополнить существующий контракт в минимально необходимом объеме. Если текущая геометрия не поддерживает сложный случай, возвращать штатную явную диагностику, а не придумывать сплошной бетон или фиктивную точку.

Единые правила для всех потребителей: порядок пересечений, попадание в вершину, устранение дублей, касание, совпадение с ребром, допуск принадлежности границе и нормализация параметров запроса. Использовать принятую геометрическую точность и систему координат/единиц проекта. `RowTolerance = 50 mm` и `GroupGapTolerance = 10 mm` не являются допусками геометрических пересечений.

Потребители не должны независимо округлять найденные точки или сливать близкие пересечения так, чтобы один расчет потерял opening, а другой его сохранил. Форматирование чисел в writer не меняет расчетную геометрию.

Геометрический компонент возвращает свой существующий тип результата/диагностики. Он не формирует внешний статус расчета, не меняет внутренние статусы solver и не дублирует status-policy.

## 23.9. Подключить всех потребителей и убрать обходные реализации

По карте вызовов из п. 23.2 перевести на общий контракт **всех найденных потребителей одинаковых операций**, а не только новые классы СП 35. Проверить расчет трещин СП 63, характеристики/запросы геометрии, другие проверки, построители схем/аннотаций, геометрическую часть импорта и иные места, где такие операции реально используются. Прочность, устойчивость и другие блоки менять только в тех местах, где найден соответствующий геометрический запрос; не добавлять ненужные зависимости.

Если старый публичный метод нужен другим классам, сохранить совместимую обертку, делегирующую общему компоненту. Внутри нее не оставлять старый независимый алгоритм. Существующие низкоуровневые пересечения ребер/дуг могут использоваться общим компонентом, но потребители не должны обходить через них единый учет сечения и opening.

Writer не приобретает собственную расчетную геометрию. Схема использует готовые контуры/аннотации; если для отображения нужны дополнительные геометрические отсечения, они получаются через тот же общий контракт и не запускают расчет Ar или НДС. Экспортер критической области читает сохраненный результат, а не пересчитывает пересечения.


На прежних входах с прежними источниками границ результаты должны совпадать в принятой точности. Изменения при добавленных точных контурах/пустотах проверять отдельными эталонами. Если перенос выявил старую ошибку учета opening, явно описать причину и добавить адресный тест; не скрывать попутные изменения алгоритма под общей централизацией.

## 23.10. Общие данные, актуальность и возможный кэш

Все запросы используют модельную геометрию, а не экранные shapes и не координаты экспорта. Перенос/поворот/масштаб визуализации не меняют расчетные ответы.

Кэш не обязателен. Если он уже есть или действительно нужен, он относится к геометрическому слою и должен учитывать как минимум идентичность/версию геометрии, источник/набор границ, вид запроса, его координаты и направление, ограничения и действующую точность. При запросе с Н.О. ее параметры и выбранная сторона также входят в идентичность запроса.

Не кэшировать результат только по имени якоря, номеру стержня, сочетания или типу СП. После изменения внешнего контура, opening, координат, источника геометрии или существенных параметров запроса старые результаты не должны переиспользоваться. Не смешивать две модели с одинаковыми локальными номерами объектов.

Потребитель не изменяет общие кэшированные точки/кольца на месте. Использовать текущую модель неизменяемых результатов либо безопасное копирование без обязательного внедрения новой инфраструктуры.

## 23.11. Схема и аннотации контуров сечения

Импортированные внешние контуры и opening отображаются тем же способом, что соответствующие контуры генераторов. Сохранять масштаб, поворот, перенос и роль границы. Расчеты и отображение используют одно геометрическое содержание, но экранные объекты не являются источником расчета.

Не терять контур при выключенной видимости схемы/аннотации: видимость является настройкой отображения. Повторная отрисовка заменяет свои объекты, а не накладывает дубли; сторонние пользовательские фигуры не удалять.

Готовая критическая область Ar остается отдельной аннотацией результата. Централизация пересечений не отменяет ее сохранение и не разрешает повторное построение из exporter-а.

## 23.12. Проверяемый результат архитектурного изменения

До завершения Codex должен повторно просмотреть карту вызовов и поиск по проекту. Для каждой одинаковой операции должен быть указан один общий владелец вычисления; перечислены потребители и совместимые делегирующие обертки, если они остались.

Добавить тесты общего контракта и интеграционные проверки его использования. Проверить одинаковые ответы из разных потребителей, opening при всех поддерживаемых источниках, Н.О., касания, инвалидацию геометрии и прежние эталоны. Повторно запустить релевантный ранее созданный набор тестов всех потребителей измененного общего геометрического кода; не запускать несвязанные долгие наборы без риска регрессии.

В рабочем журнале и итоговом отчете кратко указать выбранный существующий/новый класс и причину, устраненные дубли, подключенные потребители, результаты регрессии и реально оставшиеся ограничения. Не объявлять централизацию завершенной, если старые потребители продолжают независимо вычислять те же пересечения.

# 24. Импорт достоверных контуров геометрии из AutoCAD

## 24.1. Обязательный результат доработки

Расширить существующий импорт геометрии двумя опциональными семантическими слоями: внешний контур сечения и `opening`.

Имена этих слоев задаются пользователем в:

```text
AutoCAD.Common
```

и используются импортером как общий согласованный layer mapping. Когда пользователь задал соответствующий слой, объекты должны импортироваться, проходить валидацию и сохраняться как достоверные границы, доступные расчетам и схеме.

Не зашивать пример вроде `CONTOUR` или `OPENING` как единственно допустимое имя. Не путать слой наружного контура со слоем бетонных элементов/Region текущего импорта и со слоем арматуры. Не создавать вторую копию этих имен внутри `AutoCAD.Import`.

Добавление опциональных контуров не делает их обязательными для старых чертежей. Импорт без новых полей должен остаться работоспособным с прежним составом исходных данных.

## 24.2. Пустое поле и ошибочно заданное поле различаются

- Пустое поле: импорт соответствующего вида дополнительного контура не запрошен; сохранить прежний доступный способ получения этой границы.
- Поле задано: найти слой и подходящие объекты. Отсутствующий слой, неподдерживаемый объект или невалидная геометрия должны давать понятную диагностику, а не молча превращаться в «контура нет».
- Для слоя opening допускается пустой набор при действительно отсутствии объектов; это явно отразить в диагностике импорта. Отсутствующее имя слоя не подменять существующим пустым слоем.

При ошибке не оставлять смешанную модель из новых контуров и старой сетки. По возможности сначала собрать и проверить новый импорт целиком, затем передать его существующему механизму замены модели. Поведение ошибок согласовать с общей import-policy проекта.

## 24.3. Поддерживаемые объекты и топология

Сначала изучить уже поддерживаемые AutoCAD-объекты и переиспользовать существующее чтение геометрии. Для внешнего контура и opening необходимы замкнутые плоские границы. Поддержку полилиний, дуговых сегментов, окружностей, Region и сборки границы из отдельных объектов определять по фактическому API проекта; при необходимости обоснованно расширить его и покрыть тестами.

Чтение объектов AutoCAD остается в importer-е; общие проверки контуров, принадлежности opening и пересечений переиспользуют геометрические инструменты раздела 23. Не копировать в importer вычисления, уже централизованные для модели сечения.

Нельзя заявлять в справке поддержку произвольной кривой только потому, что AutoCAD умеет ее рисовать. Для каждого фактически поддержанного типа должен существовать корректный импорт и тест. Неподдержанные типы отклонять явно, не импортировать приблизительную оболочку без сообщения.

Проверить минимум:

1. планарность и соответствие расчетной плоскости сечения;
2. замкнутость, ненулевую площадь и отсутствие вырожденных ребер;
3. отсутствие самопересечений либо корректную обработку текущим геометрическим ядром;
4. роли внешних колец и opening, принадлежность пустот бетону;
5. дублирующиеся контуры и двойное вычитание одной пустоты;
6. пересечения/касания контуров, которые текущая модель не поддерживает;
7. соответствие размещению бетонных элементов и арматуры в принятой точности импорта.

Обычные несколько независимых внутренних пустот должны поддерживаться. Если сложная вложенность или отдельные несвязные компоненты выходят за контракт текущей модели, не сплющивать их в один контур: либо корректно поддержать, либо вернуть явную диагностику ограничения.

Не исправлять автоматически исходный чертеж, не удалять его объекты и не превращать импорт Ar-аннотации в контур материала.

## 24.4. Единицы и преобразование координат

Все части импорта обязаны пройти **один и тот же** согласованный переход из единиц/координат AutoCAD в внутреннюю модель:

- бетонная дискретизация;
- арматура и ее диаметры;
- внешние контуры;
- opening.

Не масштабировать новый контур отдельно от старой сетки и не применять перевод единиц дважды. Если текущий импорт делает перенос/поворот или работу с локальной системой, применять тот же переход к новым границам.

Codex обязан проверить фактическую реализацию единиц импорта. Не считать автоматически, что `INSUNITS`, единицы книги и одна координатная единица чертежа всегда совпадают. Если действующий контракт предполагает определенную единицу чертежа без чтения настройки AutoCAD, это должно быть прямо написано в справке. Не менять политику единиц всего импорта попутно без необходимости и отдельной регрессии.

В справке обязательно указать проверенный масштаб: например, как пользователю задать стержень диаметром 20 мм и размер сечения 1000 мм в реально поддерживаемых единицах. Это пример для проверки, а не предположение о текущей реализации.

## 24.5. Контур, сетка и механические характеристики

Новый контур является достоверной геометрической границей после валидации, но не командой заново дискретизировать сечение или подменить импортированные характеристики бетонных элементов.

Проверять, что различие контуров и сетки соответствует допустимой точности дискретизации. Большое расхождение, арматура в пустоте или контур в другом масштабе не должны молча проходить как рабочая геометрия. Не выдумывать новое универсальное численное значение допуска: использовать существующую политику либо обоснованно описать минимально необходимое расширение.

При добавлении/изменении/удалении контура сечения или opening обновлять геометрическую версию/актуальность зависимых результатов штатным способом.

## 24.6. Передача модели и отрисовка

После успешного импорта:

```text
слои / объекты AutoCAD
  → существующий importer и валидация
  → координаты модели + контуры + роли outer/opening
  → единый geometry-контракт для всех потребителей, включая СП 35 и СП 63
  → штатные аннотации и отрисовка на схеме
```

Экранные аннотации не являются единственным владельцем расчетной геометрии, если их формат теряет точность/топологию. Схема и расчеты должны ссылаться на одно геометрическое содержание.

# 25. Универсальный экспорт расчетной области нормальных трещин в AutoCAD

## 25.1. Пользовательская настройка

В `AutoCAD.Export` использовать один универсальный переключатель:

> **Выгружать контур расчетной области нормальных трещин**

Условное техническое имя:

```text
ExportCrackInteractionContour
```

Начальное значение:

```text
False
```

Если ранее существовал/был добавлен `ExportSP35InteractionContour`, заменить его семантику на универсальную без двух параллельных настроек.

Поведение зависит от выбранного стандарта расчета трещин:

```text
Standard = SP35
→ export final critical SP35 interaction region

Standard = SP63
→ export final SP63 calculation region actually used by its crack-width method
```

Настройка не влияет на расчет, НДС, выбранный стандарт или результат проверки.

## 25.2. Одна область для числа и для AutoCAD

Экспортировать **ровно ту геометрию**, по которой было получено численное значение площади, участвующее в нормативной формуле.

Обязательная инварианта:

$$
A_{\mathrm{calculation}}
=
A_{\mathrm{stored\ geometry}}
=
A_{\mathrm{exported\ polylines}}
$$

в пределах принятого численного tolerance и экспортной точности координат.

Экспортер не имеет права заново строить площадь, повторно искать пересечения, вызывать solver или создавать «красивую» геометрию, отличную от расчетной.

## 25.3. Известный контур

Если достоверный внешний контур известен, расчетная область строится как фактическое пересечение:

```text
real concrete contour
+ real opening contours
+ standard-specific lower/inner boundary
+ standard-specific side limits, if any
→ final region
```

В AutoCAD вывести **фактически получившийся замкнутый контур** этой области.

Кривые/ломаные/скругления сохранять штатным механизмом настолько точно, насколько это позволяет текущий geometry/export contract.

## 25.4. Контур неизвестен

Если внешний контур неизвестен, общая геометрическая логика использует дискретные бетонные элементы.


В общей задаче такая экспортируемая полилиния может быть ступенчатой.

Именно по этой ступенчатой замкнутой геометрии должна быть вычислена площадь, если она использована расчетом.


## 25.5. Замкнутые outer и opening loops

Каждый внешний контур компоненты экспортировать отдельной **замкнутой полилинией**.

Если в расчетную область полностью попала пустота, ее внутренний контур также экспортировать отдельной **замкнутой полилинией**.

Если пустота пересекает наружную границу расчетной зоны, сохранить корректную топологию выреза, не соединяя границы фиктивными служебными отрезками через пустоту.

Экспортируемый набор колец должен позволять однозначно восстановить ту же площадь.

## 25.6. СП 35 и СП 63 используют одну геометрическую механику

Нормативные правила построения нижней/внутренней границы и прочих параметров остаются специфичными для каждого СП.

Но после определения этих параметров:

- СП 35;
- СП 63

должны использовать **один общий движок построения/обрезки/площади расчетной области**.

Не поддерживать отдельный «SP35 polygon builder» и отдельный «SP63 polygon builder» с дублирующей топологической логикой.

## 25.7. Источник данных только готовый результат/аннотация

Экспортер читает сохраненную расчетную область через существующий контракт результата/аннотаций.

Запрещены:

- повторное вычисление области;
- повторный обход арматуры;
- поиск НДС;
- вызовы solver;
- восстановление формы только по числу площади.

Если область отсутствует или устарела, экспорт этого типа пропускается через существующую диагностику.

## 25.8. Слой, координаты и повторный экспорт

Использовать штатные координаты модели, масштаб и общий механизм слоев AutoCAD.

Не смешивать роль расчетной области трещин с ролями внешнего контура сечения и `opening`.

Цвета, типы/веса линий и другие чисто визуальные свойства остаются в `AutoCAD.Export`.

При повторной выгрузке применять существующую policy обновления экспортных объектов и не накапливать дубли одной расчетной области.

## 23.X. Отдельный централизованный класс сложных геометрических операций

Это обязательное архитектурное решение.

Codex должен создать **один отдельный общий класс/компонент** для сложных геометрических операций и перевести на него существующие и новые расчеты пересечений.

Условное назначение класса:

```text
SectionGeometryQueries / GeometryIntersections / SectionTopology
```

Точное имя выбрать по соглашениям текущего проекта. Имя из этого ТЗ не является обязательным.

### Что должно находиться в новом классе

Как минимум общие операции:

- пересечение луча/прямой/отрезка с внешним контуром;
- пересечение с `opening`;
- пересечение с нейтральной линией и другими ограничивающими линиями;
- clipping области по внешнему контуру и внутренним пустотам;
- определение интервалов реального бетона вдоль линии/луча;
- поиск первого выхода из связной бетонной области;
- проверка принадлежности точки бетону;
- различение внешнего контура и внутренних контуров;
- обработка касаний, совпадений и геометрических tolerance;
- fallback по дискретной бетонной геометрии при отсутствии явного контура;
- общие операции, которые уже сейчас дублируются в разных расчетах и дают одинаковый геометрический результат.

### Что должно остаться в классе геометрических характеристик

Если сейчас часть пересечений находится в классе, который одновременно считает характеристики сечения, после рефакторинга в нем должны остаться прежде всего:

- площадь;
- центр тяжести;
- моменты инерции;
- центробежный момент;
- главные характеристики;
- иные собственно характеристики сечения.

Он **не должен оставаться вторым местом**, где живет независимая реализация пересечений.

### Миграция существующих методов

Codex должен найти существующие методы поиска пересечений в проекте и:

1. перенести их вычислительную реализацию в новый общий класс;
2. заменить внутренние вызовы в старых потребителях на новый класс;
3. при необходимости временно сохранить старые публичные методы как **тонкие совместимые оболочки**, которые только делегируют в новый класс;
4. не оставлять две независимые реализации одного алгоритма;
5. после миграции убедиться, что старые расчеты получают те же результаты.

Все **потребители внутри подсистемы трещин** одинаковых геометрических операций должны использовать один механизм, включая при необходимости:

- СП 35;
- СП 63;
- другие классы трещин, если им нужны те же операции.

AutoCAD import/export и отрисовка используют сохраненную геометрию/контуры через существующие контракты, но не становятся расчетными потребителями нормативной логики.

**Устойчивость в этот список не входит и должна остаться на прежней дискретно-сеточной реализации.**

### Разделение ответственности

Новый класс работает только с геометрией и **не должен**:

- знать нормативные коэффициенты СП 35/СП 63;
- вычислять ширину раскрытия трещин;
- вызывать solver;
- искать НДС;
- формировать внешний статус расчета;
- работать как writer.

Расчетный модуль должен сформулировать геометрический запрос, а новый класс вернуть геометрический результат.

Так сохраняется четкое разделение:

```text
section geometric characteristics
        ↕
shared geometry-query/intersection class
        ↕
calculation modules / import / export / drawings
```

## Общая стратегия тестирования: адресно, по риску, без лишних долгих прогонов

Тестирование должно быть **достаточным для уверенности в измененном коде**, но не должно механически повторять все очень долгие проверки проекта после каждого этапа.

Особенно:

> **Не запускать повторно длительные проверки/аудиты из «Аудита 3», если текущие изменения не затрагивают код, контракт или данные, которые эти проверки способны сломать.**

Пример: если в этой задаче не менялись общая загрузка/чтение всех ячеек настроек, базовый механизм именованных диапазонов, общий serializer settings или другой код, ранее полностью проверенный длительным аудитом, **не нужно повторять весь многочасовой аудит только потому, что задача касается новых настроек СП 35**.

Перед выбором тестов Codex должен смотреть `git diff` и зависимости измененных классов.

Приоритет тестирования:

```text
1. новые методы и классы;
2. измененные существующие методы и классы;
3. прямые потребители измененного общего кода;
4. адресные регрессионные тесты старого поведения в затронутых местах;
5. финальные end-to-end прогоны реальных расчетов сечения.
```

Полный дорогостоящий набор старых тестов выполнять только если:

- затронут фундаментальный общий код с широкой зоной влияния;
- изменена общая загрузка/валидация настроек;
- изменен общий solver/state pipeline;
- изменен общий serializer/import contract;
- невозможно надежно ограничить область возможной регрессии;
- адресные тесты выявили подозрение на более широкую поломку.

Если длинный набор не запускался, это **не дефект реализации** при условии, что Codex:
- объяснил, почему изменения не затрагивают его область;
- запустил релевантные тесты измененного кода и его потребителей;
- выполнил финальные расчетные end-to-end проверки.

### Обязательные финальные расчетные прогоны

В конце реализации выполнить несколько **полных расчетов сечения через обычный пользовательский pipeline**, а не только unit-тесты отдельных методов.

Набор должен покрывать разные характеры нагрузки, насколько это поддерживается существующими эталонами/тестовой инфраструктурой, например:

- осевая сила;
- чистый изгиб;
- внецентренное сжатие/растяжение `N + M`;
- двухосное нагружение `Mx + My`;
- общее сочетание `N + Mx + My`;
- случаи до образования трещины и после нее;
- хотя бы один случай, где рассчитывается СП 35 с несколькими рядами/группами арматуры.

Для этих прогонов сравнить ключевые результаты с ожидаемыми эталонами/аналитически понятными значениями и убедиться, что незатронутые расчеты не изменили поведение.

**Scope:** подключить новый класс к расчетам трещин. Устойчивость и другие независимые расчеты не мигрировать.


До реализации новой геометрии расчетов:

1. найти все существующие методы пересечений/поиска границ;
2. определить, какие из них находятся в классе геометрических характеристик;
3. создать один отдельный общий класс сложных геометрических запросов;
4. перенести туда вычислительную реализацию пересечений, clipping, outer/opening loops, поиск бетонной области и fallback по дискретным элементам;
5. переключить старые потребители на новый класс;
6. при необходимости оставить старые публичные методы только как тонкие делегирующие оболочки;
7. проверить совпадение прежних результатов;
8. не создавать ветки по СП внутри нового класса.

Новый класс универсален для СП 35, СП 63 и любых других будущих расчетов.


## Этап 4. Настройки СП 35 и готовые входы НДС

Добавить/переиспользовать согласованные настройки `Common / SP63 / SP35`, включая `GroupGapTolerance`, `RowTolerance`, `RadiusDiameterMode`, `InteractionRadiusMode`, `RebarProfile`.

Проверка СП 35 получает готовое НДС от существующего координатора. Не добавлять внутрь нее получение Pre/Post через solver. Централизованные статусы и правила пригодности состояния не подгонять под примеры из MD.

## Этап 5. Группы, якоря и ряды

Реализовать чистый зазор, связные исходные группы, центр по площади, фактический отбор стержней конечной области, коэффициент beta для вошедшей части и настройку выбора диаметра. Определить якорные группы поддерживаемым способом; при невозможности надежной классификации использовать согласованный fallback без сложной новой подсистемы.

Предварительные второстепенные группы должны относиться к локальному доступному бетону, не находиться за opening. Затем определить ряды и нормативный опорный ряд.

## Этап 6. Единая расчетная область

Для каждого стандарта сформировать его геометрические ограничения и передать их общему движку области.

Если outer/opening известны — использовать их фактическую геометрию.

Если outer неизвестен — получить замкнутые outer/opening loops из граничных ребер дискретных бетонных элементов, затем выполнить clipping по нормативным ограничениям.

Площадь вычислять по конечной геометрии, которая затем сохраняется и экспортируется.

Для СП 35 дополнительно согласовать состав групп/рядов с фактической конечной областью. Это геометрическая фильтрация, не новый поиск НДС.


## Этап 7. Формулы и критический результат

Переиспользовать формульный класс СП 63, если это не смешивает ответственности. Иначе создать лишь необходимые отдельные классы. Разделить методы стандартов комментариями.

Посчитать сумму реальных диаметров с beta, Rr, psi, ширину, проверку предела и критическую группу. Применять централизованные единицы и существующую систему результатов.

## Этап 8. Сохранение области и аннотации

Сохранить конечную область со всеми outer/inner loops, владельцем результата, единицами, происхождением границ и актуальностью. Связать ее со штатной таблицей/контрактом аннотаций. Схема, число площади и экспорт используют один снимок.

Протестировать сериализацию, смену сочетания, повторный расчет, удаление устаревших аннотаций и сохранность контуров сечения/opening.

## Этап 9. Реализованный экспорт AutoCAD

Добавить/использовать универсальный переключатель `ExportCrackInteractionContour` в `AutoCAD.Export`.

Экспортер должен использовать общие семантические имена слоев из `AutoCAD.Common`, если соответствующая сущность имеет общий layer mapping, а чисто визуальные параметры экспорта — из `AutoCAD.Export`.

Экспортер читает готовую актуальную геометрию, не вычисляет ее. Вывести все кольца корректно в штатных координатах/слоях.

Проверить выключенный флаг, отсутствие результата, устаревший результат, выполненный расчет с превышением допустимой ширины, повторную выгрузку и разные сочетания.

## Этап 10. Подробная таблица

Вся компоновка и данные относительно `rngCrackSummaryAnchor`; скриншоты задают только относительный порядок, названия, объединения и разделители.

## Этап 11. Обе части справки

Одновременно с кодом обновить общий раздел трещин в одной скрываемой группе по образцу устойчивости: СП 63, затем СП 35, от основной формулы к составляющим.

Дополнительно создать отдельный скрываемый раздел «Подготовка геометрии в AutoCAD и импорт» с обязательными/опциональными объектами, слоями, единицами, примером, ошибками и настройкой экспорта. Проверить ссылки на пункты, формулы, таблицы и рисунки по локальным первоисточникам.

## Этап 12. Адресная регрессия, end-to-end расчеты и итоговая сверка

Не запускать автоматически весь исторический набор тестов только ради формального «полного прогона».

Сначала по `git diff` определить:

- какие классы реально изменены;
- какие общие контракты затронуты;
- какие старые потребители могут измениться;
- какие ранее проверенные подсистемы гарантированно не затронуты.

Запустить:

1. все новые тесты СП 35;
2. тесты измененных общих геометрических классов;
3. тесты импорта/экспорта, если этот код изменялся;
4. тесты настроек только в части реально измененного settings contract;
5. тесты СП 63 и других расчетов, которые используют измененный общий геометрический API;
6. writer/annotation тесты, если они изменялись;
7. другие адресные регрессионные тесты прямых потребителей измененного кода.

**Не повторять очень долгие тесты из «Аудита 3»**, если ни один измененный класс/контракт не способен повлиять на проверяемую ими функциональность. В частности, не перечитывать и не перепроверять реальную работу всех ячеек настроек только из-за добавления новых полей, если общий механизм чтения/маппинга ячеек не менялся и новые поля уже покрыты адресными тестами.

После адресной регрессии выполнить обязательные **полные end-to-end расчеты сечения** через штатный pipeline с разными видами нагрузок. Проверить ожидаемые:

- усилия/состояния;
- положения Н.О., где применимо;
- PreCrack/PostCrack/current state;
- существующие результаты СП 63;
- новый результат СП 35;
- статусы через централизованную policy;
- отсутствие незапланированных изменений других расчетов.

Минимально покрыть характерные случаи `N`, изгиб, `N+M`, `Mx+My` и `N+Mx+My`, если эти сценарии доступны в текущей тестовой инфраструктуре.

Если изменение затронуло фундаментальный общий код и область риска действительно широкая, тогда расширить набор вплоть до полного проекта. Решение должно быть основано на зоне влияния, а не на привычке запускать все подряд.

Повторно прочитать MD и скриншоты, проверить `git diff`, пройти весь checklist. Не удалять или ослаблять старый тест только ради зеленого прогона. Изменение эталона допускается только для объясненного нового входа/согласованной геометрической семантики.

В итоговом отчете указать:
- какие тесты запускались;
- почему именно они релевантны измененному коду;
- какие долгие наборы сознательно не запускались и почему они не затронуты;
- результаты end-to-end расчетов;
- исходные сбои и непроверенные интеграции с Excel/AutoCAD.

Не называть недоступные или сознательно не запускавшиеся проверки пройденными.

Вести короткий рабочий журнал/список этапов в существующем проектном формате либо рядом с этим MD: выполнено, текущая задача, решения, тесты, оставшиеся ограничения. После сжатия контекста перечитать его, этот MD, `git status` и текущий diff.

Повторно прогнать прежние тесты тех подсистем из геометрических характеристик, прочности, устойчивости, трещин, writer-ов, аннотаций и импорта/экспорта, которые реально зависят от измененных классов/контрактов.
