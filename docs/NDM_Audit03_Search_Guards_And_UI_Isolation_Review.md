направленном прогоне watchdog завершен, source unchanged=True. Новых классов,
физических критериев и нормативных формул нет. Действующие numerical tolerances
и исторические expected values не изменены.

Для геометрии проверяются площадь, центр и все центральные моменты инерции
по независимому прямоугольному oracle. Положения проема проверяют центр базовой
ячейки внутри и вне пустоты, плюс контроль проема на стыке четырех ячеек.
Для выпуклой области сохранена ветка полной ячейки; subdivisions=1 не менялся.

Retry проверяется в двух расположениях настоящей таблицы, включая CH800.
Число ступеней каждой разрешенной попытки должно быть <= 2147483646, чтобы
счетчик Long мог завершить цикл. Например: база 1 допускает 30 удвоений,
база 3 допускает 29. Это представимость программного счетчика, не предел
нагрузки по СП и не рекомендация использовать миллиарды ступеней.

## Расход Памяти Excel

Full Off v286 завершил шесть suites без ошибок, но UI остановился с VBA 14
`Out of string space`. Он не является полным PASS. Диагностика на независимых
копиях не обнаружила дополнительный solve или большой ошибочный output range.

Сохраненный UI-prefix воспроизводит расход около 120 МБ на один unit/sign
вариант, когда Results активен. Разметка стадий v291b выполнялась только во
временном VBA-проекте отдельной fixture; production source не инструментирован.
Память увеличивалась на разных обычных операциях оформления. Короткие проверки:

- v290: 43/0, две полные записи, summary примерно +110/+105 МБ;
- v292 ScreenUpdating=Yes: 44/0, privateBytes после двух вариантов 357 МБ;
- v292 ScreenUpdating=No: 44/0, 150 МБ после восстановления приложения;
- v293 штатный guard: 44/0, около 175 МБ после восстановления;
- v293 активный Config: 44/0, около 104 МБ, практически без роста второй записи.

Это воспроизводимая зависимость ресурсов Excel от отображения листа, а не
NumFail равновесия. Только временное отключение экрана не устраняет весь рост.
Основная книга, пользовательский Excel PID 23476 и настройки его приложения
не изменялись. Остановленные собственные тестовые процессы отмечены в логах;
их RPC errors не трактуются как физические исходы.

Высокообъемный тест 72 вариантов v294 теперь выполняет табличные assertions
при активном Config и восстанавливает исходный активный лист. Все варианты,
численные comparisons, writer/readback и no-extra-solve assertions остаются.
Добавлена отдельная проверка восстановления листа. Двухвариантная stage-
диагностика сохраняет возможность воспроизвести исходный ресурсный сценарий.
Это исправление изоляции теста, не заявленная оптимизация production writer-а.

## Оставшиеся Gates

### Дополнение F07 v304-v306

Frozen runner v304 воспроизвел 48 runtime overflow при конечных моментах
1e160/1e308 и N=0: обе схемы Newton/Secant, Extension Off/On, шесть направлений.
После каждой большой нагрузки обычное сжатие успешно восстанавливалось.
Причина находится до solve: ApplyInitialGuess вычислял Mx^2 + My^2.

Guard теперь вычисляет эту норму только когда обе компоненты не больше
исходного NEAR_ZERO. В остальных случаях норма заведомо выше допуска,
поэтому квадрат не нужен. Допуск, старые ожидаемые числа и физические
критерии не менялись. Directed positive v305 `336/0`, полный Solver `1367/0`;
stable v306 сохраняет ту же правку без экспериментального изменения psi.
Batch v306 `28725/0`, Results/status-style save-reopen=True. Это конкретный
закрытый overflow, не blanket приемка любых произвольных Double-сценариев.

Actual export/source v306 `108/108`, failed=0. Последующие comment-only
и восстановленные исторические test assertions перечислены в Progress;
им нужна следующая фактическая build, а не декларация equality старой книги.

UI v294 не принят: все 72 unit/sign варианта прошли со стабильной памятью,

контракт изоляции на InputUnit и массовую часть suite, возвращает исходный
лист при успехе/ошибке и сохраняет исходную ошибку обработчика.
