# CapacityLoadPath: ветвления и стартовые приближения

Документ фиксирует фактическую логику поиска предельной несущей способности после перехода на универсальную lambda-траекторию. Главная идея: пользователь выбирает, какие компоненты нагрузки масштабируются, а расчет дальше сводится к одной форме:

```text
Target(lambda) = Offset + lambda * Base
```

Нулевые компоненты внутри `Base` допустимы. Ошибка возникает только тогда, когда выбранная траектория вообще не содержит ни одной ненулевой масштабируемой компоненты.

## Где находится логика

Основные места в коде:

- `CBatchSectionCalculator.RunCapacity` - читает уже разобранный `CCapacityLoadPath` и выбирает численный путь по `Capacity.SolutionStrategy`.
- `CCapacityLoadPath` - переводит пользовательский вариант `lambda*...` в шесть чисел: `NOffset`, `NBase`, `MxOffset`, `MxBase`, `MyOffset`, `MyBase`; моментные компоненты проходят общий фильтр `Calculation.ZeroMomentPerDepth`.
- `CCapacityLoadPath.ForceOnly` - определяет силовую осевую траекторию, когда пользователь масштабирует только `N` или `lambda*NMxy` фактически содержит только `N`; имя пользовательского пути при этом не меняется.
- `CStateSolutionRunner` - управляет прямым `StateSolution`: стартовой плоскостью, retry, extension warm-start и повторными вызовами `CSectionSolver`.
- `CCapacitySolver` - решает уже готовую математическую задачу `Offset + lambda*Base`.
- `CStateGuessBuilder` - строит стартовую плоскость деформаций для редких численно трудных случаев; не выбирает путь, не меняет нагрузки и не принимает решение о статусе.

Архитектурно смысл пользовательской траектории теперь сосредоточен в `CCapacityLoadPath`, а batch получает готовый Offset/Base и признаки вроде `ForceOnly`. `CCapacitySolver.ApplyPureBendingProbeGuess` оставлен локально внутри solver-а, потому что это не пользовательская ветка, а подсказка старта для конкретной probe-точки `LoadMultiplier`; саму плоскость строит общий `CStateGuessBuilder`.

## Варианты CapacityLoadPath

| Вариант | Что масштабируется | Что остается постоянным | Минимально нужно задать |
|---|---|---|---|
| `lambda*Mx` | пользовательский `Mx` | `N`, пользовательский `My`, моменты от эксцентриситета `N` | `Mx <> 0` |
| `lambda*My` | пользовательский `My` | `N`, пользовательский `Mx`, моменты от эксцентриситета `N` | `My <> 0` |
| `lambda*Mxy` | пользовательские `Mx` и `My` | `N`, моменты от эксцентриситета `N` | `Mx <> 0` или `My <> 0` |
| `lambda*N` | `N` и моменты от эксцентриситета этой силы | пользовательские `Mx`, `My` | `N <> 0` |
| `lambda*NMxy` | полный внутренний вектор `N`, `Mx`, `My` | ничего | `N <> 0` или `Mx <> 0` или `My <> 0` |

Для `lambda*NMxy` нулевые компоненты просто не участвуют. Например, если задано только `N`, расчет остается путем `lambda*NMxy`, но математически масштабируется только продольная сила.

## Как собирается Offset/Base

В `CCapacityLoadPath.BuildOffsetBase` учитываются две части момента:

- пользовательские `Mx/My`;
- моменты от переноса продольной силы из точки приложения нагрузки к расчетной системе координат.

Правило такое:

- если масштабируется `N`, то вместе с ней масштабируются и моменты от ее эксцентриситета;
- если масштабируются только моменты, то `N` и ее эксцентриситетная часть остаются постоянными.

Это важно, чтобы `lambda*N` означало увеличение всей продольной силы с ее фактической точкой приложения, а `lambda*Mxy` - увеличение именно пользовательского изгиба при той же `N`.

## Capacity.SolutionStrategy

`Capacity.SolutionStrategy` - предпочтительная стратегия, а не абсолютный запрет на другой внутренний метод.

Фактическая логика:

- `Auto` - для обычных моментных траекторий сначала используется быстрый `UltimateStrain`; для силовых траекторий применяется `LoadMultiplier`.
- `UltimateStrain` - для моментных траекторий используется `UltimateStrain`; для силовой осевой траектории используется `LoadMultiplier`, потому что предельная осевая сила устойчивее ищется как множитель нагрузки.
- `LoadMultiplier` - всегда используется одномерный поиск по lambda через выбранный `Capacity.SearchMethod`.

В Results выводится фактически использованный метод: `UltimateStrain` или `LoadMultiplier`.

## Когда сходимость хорошая без помощи

Обычно без дополнительных стартовых подсказок хорошо сходятся:

- `N + lambda*Mx`;
- `N + lambda*My`;
- `N + lambda*Mxy`;
- общий `lambda*NMxy`, если в нагрузке есть выраженный моментный компонент;
- прямой `DirectState`, если есть `N` или уже ненулевая понятная жесткость в начальной точке.

В этих случаях нулевая стартовая плоскость быстро уходит в нужную сторону, а предыдущая acceptable-точка `LoadMultiplier` дает нормальный warm-start для следующих probe-точек.

## Когда вызывается CStateGuessBuilder

`CStateGuessBuilder` вызывается только как численная подсказка начальной плоскости:

1. `CStateSolutionRunner.ApplyInitialGuess`
   - случай: прямой НДС для чистого изгиба `N = 0`, но есть пользовательский `Mx` или `My`;
   - метод builder-а: `BuildForDirectState`;
   - смысл: не стартовать ровно из нулевого излома диаграммы бетона.

2. `CCapacitySolver.ApplyPureBendingProbeGuess`
   - случай: probe-точка `LoadMultiplier` имеет `N = 0` и ненулевой момент;
   - метод builder-а: `BuildForDirectState`;
   - смысл: каждая probe-точка чистого изгиба получает разумный старт от собственных целевых усилий.

3. `CStateSolutionRunner.TrySolveWithExtensionWarmStart`
   - случай: прямой `StateSolution` не сошелся на первой попытке, а `Solver.DirectState.DiagramExtension = Yes`;
   - метод builder-а: `BuildForExtensionState`;
   - смысл: дать повторному solve старт уже в области технического продолжения диаграммы.

Во всех случаях builder не меняет результат напрямую. После него `CSectionSolver` заново решает полное равновесие.

## Fallback-и

Фактические fallback-и сейчас такие:

- `Auto` для capacity может перейти от предпочтительного `UltimateStrain` к `LoadMultiplier`, если это нужно для выбранной траектории.
- Для силовых траекторий `lambda*N` и фактически силового `lambda*NMxy` применяется `LoadMultiplier`, даже если пользователь выбрал `UltimateStrain`.
- Для `DirectState` при включенном `DiagramExtension` возможна повторная попытка solve со стартом от `CStateGuessBuilder.BuildForExtensionState`.
- В `LoadMultiplier` probe-точки кэшируются, поэтому Brent/Secant/Bisection не пересчитывают один и тот же lambda повторно.

Это не fallback на другой `CapacityLoadPath`: пользовательский путь сохраняется. Меняется только численный метод, которым ищется предельная точка на той же траектории.

## Что можно улучшить позже

Если логика стартовых подсказок продолжит расти, можно будет расширить `CStateGuessBuilder` новыми чистыми методами построения eps0/kappaX/kappaY. Управление retry при этом должно оставаться в runner-е или solver-е того сценария, который выполняет повторные solve-ы.
