# Сравнение вызовов решателя в расчете трещин

Документ сравнивает текущую реализацию `Calculation.Crack.Width` с предыдущей схемой, где `Mcrc/Ncrc` определялись только в режиме `SLS.Crack.PsiMode = Auto` и только если первая проверка раскрытия с `psi_s = 1` не проходила.

## Что считаем решением НДС

В этом сравнении разделены два типа вычислений:

- **полноценный solve НДС** через `CStateSolutionRunner` / `CSectionSolver.Solve`: итерационный подбор `epsilon0`, `kappaX`, `kappaY` под заданные `N, Mx, My`;
- **прямой поиск состояния образования трещины** через `EvaluateStrainPlane`: программа сама итерационно меняет плоскость деформаций и только оценивает напряжения/усилия для этой плоскости. Это тоже расчетная работа по всем элементам, но это не отдельный обычный solve НДС по заданным усилиям.

## Предыдущая схема

Раньше batch сначала всегда находил текущее состояние:

```text
CBatchSectionCalculator
→ RunProfileState(CrackedState, MaterialModel.CrackedState)
→ CCrackWidthCalculator.Calculate(current CrackedState)
```

Дальше поведение зависело от `PsiMode`.

| Сценарий | Полноценные solve НДС | Дополнительные состояния |
|---|---:|---|
| `PsiMode = User` | 1: только текущий `CrackedState` LC | `CrackedState` |
| `PsiMode = Auto`, первая проверка с `psi_s = 1` прошла | 1: только текущий `CrackedState` LC | `CrackedState` |
| `PsiMode = Auto`, первая проверка не прошла, общая ветка `N + M` | обычно 2: текущий `CrackedState` LC + `AfterMcrcState`; плюс прямой поиск `lambda_crc` через `EvaluateStrainPlane` | `CrackedState`, `BeforeMcrcState`, `AfterMcrcState` |
| `PsiMode = Auto`, центральное растяжение, первая проверка не прошла | обычно 2: текущий `CrackedState` LC + `AfterMcrcState` | `CrackedState`, `AfterMcrcState`; `BeforeMcrcState` для центральной ветки не создавался |
| `PsiMode = Auto`, первая проверка не прошла, но найдено `lambda_crc > 1` | обычно 1: текущий `CrackedState` LC; `AfterMcrcState` не нужен | возможно `BeforeMcrcState` в общей ветке, без `AfterMcrcState` |

Главное свойство старой схемы: если первая формула раскрытия проходила или пользователь задавал `psi_s`, программа вообще не проверяла факт образования нормальной трещины. То есть `Mcrc/Ncrc` были не самостоятельной обязательной стадией расчета, а только служебным способом уточнить `psi_s`.

## Текущая схема

Сейчас batch сначала проверяет факт образования нормальной трещины, затем независимо от результата считает текущее `CrackedState` полного LC:

```text
CBatchSectionCalculator
→ CCrackWidthCalculator.CheckFormationBeforeWidth(...)
→ сохранить BeforeMcrcState / AfterMcrcState, если они получены
→ RunProfileState(CrackedState, MaterialModel.CrackedState)
→ проверка продольных трещин по текущему CrackedState
→ если нормальная трещина образована:
     CCrackWidthCalculator.CalculateAfterFormationCheck(current CrackedState)
```

Для общей ветки `N + M` текущий `Mcrc` ищется при постоянной `N` и масштабировании только моментного вектора относительно центра приведенного сечения. Это отличается от старого масштабирования всего набора `N, Mx, My`.

| Сценарий | Полноценные solve НДС | Дополнительные вычисления | Состояния |
|---|---:|---|---|
| Нет действия, способного вызвать нормальную трещину | 1: текущий `CrackedState` LC | нет поиска `Mcrc/Ncrc` | `CrackedState` |
| Центральное растяжение, есть действие для нормальной трещины | 3: `BeforeMcrcState` по модели `CrackInitiation` + `AfterMcrcState` по модели `CrackedState` + текущий `CrackedState` LC | `Ncrc = Ared * Rbt,ser` без итерационного поиска | `BeforeMcrcState`, `AfterMcrcState`, `CrackedState` |
| Общая ветка `N + M`, прямой поиск Mcrc сошелся | 2: `AfterMcrcState` + текущий `CrackedState` LC | прямой поиск `BeforeMcrcState` через `EvaluateStrainPlane`; это не полноценный solve, но расчет по всем элементам | `BeforeMcrcState`, `AfterMcrcState`, `CrackedState` |
| Общая ветка `N + M`, прямой поиск Mcrc не сошелся и включился fallback | 2 + `k` + `b`: нижняя точка `lambda = 0`, bracketing `k`, бисекция `b`, `AfterMcrcState`, текущий `CrackedState` LC | fallback решает серию обычных НДС при разных `lambda` | `BeforeMcrcState`, `AfterMcrcState`, `CrackedState` |
| Общая ветка `N + M`, поиск без стартового состояния не дал результата | сначала путь выше; затем при необходимости добавляется solve `CrackInitiation` на полном LC и поиск повторяется | это страховочный путь для сложных случаев, чтобы не ухудшать надежность относительно старой реализации | `BeforeMcrcState`, `AfterMcrcState`, `CrackedState` |

Где:

- `k` - количество дополнительных solve-ов при расширении верхней границы `lambda`;
- `b` - количество solve-ов бисекции до заданной точности.

## Зачем нужно каждое текущее состояние

### Текущий `CrackedState` полного LC

Это состояние для фактической нагрузки сочетания по модели `MaterialModel.CrackedState`.

Зачем нужно:

- из него берутся `sigma_s`, растянутая зона, `Abt`, `As`, `ds,eq`, `ls` и итоговая ширина `a_crc`;
- по нему выполняется проверка продольных трещин бетона;
- оно записывается в snapshot, чтобы схема и AutoCAD могли вывести состояние с трещинами;
- оно считается даже если нормальная трещина не образовалась, потому что продольные трещины должны проверяться независимо от нормальных.

Можно ли убрать:

- для профиля с включенным `Calculation.Crack.Width` - практически нет;
- можно было бы не считать его только если отказаться от проверки продольных трещин и от вывода `CrackedState` для такого LC, но это противоречит текущему принятому поведению.

### `BeforeMcrcState`

Это состояние непосредственно перед образованием нормальной трещины по модели `MaterialModel.CrackInitiation`, где растянутый бетон еще работает.

Зачем нужно:

- фиксирует физическое состояние, на котором бетон достигает предельной растягивающей деформации `eps_bt,ult`;
- дает пользователю возможность вывести состояние до трещины и вручную проверить порог;
- в текущей архитектуре сохраняется как named state, если есть действие, способное вызвать нормальную трещину.

Можно ли убрать:

- если не нужен вывод состояния до трещины, для самой формулы раскрытия его можно было бы не записывать в snapshot;
- но для трассируемости `Mcrc/Ncrc` и проверки пользователем оно полезно, поэтому сейчас оставлено.

### `AfterMcrcState`

Это состояние при том же уровне нагрузки образования трещины, но уже по модели `MaterialModel.CrackedState`, то есть без работы растянутого бетона.

Зачем нужно:

- именно из него берется `sigma_s,crc` для формулы `psi_s = 1 - 0.8 * sigma_s,crc / sigma_s`;
- оно показывает состояние сразу после образования трещины;
- теперь оно заранее сохраняется, чтобы при `PsiMode = Auto` не решать то же состояние повторно.

Можно ли убрать:

- при `PsiMode = User` формально можно было бы не считать `sigma_s,crc`;
- но состояние нужно для вывода и для единообразного snapshot-а трещинообразования;
- если оставить его только для Auto, вернется старая ситуация, когда часть состояний появляется только при непрохождении первой проверки ширины.

### Страховочный `CrackInitiation` на полном LC

В общей ветке `N + M` текущий код сначала пробует найти `Mcrc` без обычного solve `CrackInitiation` для полного LC. Если этот путь не дал расчетного результата, программа решает `CrackInitiation` на полном LC и повторяет поиск уже с этой стартовой плоскостью.

Зачем нужно:

- дает хорошую стартовую плоскость для прямого поиска `Mcrc`;
- сохраняет запас надежности на сложных сочетаниях;
- не тратится в типовых случаях, где геометрической стартовой плоскости достаточно.

Можно ли убрать:

- как обязательный шаг он уже убран;
- полностью убирать страховочный повтор нежелательно, потому что он может помочь там, где геометрический старт оказался плохим.

### Fallback-поиск `lambda_crc`

Fallback включается только если прямой поиск плоскости образования трещины не сошелся.

Зачем нужен:

- защищает расчет от `NumFail` при малых моментах, чистом изгибе, почти осевых случаях и сложных геометриях;
- ищет `lambda_crc` обычными НДС-решениями при разных `lambda`, поэтому медленнее, но устойчивее.

Можно ли убрать:

- можно, но тогда вернутся случаи, где расчет трещин падает вместо корректного `Cracked/NotCracked`.

## Главная разница по производительности

Старый вариант был быстрее в случаях, где проверка образования трещины раньше вообще не запускалась:

- `PsiMode = User`: было 1 solve, сейчас обычно 2 solve в общей ветке `N + M` или 3 solve в центральном растяжении;
- `PsiMode = Auto`, первая проверка ширины проходит: было 1 solve, сейчас обычно 2 solve в общей ветке `N + M` или 3 solve в центральном растяжении;
- `PsiMode = Auto`, первая проверка не проходит: было обычно 2 solve, сейчас в общей ветке `N + M` тоже обычно 2 solve, но дополнительно всегда выполняется прямой поиск `BeforeMcrcState` через `EvaluateStrainPlane`.

Текущий вариант дороже прежде всего в тех сценариях, где старая схема вообще не проверяла `Mcrc/Ncrc`. Для сценария `Auto` с непрохождением первой проверки ширины типовое число обычных solve-ов осталось близким к старому, но изменилась очередность и добавилась обязательная трассировка факта образования трещины.

Зато текущий вариант дает то, чего старая схема не гарантировала:

- `Cracked / NotCracked` определяется всегда до расчета ширины;
- `Mcrc/Ncrc` не зависит от того, потребовалось ли уточнять `psi_s`;
- `BeforeMcrcState` и `AfterMcrcState` доступны для вывода и ручной проверки;
- продольные трещины проверяются по текущему `CrackedState` всегда;
- `Auto` не пересчитывает `AfterMcrcState`, а использует уже сохраненное состояние;
- новый fallback уменьшает риск `NumFail` в опасных нагружениях.

## Итоговая оценка

Предыдущая схема была вычислительно экономнее, но методически смешивала две разные задачи:

1. расчет ширины раскрытия уже образовавшейся трещины;
2. проверку факта образования трещины.

Текущая схема разделяет эти задачи:

1. сначала определяется, есть ли нормальная трещина и где находится уровень `Mcrc/Ncrc`;
2. затем всегда считается текущее `CrackedState` полного LC;
3. ширина раскрытия считается только если нормальная трещина образована;
4. продольные трещины проверяются независимо от нормальных.

Поэтому текущая реализация ожидаемо тяжелее по числу НДС-состояний, но лучше подходит для проверяемого snapshot-а, вывода `BeforeMcrcState/AfterMcrcState` и ручной нормативной трассировки.
